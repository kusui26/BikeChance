#### 2.3f 曜日種別の番号は `DOW_TYPES` の順ではない

`eval/dataset.py` の `_dow_type` は「曜日種別を **`DOW_TYPES` の番号**にする」と書いてあるが、**返すのは `sorted(DOW_TYPES)` の番号**である。

```
DOW_TYPES        = ('weekday', 'sat', 'sun_holiday')
sorted(DOW_TYPES) = ('sat', 'sun_holiday', 'weekday')
  'weekday'     → 2   （DOW_TYPES[2] = 'sun_holiday'）
  'sat'         → 0   （DOW_TYPES[0] = 'weekday'）
  'sun_holiday' → 1   （DOW_TYPES[1] = 'sat'）
```

**確率は正しい。** 当てはめも配信も同じ写像を通るので（配信側は `models/predictor.py` が `tuple(sorted(DOW_TYPES))` と書いている）、セルはずれない。**ずれるのは名前のほうである**——§2.3c の表を最初に出したとき、平日のセルが「日祝」と表示された。

| # | 論点 | 決定 | 理由 |

### 4.1 実装のあとに足した判断（2026-09-13）

**PR A〜D を作ってから分かったこと**を 4 つ。**どれも「決めてから実装する」に間に合っていない**ので、決めた根拠を数字と一緒に残す。

## 5. 実装で踏みそうな落とし穴

**W4 までに踏んだものと同じ形のものが 6 つ見えている。** 先に書いておく。

### 5.1 成果物の並びを「直す」と、過去の成果物が別のセルを指す

§2.3f のとおり、曜日種別の番号は `sorted(DOW_TYPES)` である。**`DOW_TYPES` の順に「直す」のは、いちばんやりそうで、いちばん静かに壊れる。** `weekday` の 663,085 セルが `sun_holiday` として読まれ、**例外は出ず、確率だけが変わる。**

**やること**：値を変えず、**名前を付けて 1 か所に置く**（W5-08）。**落ちる検査**を書く——`DOW_TYPE_ORDER == ("sat", "sun_holiday", "weekday")` を固定し、`eval/dataset.py` と `models/predictor.py` が同じ写像を返すことを突き合わせる。

### 5.2 ECE のビンを変えると、v0 の 0.0359 と比べられなくなる

`docs/260910_eda_03_lightgbm_v0.md` と開発プラン §7.4 に **ECE 0.0359**（20 等幅）という数字が残っている。**定義を変えた新しい数と並べると、変わったのが確率なのか物差しなのか分からなくなる。**

**やること**：**乗り換える PR（PR C）で、同じ成果物を両方の定義で測って両方を書く。** 以降は等頻度を判定に使い、等幅は図に残す。

### 5.3 プロファイルは「前日まで」。当日を入れるとリークする

開発プラン §6.2 のリーク防止は「ポート単位の履歴プロファイルは、`t` の**前日 23:59 まで**のデータで計算した値のみ使う」と書いている。**`build_reference` と同じ規則**（前日の版を読む）。

**踏みやすい形**：推論は「今日」動くので、**今日のプロファイルを作って読みたくなる**。作った瞬間に、当日の観測が特徴量に入る。**学習では絶対に作れない値**なので、`test_features_parity.py` では捕まらない（学習側にその日が無い）。

**やること**：プロファイルのパスを**日付で切り**、読む規則を「基準時刻の**前日**の版」に**1 か所で**固定する（`features/reference.py` と同じ関数の形）。**推論側も学習側も同じ関数を通す。**

### 5.4 プロファイルの成果物が大きくなりすぎる

いまのベースライン成果物は **3.36 MB** で、使えるセルは **663,085** である。**全格子から作ると 20,628 ポート × 3 曜日種別 × 96 枠 ＝ 594 万セル**になりうる。**単純に 9 倍なら 30 MB** で、5 分毎に取り直せば **1 日 17.3 GB**（30 MB × 288 × 2 系）の転送になる。いまでも **1.8 GB／日**（3.36 MB × 288 × 2）で、開発プラン §8.2 が「900 MB」と書いているのは 1 系ぶんである。

**やること**：**PR B で先に測る。** 減らす手は 3 つあり、**測ってから選ぶ**。

1. 確率を `int16`（×10000）で持つ（いまは JSON の float）
2. `n_days < 2` のセルを**書かない**（下限に届かないセルは B1 に落ちるので、持つ意味が無い）
3. **成果物に混ぜず別ファイルにし、日次で 1 回だけ取る**（版は日付なので、日に 1 回しか変わらない）

### 5.5 グリッド集約は「同じ確率を 2 つの形で配る」入口になる

契約 4 と同じ形である。**セルの確率とポートの確率が両方返ると、どちらが正か決まらない。**

**やること**：**低ズームでは `stations` を返さない**（`cells` だけ）。**高ズームでは `cells` を返さない**。境目は**要求の辺の長さ**で決め、応答に**どちらを返したかを書く**（`aggregation: "cell" | "station"`）。**同じ応答に両方は入れない。**

### 5.6 `FEATURE_SET` v4 に上げると、作り直す日数が 1 日ずつ増える

契約 8（版を上げたら前の版と混ぜて学習しない）より、`prof_*` を足した瞬間に **v3 の日は v4 の学習に使えない**。**作り直しは可能**だが（`status_snapshots` 60 日・`weather_hourly` 30 日・PR L の手順で天気は生から戻せる）、**待つほど本数が増える**。

| **9/24（いまの予定）** | **17 日** | **17〜51 分** |
| 9/26 | 19 日 | 19〜57 分 |

#### 純粋な部分と副作用を分ける

```

  FORECAST_LOG_BUCKET / FORMAT_VERSION / SCHEMA
  log_path(system_id, base_observed_at, model_version) -> str
  to_table(forecasts, base_observed_at, model_version, ...) -> pa.Table

bikechance_ml/jobs/infer.py            ← 呼ぶだけ。失敗は握って detail に残す
```

**`to_bytes` は `jobs/build_features.py` の `to_parquet_bytes` と同じ形にする**（zstd・同じ圧縮水準）。**2 つ目の書き方を作らない。**

- **`station_id` を昇順に並べてから書く**（PR N の実測：並びが圧縮に効く）。`station_forecasts` に渡す順とは別で、**ここで並べ替える**

### 6.2 PR B：ポートプロファイル（全格子から日次で作る）

**W5 の本体。** §2.3d で測ったとおり、気候値が痩せているのは抽出が原因である。**全格子から作れば、その曜日種別の 2 日目に下限を満たす。**

#### 何を作るか

```
profiles/date=YYYY-MM-DD/daily.parquet     ← その日ぶんの素の集計
profiles/date=YYYY-MM-DD/profile.parquet   ← 直近 28 日の累積（読むのはこちら）
```

**`gbfs-parquet` バケットに置く**（`reference/` と同じ。MIME は Parquet で通る。W3 プラン §12 の 106）。

| `daily.parquet` の列 | 型 | 意味 |
|---|---|---|
| `system_id` / `station_id` | `string` | |
| `dow_type` | `string` | **その日 1 つだけ**（`weekday` / `sat` / `sun_holiday`） |
| `slot15` | `int16` | 0〜95 |
| `n` | `int16` | 観測できた 5 分格子点の数（**最大 3**） |
| `n_bike_ok` / `n_dock_ok` | `int16` | `bikes ≥ 1 ∧ is_renting` / `docks ≥ 1 ∧ is_returning` を満たした数 |
| `sum_bikes` / `sum_bikes_sq` | `int32` | `prof_mean_bikes` / `prof_std_bikes` の材料 |
| `n_rentals` / `n_returns` | `int32` | **フィード本来の周期で数えた**流量（W3-11。`features/flow.py` と同じ実装） |

`profile.parquet` は同じ列に **`n_days`**（そのセルに寄与した日数）を足したもの。

#### 積み上げ方（W5-05）

**`build_reference` の `capacity_daily_max` と同じ持ち回り。**

```
profile(D) = profile(D-1) + daily(D) - daily(D-28)
```

読むのは **3 ファイルだけ**（`profile(D-1)`・当日の毎時 Parquet 48 本・`daily(D-28)`）。28 日ぶんを毎日読み直すと 1 回 150〜400 MB になる。

**`daily(D-28)` が無い日は引かない**（`n_days` がそのぶん小さく出るだけ）。**`profile(D-1)` が無い日は当日だけで作る**（初日）。

#### 除外規則は 1 実装（契約 6）

**`features/exclude.py` をそのまま通す。** 観測されていない（配列が `-1`）・実在しないポート（`PHANTOM_STATIONS`）・フィード全体の異常は、ここでも同じ規則で落とす。**`stations.is_active` は使わない**（生存者バイアス。開発プラン §6.1）。

**休止中（`flags`）は落とさない。** `n_bike_ok` の定義そのものが `is_renting` を含むので、**休止していた時間は「借りられなかった時間」として数える**——これは B2 のラベルの定義（`y_bike = 1[bikes ≥ 1 ∧ is_renting]`）と一致する。

> **⚠️ 推定している量がわずかに変わる。** いまの B2 は **`t` が休止していなかった行だけ**から作られている（`features/exclude.py` の `suspended_at_t`）。**プロファイルには `t` が無い**ので、その条件が外れる。恒常的に休止しているポート（実測：HELLO **557**・ドコモ **28** が `flags <> 7`）で差が出る。

#### どこで走らせるか

**GitHub Actions（`build_features` と同じワークフロー、同じ `training` 環境）。** 理由は W4-27 と同じで、加えて 2 つ。

- **`build_features` が読む**（PR J で `prof_*` を足したあと）ので、**プロファイルが先に走る必要がある**。同じジョブの中で順に走らせれば順序が保証される

> **等頻度にすると数字は上がる見込み。** …**潰れていた中のずれが表に出る。**

**予想は外れた**（§12 の 139）。5 日ぶんのベースライン（09-07〜09-11、検証 2 日）で測ると、**差が大きいのは B3** である。

|---|---:|---:|---:|
| B0 | 0.14592 | 0.14592 | 0.00000 |
| B1 | 0.01048 | 0.01048 | 0.00146 |
| B2 | 0.09182 | 0.09228 | 0.00260 |
| **B3** | **0.03339** | **0.03784** | **0.01562** |

**理由は分布の形である。**

| | 確率の形 | 等幅 20 区間で何が起きるか |
|---|---|---|
| B0 | 0 か 1 | 2 区間。**どちらの物差しでも同じ** |
| **LightGBM** | **連続でばらける** | 20 区間が全部埋まり、1 区間の中が狭い。**ほぼ同じ値になる** |
| **B3** | **少数の値が上端に固まる** | 上端の 1 区間に大量に入り、**中のずれが平均で消える**（§2.3e） |

**つまり、物差しを変えて効くのは「いま配っているベースライン」のほうだった。** W5 の PR D はまさにそこを入れ替える PR なので、**先に物差しを直しておいたのは正しかった**——ただし理由は書いたものと違う。

##### ③ スライスは 2 つ足した（4 つではない）

| 軸 | 足したか | 理由 |
|---|---|---|
| **曜日種別** | **✅** | `Samples.dow_type` が既に在る。**PR D の効果はここに出る** |
| **時間帯**（到着時刻） | **✅** | `minute_of_day + h_min` で作れる。**`t` ではなく `t + h` で切る** |

```sql
  from storage.objects where bucket_id = 'forecast-log' group by 1,2 order by 2,1;

-- 書けなかった回
select count(*) from public.inference_log
 where detail->>'forecast_log' is distinct from 'ok' and generated_at > now() - interval '24 hours';
```

### 8.3 確率がポート別になったこと（PR D）— **W5 の主判定**

```sql
-- 1 水平あたりの相異なる値。**いま 8〜12**
select h.i as 添字,
       count(distinct p_bike_x1000[h.i]) as 異なる値_bike,
       count(distinct p_dock_x1000[h.i]) as 異なる値_dock
  from public.station_forecasts, generate_series(1,10) as h(i)

-- confidence の分布。**いま全ポート 2**
```


## 12. 見つかった問題

**W4 の 130 から続けて 131 番から採る。** 131〜134 は**着手前の点検**（この文書を書くために本番を測ったとき）で見つかったもので、§2.3 に詳しく書いた。

### 131. **配信している確率は、B1 の台数バケツの関数そのものだった**（着手前）

**1 システム・1 水平あたりの相異なる値は 4〜6 個**（§2.3a）。B1 の参照表のバケツ数はちょうど **6**（`0 / 1 / 2 / 3-5 / 6-10 / 11+`）で、**一度も超えていない**。HELLO の 14,407 ポートは、h = 30 分で **5 個の値**に塗り分けられている。**ポートの識別子は 1 ビットも効いていない。**

**原因は B2（気候値）が 100% B1 に落ちていること。** `docs/260908_eda_02_baseline.md` が「日数が足りない」と書き、W3-17 が予告していたとおりである。**だが「日数」だけではなかった**——**3.50% の抽出が、1 セルあたりの情報を 3 点から 1.62 行に削っていた**（§2.3d）。

**見落としていた理由**：**W4 は「予測が地図に出るか」を確かめて、「出ている数がどれだけ違うか」を確かめなかった。** 合格基準（W4 プラン §1）に「予測の被覆 96% 以上」は在るが、**被覆は「予測が付いたか」であって「意味のある予測か」ではない**。

**規則**：**配るものは、数だけでなく分布を見る。** W5 の合格基準に「**相異なる値の数**」を入れた（§1.2）。

### 132. **曜日種別の番号は `DOW_TYPES` の並びではない**（着手前）

`eval/dataset.py::_dow_type` の docstring は「`DOW_TYPES` の番号にする」と書いているが、返すのは `sorted(DOW_TYPES)` の番号である（§2.3f）。

```
'weekday' → 2   （DOW_TYPES[2] = 'sun_holiday'）
```

**確率は正しい**（当てはめも配信も同じ写像を通る）。**間違っているのは名前のほうで**、§2.3c の表を最初に出したときに平日のセルが「日祝」と表示された。

**危ないのは、規約が 2 か所に書かれていて名前が無いこと。** `eval/dataset.py` と `models/predictor.py` が別々に `sorted` を呼んでいる。**片方を「直す」と、Storage に在る成果物が別のセルを指す——例外は出ず、確率だけが静かに変わる。**

**直し方**：値を変えず、**`DOW_TYPE_ORDER` として名前を付けて 1 か所に置く**（PR C）。**わざと `DOW_TYPES` の順に直すと落ちる検査**を書く。

**同じ形の所見**：117（読んだ窓の長さで値が変わる列）、122（格子の鍵の丸めがたまたま一致している）。**「たまたま合っている」を、合っていると書かないこと。**

### 133. **ECE のビンが、プランと実装で違う**（着手前）

開発プラン §7.3 は「**15 等頻度ビン**」、`eval/metrics.py` は「**20 等幅**」（§2.3e）。

**しかもいまの確率は等幅 20 ビンのうち 4 つにしか入らず、66.7% が最上位ビン（0.95〜1.00）に入る。** アプリの約束（85% 以上＝「ほぼ大丈夫」。開発プラン §9.3）を測るのに、**いちばん大事な帯がいちばん潰れている。**

配信が読むのは**成果物**で、成果物の B2 は **`fit_baseline` を走らせたときのプロファイル**から作られて**固まる**。これは W5-04（「推論が 5 分毎に 200 万行を引かない」）を選んだことの裏返しで、**設計どおり**である。**間違っていたのは表のほうだった。**

**気づいた経緯**：PR D をマージしたあと「次に何をやるべきか」を数えていて、**9/21 に何が起きるかを実装に当てて追った**ときに出た。**プランを書いた時点では、B2 をどこから引くかを決めていて、いつ引くかを決めていなかった。**

**何が失われかけたか**：**5 連休の 5 日とも、土日祝のセルが 0 のまま配ることになっていた**（§7.2 を「何もしない場合」として書き直した）。**W5 でいちばん急いだ理由がそのまま無駄になる。**

2. **当てはめ直しを日程のゲートにした**（⭐ 9/13 と ⭐ 9/21。§7.1）
3. **契約 20 に書いた**——「成果物は当てはめた時点の気候値を持つ。配信はプロファイルを読まない」
4. **古びたら鳴らす**（PR M）。**忘れたときに黙って古い確率が出続ける**のがいちばん悪い

**同じ形の所見**：137（「前日の版」がどちらの意味かを取り違えた）、143（同じ関数が使えるかを単位で確かめなかった）、145（日付を暦で数え直さなかった）。**いずれも「プランの言葉が実装の 1 つの解釈しか指していない」**。

**規則**：**「効く」と書くときは、誰が・いつ・どこから読むかまで書く。** 量（何を）だけでなく、**経路（どこを通って配信に出るか）**を書く。

### 150. **`capacity_est` は Storage にしか無かった**（PR F）

### 154. **「24 時間で切る」の検査が恒真だった**（PR F）

### 155. **「3 日で鳴らす」は狼少年の閾値だった**（PR M）

§6.13 は当初「**3 日以上前なら鳴らす**」と書いていた。**実装のときに数え直したら、
どちらの運用でも鳴りっぱなしになる。**

| 閾値 | 週次運用（W6 以降。月曜に当てはめ直す） | W5 の途中（09-12 までの版が `active`） |
|---|---|---|
| **3 日** | 木・金・土・日と**毎週 4 日ぶん鳴る** | **09-15 から 09-21 まで連続**（6 時間おき ＝ 約 24 通） |
| **7 日** | **毎週 1 回必ず鳴る**（正常の上限でちょうど鳴る） | 09-19 から鳴る |
| **8 日**（採った） | **週次を 1 回飛ばしたときだけ** | **09-20 に 1 通**（⭐ 9/21 の当てはめ直しの前日） |

**間違えていたのは「何日で古いか」ではなく、「鳴ったとき何をするか」だった。**
3 日で鳴る通知に対してできることは「まだ大丈夫」しかない——**正常な状態でも鳴る閾値は、
読まれなくなる**。8 日なら答えは常に 1 つ、「`fit_baseline --upload` を回して、測ってから
昇格する」である。

**規則**：**見張りの閾値は「異常の定義」ではなく「鳴った日の行動」から決める。**
正常な運転で 1 度でも鳴るなら、その閾値は間違っている。

**同じ形の所見**：W1 の 43（期待周期が 1.1% 楽観的で、**取りこぼしゼロでも毎日 98.9% と表示され続ける**——「鳴りっぱなしの警報は無視されるようになる」）、W3 プラン §14.8（「**鳴りっぱなしの通知は、鳴らない通知と同じくらい役に立たない**」）。**3 度目なので、規則として書いておく。**

### 156. **「昇格を呼んでいない」は、名前の不在では測れなかった**（PR M）

完了条件 5 は「`promote_model_version` を呼ぶ経路がコードにもワークフローにも無いこと」で、
最初は**リポジトリ全体で文字列を禁じる**検査を書こうとした。**書けなかった。**

```
jobs/infer.py:383       … 配信を切り替えるのは `promote_model_version()` の仕事で、
jobs/fit_lightgbm.py:629 … **配信に切り替えるには `promote_model_version()` を人が呼ぶ**
```

**この 2 つは消してはいけない文である。** 境界がどこにあるかを読む人に伝えているのは
散文のほうで、消すと**境界そのものが見えなくなる**。かといって「この 2 ファイルは除く」に
すると、**除いたファイルに呼び出しを書けてしまう**。

**分けたのは「散文」と「呼ぶ形」だった。**

| 見るもの | 当たるもの | 当たらないもの |
|---|---|---|
| `promote_model_version\s*\(\s*[^)\s]` | `promote_model_version('x')`・`($1)` | 散文の `promote_model_version()`（括弧が空） |
| `rpc/promote_model_version` | REST から呼ぶ形（`io/supabase.py` の書き方） | — |

そのうえで、**自分の手を介さずに走るもの**（`.github/workflows/`・`scripts/`・
`supabase/functions/`・`bikechance_ml/io/`）だけは**名前すら持たせない**。
`io/` を入れているのは、Python から DB を叩く口がそこだけだからである（CLAUDE.md §3）。

**除外そのものも検査する。** `supabase/migrations/`・`supabase/tests/`・`docs/` の 3 つは
呼ぶ形を持っていてよい場所だが、**その 3 つが実際に呼ぶ形を持っていること**も同じ試験で
確かめる——持っていなければ「効いていない除外」で、上の 2 つは知らないうちに何も
守らなくなる。

**置き場所も間違えかけた。** 最初は `apps/ml/tests/` に pytest として書いたが、
**`python.yml` は `apps/ml/**` が変わった PR でしか走らない**——ワークフローだけを変える
PR は素通りする。**`ci.yml` の `secrets` ジョブ**（すべての PR で走り、同じ形の検査を
7 つ持っている）に移した。**完了条件が「`git grep` で確かめる」と書いていたのとも、
字面で一致する。**

**規則**：**禁じるのは名前ではなく形である。** そして**除外を書いたら、除外が生きていることも
検査する。** **不変条件を守る検査は、その不変条件が壊れうるすべての PR で走る場所に置く。**

### 157. **当てはめ直しが 1 行になると、配信中の成果物を上書きしやすくなる**（PR M）
