### 249（11/21）：`training` 環境は main 以外の枝を通さない（W12-06 の「枝から回す」は一時的な許可が要った）

### 250（11/22）：途中まで保存できた発行では、欠けた分割の格子の天気が次の発行まで欠ける

**見つけ方**：PR T の「途中まで保存できた時間は取り直さない」の理由を書くとき、下書きの「推論は直近 3 つの発行を使い、欠けた分割の格子は 1 つ前の発行が埋める」をコードで確かめた。

- **作り**：天気の特徴量は、基準時刻ごとに「使ってよい中でいちばん新しい発行」を 1 つ選ぶ（`features/weather.py` の `Weather.issue_at`）。値はその発行 × 格子 × 時間帯から引き、**格子ごとに古い発行へは戻らない**（無ければ NaN）。推論と学習は同じ関数を通るので、2 つの間に食い違いはない
- **起きること**：分割が欠けた発行（直近 40 日の 941 時間で 7 時間。11/15 01:17 は 7 分割のうち 3 つ）が最新でいる約 1 時間、欠けた分割の格子のポートは天気の 4 列が NULL になる（LightGBM は欠けとして扱う）。推論の記録の `stations_without_weather` は「どの発行にも格子が無いポート」だけを数えるので、この欠けは出ない（11/15 01:20〜02:20 も 16 のまま）
- **47 分の取り直しで埋めない理由**：欠けた分割を同じ時間の別の回で足すと、取り込みが同じ発行に遅い入手時刻を重ね、特徴量は遅いほうを採る（`_issue_order`）——それまで配っていた格子のぶんまで、学習では使えなくなる（W7-01）
- **扱い**：W12 では変えない（時間で 0.7%。起きたのは分割の時間切れの時間だけ）。格子ごとに 1 つ前の発行へ戻す形は特徴量の意味が変わる（`FEATURE_SET` の版を上げて森を当てはめ直す）ので、W13 以降に「推論の記録に、欠けた格子の数を足す」と合わせて諮る

### 251（11/26）：GitHub の障害中に push した PR は、障害が明けても古いコミットのまま（CI も走らない）

**見つけ方**：#212 に掲載情報 v0.3 を push した直後（11/26 01:05）から GitHub が障害（01:11〜。Pull Requests が大規模障害、Actions が一部障害）。枝は新しいコミット（a4b0978）なのに PR は古いコミット（b911d1c）のままで CI も走らず、マージの見張り（8 時間）は時間切れでマージしなかった。09:28 には障害は明けていたが、PR は古いままだった。

- **作り**：PR の head は push の知らせ（synchronize）で進む。障害中に失われた知らせは、障害が明けても送り直されない。枝そのもの（`git ls-remote`・`gh api …/branches/…`）は新しいので、`git status` では気づけない
- **直し方**：`gh pr close` → `gh pr reopen` で head が枝に追いつき、CI も走った（09:29。空のコミットは要らない）。マージは `gh pr merge --match-head-commit <SHA>` で、確かめたコミットに限った（09:30:38、a13b601）
- **影響**：#212（文書だけ）のマージが 8 時間遅れただけ。本番（Vercel・Supabase）は GitHub と独立に動き、収集・推論・Cron は止まらなかった。GitHub Actions の定時（日次の枠の 00:40）は 08:47 に来た（ほかの日と同じくらいの遅れ）
- **これからの形**：GitHub の障害の後は、マージの前に PR の head（`gh api …/pulls/N --jq .head.sha`）と枝の先が同じかを確かめる。食い違っていれば close・reopen で追いつかせ、CI を待ってからマージする
