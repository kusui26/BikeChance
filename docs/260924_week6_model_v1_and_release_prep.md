## 1. W6 のゴールと完了条件

**ゴール：LightGBM v1 を、費用の上限（公開後の定常で Vercel の使用量 $20。D-32）の内側で、門を越えたセルにだけ配る（M4）。あわせて、TestFlight（W7）に出せる下地を作る。**

W5 で確率はポート別になり（B3 の B2 がプロファイルから引ける）、配った確率を測る仕組み（予測ログ・日次評価）も揃った。**残る差分は「ポートの個性を、木が掛け合わせで持つ」こと**で、それが v1 である。9/24 の予備の当てはめで、**v1 は B3 を 40 組中 31 組で 10% 以上上回り、100 本でも 300 本の効果の 96% を保つ**ことが分かった（M4 の文書 §1.4）。**作る側は準備ができている。配る側がまだである。**

**W6 の主題は 4 つ。**

1. **配る側の前提を揃える。** 成果物の書式（W5 プラン §12 の 176）・推論がプロファイルを読む（J2）・shadow の経路・合成器・特徴量の経路 B。**どれも「配信の関数を v1 のために空ける」か「2 つのモデルを並べる」仕事**で、本番の推論に触る。**平日の朝に 1 日 1 つ**入れる（§6.0）。
2. **v1 を当てはめて置き、測ってから配る。** 28 日ぶんを当てはめる場所（Actions）→ 予行演習 → 試し打ち → shadow（3 連休を含む 4 日）→ active。**門はセル単位で当て、本数は費用の上限から決める**（D-32）。
3. **B3 を回し続ける。** 下限の形と leave-one-out の直し（W5 プランの所見 179・180）と、鮮度の警報に合わせた当てはめ直し（9/29・10/6・10/13）。**B3 は合成器の中で「門を越えないセル」を受け持ち続ける**ので、W6 で捨てるものではない。
4. **TestFlight の下地を作る。**
   - クレジットと免責（「改変して利用」の書式、天気と祝日の出典）
   - 予測時刻の表示の漏れ
   - iOS のセル応答のバグ
   - プライバシーマニフェストと暗号化の申告
   - **アイコンと署名は利用者の作業**（§7.4）

## 5. 実装で踏みそうな落とし穴

### 5.1 書式の版を上げた瞬間に、配信中の成果物が読めなくなる

`baselines/artifact.py` の `from_bytes` は `if version != FORMAT_VERSION: raise` で照合している。**版 2 だけを読む実装を先に出すと、その時点で active（版 1）が読めず、推論が止まる。** **版 1 と 2 の両方を読む実装を先に入れ、当てはめ直し #1 で版 2 に移る。** 版 1 を読む道を消すのは、版 1 の成果物が active・shadow・候補のどこにも無くなってから（契約 30）。

### 5.2 キャッシュが 1 つしか持たない

`registry.load` は版が変わると `_CACHE.clear()` する。**active と shadow を同じ周期に読むと、互いを追い出して毎回落とし直す**（§4 の W6-02）。**検査は「2 周期目に下りが 0」で書く**——値が合っていても、落とし直していれば費用と下りが漏れる。

### 5.3 Range 要求は効くが、並びが揃っていないと全部を落とす

契約 28 の並び（`dow_type, slot15, system_id, station_id`、1 行群 ＝ 1 セル）が崩れると、Range で取っても**行群の数だけ往復してファイル全体を落とす**。**並び替え（PR C）が本番のファイルに出た次の周期から部分読み（PR D）を入れる**——逆にすると、並び替え前のファイルを丸ごと読む日が 1 日でき、下りが約 8 GB 増える。

### 5.4 朝の穴

前日の版は 06:00（遅れれば 08:00）までできない。**00:40 の枠を足しても、Actions の遅れで 0 にはならない**。1 つ古い版に落とす道（W6-04）が無いと、**毎朝 J2 が `prof_*` を NULL で配り、合成器が毎朝 B3 に落ちる**。

### 5.5 shadow のメモリは切り離せない

shadow の例外は `try` で包めるが、**メモリ不足は active ごと同じ呼び出しを落とす**。3 連休の前に初めて shadow を入れるので、**平日に小さな候補で予行演習をしてから**にする（§7.2）。

### 5.6 shadow を下ろす口が無い

`promote_model_version` は active か shadow にしか動かせない。**合成器を active にしても、LightGBM 単体の shadow は走り続け、森の費用が 2 倍になる。** PR E で `retire_model_version` を足し、M4 の手順に「shadow を下ろす」を入れる（§8.9）。

### 5.7 門の相手が本番の B3 と違う

`harness.run` の B3 は学習窓ぜんぶで当てはめるので、**本番の 7 日の B3 より強いか弱いかが分からない**。報告書の「B3 比 +12%」が本番では +10% かもしれない。**相手は本番と同じ作り方にする**（W6-10）。

### 5.8 本数だけを減らすと、校正が崩れる

予備の当てはめで、学習率 0.05 のまま 100 本で止めると ECE が 0.0311 だった（基準は 0.03）。**本数と学習率は組で決める**（契約 37）。

### 5.9 特徴量の経路 B は、学習・推論・圧縮で共有している

`snapshot_table.to_table` は**毎時の Parquet 化**でも使い、`asof`・`flow` は**学習（`build_day`）と推論（`build_now`）の両方**で使う。**1 つでも値が変わると、学習と推論が静かにずれるか、一次ソースの次の Parquet が変わる。** 検査は 3 か所のバイト一致で書く（契約 40）：過去の時刻での `build_now`、過去の日の `build_day`、過去の時間の `to_table`。

### 5.10 合成器の境目で、確率が段になる

水平の境（例：h = 30 は B3、45 は LightGBM）やバケツの境で、**同じポートの確率が段になる**。地図は水平のあいだを線形補間するので、段はそのまま曲線に出る。**PR H で境目の差（|P_LGBM − P_B3| の分布）を測り、報告書に出す**。大きければ利用者に諮る。

### 5.11 3 連休の前の shadow

原則（連休の前に配信の形を変えない）の例外である（§7.2）。**予行演習が済んでいなければ、shadow は 10/13 から、active は 10/19**。

### 5.12 鮮度の警報と合成器

合成器の `train_days` を LightGBM の日だけにすると、10/13 に入れた瞬間に鳴る（W6-08）。**2 つの和にする**。そのうえで、**LightGBM の部分が何日前のデータかは報告書とカードに出す**（警報では見ない）。

### 5.13 当てはめ直しの `--upload` の上書き

v1 と合成器を置く経路が増える。**配信中の版の名前で置けないようにする**（W6-19、契約 38）。

### 5.14 iOS の 0.08 と 0.1

W5-19 は「iOS は 0.1 度より広い矩形を要求しない」ので影響しないと書いたが、**サーバーがセルに切り替えるのは 0.08 度**で、比べる向きが逆だった。**閾値を 1 か所に書き、iOS の要求がそれを超えないことを検査で固定する**（契約 41）。

### 8.3 J2（PR C・PR D）と 28 日窓の引き算

```sql

       count(*) filter (where detail->>'profile_date' is null) as 読めなかった回,
```

## 12. 見つかった問題

**番号は M4 の文書 §3 の続き（〜186）から振る。** どれも 2026-09-24 に、この文書を書く前の下調べで見つけた。

### 187. **J2 の「1 周期 1.51 MB」は手元のファイルで数えた値で、本番の読み口はファイル全体を落とす**

W5 プラン §6.10 の「先に測った」②は、**読んだバイトを数えて**部分読みの効きを確かめた——ただし**手元のファイル**で。本番の読み口（`SupabaseIo.download`）は **GET 1 回でオブジェクト全体を落とす**。**並びを揃えても、この口のままでは 1 周期 15〜44 MB を落とす。**

**Range 要求は本番で効く**（§13.1）：`206 Partial Content`、末尾からの範囲指定も効く。**読み口を新しく作る**（W6-03、PR D）。

**規則**：**手元で測った効きは、本番の読み口を通して確かめる**。測った道と使う道が違えば、効きは移らない。

### 188. **J2 の「前日の版を読む」は、00:00〜06:00 に前日の版が無いことを見込んでいなかった**

プロファイルは `build-features.yml` が **06:00 JST**（遅れれば 08:00）に作る。**毎日 00:00〜06:00 の推論は、前日の版を読めない**。このままだと J2 は毎朝 `prof_*` を NULL で配り、合成器は毎朝 B3 に落ちる。

**参照スナップショットで同じことが起き、同じ形で直した**（W4 プラン §12 の 118：05:00 に置かれるので、00:00〜05:00 は 1 つ古い版を使い、日付を残す）。**J2 も同じ手当てにする**（W6-04）。そのうえで、プロファイルを 00:40 の枠でも作り、古い版で配る時間を縮める。

**規則**：**「前日の版を読む」と書くときは、その版がいつ置かれるかを一緒に書く**。

### 189. **成果物のキャッシュが 1 つしか持たない**

`models/registry.py` の `load` は、版が変わると `_CACHE.clear()` してから新しい版を入れる。**配るものが 1 つのあいだは正しかった。** shadow（active と shadow）と合成器は同じ周期に 2 つ以上を使うので、**毎周期、互いを追い出して落とし直す**。版 1 の成果物（20 MB）なら下りは月 300 GB を超える（W6-02）。

**規則**：**「1 つだけ持つ」キャッシュは、同時に使うものが増えた日に必ず見直す**。検査は「2 周期目に落とし直さない」で書く。

### 190. **shadow を下ろす口が無い**

`promote_model_version(p_version, p_status)` の行き先は `active` か `shadow` だけで、**代わりを立てずに shadow を retired にする方法が無い**。予行演習の後にも、合成器を active にした後にも要る。後者を忘れると、**LightGBM の shadow が全行を歩き続け、森の費用が 2 倍になる**。`retire_model_version` を足す（W6-07、PR E）。

### 191. **版の照合が完全一致なので、書式を上げた瞬間に配信中の成果物が読めなくなる**

`baselines/artifact.py` の `from_bytes` は `if version != FORMAT_VERSION: raise`。**書く側と読む側を同じ PR で版 2 にすると、デプロイした瞬間に active（版 1）が読めず、推論が止まる**。**読む側は版 1 と 2 の両方**にし、書く側は当てはめ直しで版 2 に移る（契約 30）。

**規則**：**書式を上げるときは、配信中の成果物が古い書式であることを前提に、読み手を先に広げる**。

### 192. **開発プラン §8.4・§11.1 の「自動ロールバック」は、CLAUDE.md §6 と契約 22 に反する**

開発プラン §8.4 は「悪化時は自動ロールバック」、§11.1 は「昇格：candidate → shadow（3 日）→ active。自動ロールバック」と書いている。**CLAUDE.md §6 は「モデルの active 切替・ロールバック」を確認なしに実行しないと決め**、W5 の契約 22 は昇格の経路をコードにもワークフローにも作らないと決めた。**ロールバックも active の切替である。** **取り下げ、人が戻す手順（§8.10）に置き換える**（D-36）。

### 193. **推論の CPU は、特徴量の計算より「前処理」が重い**

9/24 に、推論の特徴量づくり（`infer.read_features`）を手元でプロファイルした（§13.4）。**上位はどれも、特徴量の定義ではなく前処理**だった：①JSON の整数配列の要素ごとの型検査（`isinstance` が 1,000 万回を超える）、②配列から長形式への展開、③as-of の内包表記、④流量のポートごとのループ、⑤**5 分ごとの、前日の参照スナップショットの組み立て直し**（1 日に 1 回しか変わらない）。W4 の案 B（「配列の検査と長形式化を numpy に寄せる」、見込み −$2.7）は①②だけを数えていた——③〜⑤は数えていない。**⑤は危険が小さく単独で効く**（W6-20、PR G）。

**但し書き**：手元の機械はメモリを他のアプリと取り合って退避を多用しており、プロファイラ自体も関数呼び出しを重く見せる。**絶対値ではなく順位だけを使う**。PR G の最初に、段ごとの所要を本番で取る。

### 194. **iOS がサーバーのセル応答を読めない——W5-19 の比べ方が逆だった**

W5-19 は「iOS は 0.1 度より広い矩形を要求しないので、セル応答は iOS に影響しない」と書いた。**サーバーがセルに切り替えるのは 0.08 度**（`cells.ts`）で、**iOS は 0.08〜0.1 度の矩形を要求しうる**（外側に丸めると最大約 0.12 度）。応答の型（`StationsResponse`）は `stations` を必須にしているので、**そのとき読み取りに失敗し、赤い帯を出す**。**本番で確かめた**（§13.3：0.09 度で `aggregation: cell`・`stations` 無し）。**契約テストにセル応答のフィクスチャが無かった**ので捕まらなかった（W6-30、PR I）。

**規則**：**閾値を 2 か所に書かない**。書くなら、**両側の検査が同じ値を書く**。

### 195. **クレジットの書式が開発プラン §3.7 と違い、天気・祝日・行政区域の出典が無い**

開発プラン §3.7 は ODPT の FAQ の「改変して利用する場合」の書式（「このアプリは、以下の著作物を改変して利用しています。」を**前に**置く）を採った。iOS は「上記の著作物を改変して利用しています。」を**一覧の後に**、**3 か所に焼き付けて**いる（サーバーには `CREDIT_TEXT` が在るが、`/v1/meta` に載っていない）。**天気（Open-Meteo、CC BY 4.0・リンク表示）、祝日（内閣府）、行政区域（総務省）の出典はどこにも無い**（開発プラン §6.4 は表示が要ると決めてある）。W6-31、PR J。

### 196. **予測時刻が Trip Check とお気に入りに無く、目的地の候補の実測値に観測時刻が無い**

CLAUDE.md §2 の原則 7（実測値には観測時刻、予測値には予測時刻を必ず添える）と、開発プラン §9.2 の「鮮度の表示は必須」。**ポート詳細だけが満たしていた**。W6-32、PR J。

### 197. **意思決定の指標（開発プラン §7.3）とデータの版（§7.5）が、どこにも実装されていない**

開発プラン §7.3 は `precision@0.9`・`coverage@0.9`・3 段階の実現率を「モデルカードに記録」と求め、§7.5 は「使用した Parquet ファイル一覧＋ハッシュ」で版を固定すると書いた。**どちらもコードに無い**。v1 のカードに載らない。**J1 のように同じパスを作り直すので、パスだけでは版にならない**。W6-16・17、PR F。

### 198. **門の相手の B3 が、本番の B3 と違う作り方だった**

`fit_lightgbm` は `harness.run` の B3 と比べる。`harness.run` は B1・B3 を**学習窓ぜんぶ**で当てはめる（v1 なら 28 日）。**配るのは `fit_baseline` の 7 日の B3** である（W5-16）。**門の数字（「B3 比 10%」）が、本番の B3 に対する数字になっていなかった。** W5 プランの所見 166（気候値の作り方）と同じ形——**同じ名前の相手が 2 通りに作られている**。W6-10、PR F。

### 199. **v1 は検証日の前で学習を止めるので、配った瞬間に「8 日前のデータ」になる**

学習 09-08〜10-05／検証 10-07〜10-08／shadow 10-09〜10-12／active 10/13。**active になる日に、LightGBM の最終学習日は 8 日前**で、`check_model_freshness`（8 日以上で鳴る）はその日に鳴る。**合成器の `train_days` を 2 つの和にして、B3 の週次で見張る**（W6-08）。**LightGBM の部分の古さは報告書とカードで読む**。見張りを LightGBM に合わせて作り直すかは W8（週次の当てはめと一緒に）。
