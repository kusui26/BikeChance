## 3. W2 で確定させた設計判断

W1 の W1-01〜W1-31 に続けて W2-01 から採番する。**実装前に決め、実装で変わったら §3 と開発プランを直してから進む**（CLAUDE.md §2 の原則 10）。

### 3.1 天気の保全について

| ID | 論点 | 決定 | 根拠 |
|---|---|---|---|
| **W2-01** | 天気を W2 に前倒しするか | **予報の生 JSON を毎時アーカイブする作業だけを W2 に置く。解釈（テーブル化・特徴量）は W4 のまま** | 天気は「`t` 時点で入手できた予報」を使う決まりで、**過去に遡って観測できない唯一の入力**（開発プラン §6.7）。ODPT のデータは生 JSON からいくらでも作り直せるが、これだけは違う。保存だけなら 1 日で作れるので、解釈を待つ理由が無い |
| **W2-02** | 何を保存するか | **API の応答をそのまま gzip して Storage に置く。パースも変換もしない** | PR 0 と同じ思想（開発プラン D-03）。W4 で特徴量の定義が変わっても、保存済みのアーカイブから作り直せる。テーブル設計を先に決める必要が無いぶん、着手が速い |
| **W2-03** | 地点の粒度 | **jma_msm の格子 595 セルをすべて取る。クラスタリングしない** | 開発プランは「約 50 クラスタ」としていたが、実測ではポートは **595 格子**に分布する（HELLO 463・ドコモ 218、重なり 86）。Open-Meteo は**複数地点を 1 回の要求でまとめられる**ので、100 地点 × 6 要求で全部取れる（実測 2.0 秒 / 214 KB / 100 地点）。1 日 144 要求で、無料枠 10,000/日 の 1.4%。クラスタリングして空間解像度を落とす理由が無い |
| **W2-04** | 予報の「発行時点」 | **ライブのアーカイブを今日から始める。過去分は Historical Forecast API で埋め、どの近似を使ったかを記録する** | 学習で使うのは「`t` 時点で入手できた予報」で、これは発行時点に依存する。実測（東京駅・2026-08・744 時間）で、**最新の予報と 1 日前の予報は降雨フラグが 15% 食い違う**（MAE 0.272 mm/h）。過去 API の既定（リード 0〜24 時間）は水平 3 時間の学習には**新しすぎて漏洩し得る**。`previous_day1` は古すぎる。**厳密に正しいものはライブでしか取れない** |

### 3.2 再構築について

| ID | 論点 | 決定 | 根拠 |
|---|---|---|---|
| **W2-05** | 再構築の実装言語 | **TypeScript で書き、`packages/gbfs-core` をそのまま再利用する**（開発プラン §5.6 が挙げていた Python 実装は採らない） | 正規化の規則（負値の丸め・重複排除・フラグ・経過秒）は `gbfs-core` に 69 件のテストつきで実装済み。Python で書き直すと**本番と再構築で正規化がずれる**（開発プラン R7 と同じ型のリスク）。再構築は「本番と同じ手続きをやり直す」ことなので、同じ実装を通すべき |
| **W2-06** | TS スクリプトの実行手段 | **`tsx` を devDependency として 1 つ追加する。ユーザーの承認を得てから** | `gbfs-core` は `exports` が `./src/index.ts` で、内部の import に拡張子が無い。Node 22 の `--experimental-strip-types` では解決できないことを実測で確認した。`vite-node` も `esbuild` も入っていない。**W2-05 を成立させるには実行系が要る**。dev 専用で本番には出ない |
| **W2-07** | 再構築が呼ぶ RPC | **`ingest_snapshot` だけを呼ぶ。`begin_fetch` と `finish_fetch` は呼ばない** | 後者 2 つは `feed_state`（claim・ETag・連続失敗・最終観測）を書く。過去のデータを流し込むときにこれを触ると、**現在の収集の状態が壊れる**。`ingest_snapshot` は `status_snapshots` と `stations`、`station_status_latest` にしか触らず、後退したスナップショットでは最新状態を書かない（W1 プラン §5.3 の 34） |
| **W2-08** | 過去月のパーティション | **再構築の前に対象月のパーティションが在ることを確かめる。無ければ作る手段を用意する** | `ensure_snapshot_partitions` は**今月から先しか作らない**（実装で確認）。過去月を再構築すると行は DEFAULT パーティションに落ち、`monitor_feeds` が通知を上げる。W2 で扱う 9 月は現行月なので問題は出ないが、**本当の障害復旧では必ず踏む** |

### 3.3 Parquet について

| ID | 論点 | 決定 | 根拠 |
|---|---|---|---|
| **W2-09** | 圧縮ジョブの入力 | **Postgres の `status_snapshots` から作る**（開発プラン §5.6 の「生 JSON を読む」から変更） | 生 JSON から作ると、正規化を Python で書き直すことになり W2-05 と矛盾する。Postgres の配列は検証・重複排除・`idx` の整列が済んでいる。**「生 JSON → Postgres」は再構築（PR B）の担当、「Postgres → Parquet」は圧縮の担当**と分けると、それぞれ 1 つの関心事に閉じる。Postgres の正しさは `reconcile-snapshot.mjs` が生 JSON と独立に検証している |
| **W2-10** | Parquet のキー | **`station_id` を持たせる。`idx` は書かない** | `idx` は台帳の採番順に依存し、**全面再構築すると変わり得る**。過去に書いた Parquet と将来の台帳で `idx` の意味がずれると、静かに壊れる。`station_id` は提供側の識別子で不変 |
| **W2-11** | Parquet の形式 | **長形式**（1 行 = 1 ポート × 1 観測）。`station_id, observed_at` でソート、zstd、`date=YYYY-MM-DD/hour=HH` で分割 | 学習はポート単位の時系列を読む。配列形式は書き込みに最適化されていて、ポート単位の抽出に全行の展開が要る（開発プラン §6.7）。長形式にすれば列指向の恩恵が効く。見込みサイズは 1 日 1,050 万行 × 0.3〜0.7 B/行 ＝ **5〜10 MB/日** |

### 3.4 配信と体制について

| ID | 論点 | 決定 | 根拠 |
|---|---|---|---|
| **W2-12** | `ml` サービスの追加手順 | **`vercel.json` に `services` と `rewrites` を足す PR と、`/ml/compact` を実装する PR を分ける。前者は `/ml/health` だけを含む** | `vercel.json` の変更は本番デプロイであり、**収集の Cron 設定の更新**でもある。現在の `rewrites` は `/(.*)` を web に流す 1 本だけで、ここに手を入れる。**W2 で収集を止めうる変更はここだけ**なので、他の変更と混ぜない。W1 の PR 0 と同じ考え方（最大の未知を最小の投資で先に潰す） |

## 5. PR の分割と各 PR の定義

### 5.1 分割の方針

W1 と同じ。1 つの PR は **1 つの関心事**に閉じ、レビューが 20〜60 分で終わる量にする。各 PR はそれ自体で CI を通し、テストを含む。**本番に影響する変更を後ろに寄せる。ただし損失が日ごとに積み上がるものは最初に置く**（W1 の PR 0 と同じ例外）。

| 段 | PR | 名前 | 主な成果物 | 本番影響 | 目安 |
|---|---|---|---|---|---|
| **0** | — | 監視の通知先 | Vault に `alert_webhook_url`。強制発火で到達確認 | なし（設定のみ） | 15 分 |
| **1** | **A** | 天気予報の生アーカイブ | `/api/jobs/archive-weather`、毎時 Cron、`weather-raw` バケット | 小（Storage に書くだけ） | 半日 |

### 5.6 PR D：毎時 Parquet 化（M2）

**目的**：Postgres の 60 日保持から独立した、学習用のアーカイブを作り始める。

**変更ファイル**（実装後に確定した構成）

```

apps/ml/bikechance_ml/jobs/snapshot_table.py       # 純粋：配列 → 長形式の表
apps/ml/bikechance_ml/jobs/compact.py              # 手順：前 1 時間を畳む
apps/ml/bikechance_ml/io/supabase.py               # 副作用：PostgREST と Storage
apps/ml/bikechance_ml/json_shape.py                # 純粋：JSON の形の検査（型ガード）
apps/ml/bikechance_ml/redact.py                    # 純粋：記録から秘密を落とす
apps/ml/bikechance_ml/api.py                       # /ml/compact を追加
apps/ml/tests/{test_compact,test_snapshot_table,test_supabase_io,test_json_shape}.py
apps/ml/uv.lock                                    # PR C で見送った分（実依存が増えた）
packages/shared/src/constants.ts                   # PARQUET_BUCKET / COMPACT_CRON / COMPACT_MAX_DURATION_S
vercel.json                                        # crons に 1 本（7 * * * *）と services.ml.functions
```

**`db.py` / `storage.py` に分けなかった理由**：入口はどちらも Supabase の REST で、認証も
エラーの詰め替えも共通である。分けると同じヘッダ組み立てと `redact()` が 2 か所に増える。
副作用を `io/` に閉じるという規約（CLAUDE.md §3）はファイル数ではなくディレクトリで守る。

**`psycopg` を入れない**：Postgres は PostgREST 越しに読む。1 時間ぶんは 60 行に満たず
（HELLO 12 ＋ ドコモ 45）、JSON の上乗せは 5 MB 程度で済む。直接接続を足すと経路が 2 本になり、
依存も 30 MB 増える。**pyarrow を選んだのも実測が理由**で、polars 211 MB に対し pyarrow 139 MB
だった（§10.5）。

**アドバイザリロックを取らない**：PostgREST は 1 要求 1 トランザクションなので、
`pg_try_advisory_xact_lock` を RPC 越しに取っても戻った時点で解放される。代わりに
**構造で冪等にする** — 同じ時間帯は同じパスに写像し、内容ごと上書きする。二重起動は
同じバイト列を 2 回書くだけで終わる。

**`?hour=` で畳み直せる**：`GET /ml/compact?hour=2026-09-08T04:00:00Z`。再構築で過去の
スナップショットを後から入れた場合や、取りこぼした時間帯の埋め戻しに使う。**正時でなければ
400**、まだ終わっていない時間帯も 400（区間が重なった Parquet が同じパスに書かれるのを防ぐ）。

**Parquet のスキーマ**（§9.2 に契約として置く）

| 列 | 型 | 備考 |
|---|---|---|
| `system_id` | string | パーティション列にはしない（1 ファイルに両システムを入れない） |
| `station_id` | string | **`idx` は書かない**（W2-10） |
| `observed_at` | timestamp[ms, UTC] | フィードの `last_updated` |
| `bikes` / `docks` / `flags` / `reported_age_s` | int16 | **`-1` は「観測されなかった」。0 と区別する**（開発プラン §6.7） |

- ソート：`station_id, observed_at`。圧縮：zstd
- パス：`gbfs-parquet/{system}/date=YYYY-MM-DD/hour=HH/part.parquet`（UTC）
- 区間：半開 `[hour, hour+1)`（§4 の 9）
- **配列長より外側の `idx` は行にしない**（当時まだ台帳に無いポート。行を作ると「観測されなかった」と区別できなくなる）

**冪等性**：同じ時間帯を 2 回処理したら同じ内容を上書きする。`job_runs` に行数とバイト数を記録する。

**観測が 0 件の時間帯にはファイルを作らない**：空のファイルを置くと「収集していない」と
「畳んでいない」を見分けられなくなる。`job_runs.detail.n_empty` に数だけ残す。収集の欠落は
`monitor_feeds` が別途通知するので、ここで二重に鳴らさない。

**完了条件と結果（M2、2026-09-08 判定）**

**読み取りビュー**（W2-13。実装した形）

```sql
create view public.v1_stations_current as
select l.system_id, l.station_id, a.name, a.lat, a.lon, a.capacity,
       nullif(l.bikes, -1) as bikes,            -- 未観測は NULL。0（本当に 0 台）と区別する
       nullif(l.docks, -1) as docks,
       case when l.flags < 0 then null else (l.flags & 1) > 0 end as is_installed,
       case when l.flags < 0 then null else (l.flags & 2) > 0 end as is_renting,
       case when l.flags < 0 then null else (l.flags & 4) > 0 end as is_returning,
       l.is_present, l.last_changed_at
  from public.station_status_latest l
  join public.systems sy on sy.system_id = l.system_id and sy.is_active
  -- 属性は left join。新しいポートは最大 1 日属性を持たない（開発プラン §8.3）
  left join public.station_attributes a
    on a.system_id = l.system_id and a.station_id = l.station_id and a.valid_to is null
```

`security_invoker` は既定の `false` のまま。実行はビューの所有者（postgres）の権限で
行われ、所有者は基底テーブルの RLS を迂回する。「匿名は絞り込まれたビューだけを読める」を
実現する唯一の形なので、pgTAP で `security_invoker` が false のままであることも固定した。

**停止したシステム（`systems.is_active = false`）を出さない**のは、収集が止まったあとの
古い値を「現在値」として出さないため。`v1_feeds` も同じ条件で絞る。

匿名には**この 2 つのビューにだけ** SELECT を与える。基底テーブルの権限は与えない。
`authenticated` にも与えない（認証の仕組みがまだ無く、到達し得るのは `anon` だけ）。

**索引**：`station_attributes (lat, lon) where valid_to is null`（0019 で述語を直した）。
索引が無いと bbox の絞り込みが現在有効な属性行（実測 20,742 行）を毎回全件走査する。

**述語に `geo_suspect` を足してはいけない。** 0018 では `where valid_to is null and not
geo_suspect` にしていたが、**一度も使われなかった**。ビューは属性を `left join` するので
`where` が `coalesce(a.geo_suspect, false) = false` になり、**Postgres の含意判定は
`NOT COALESCE(x, false)` から `NOT x` を導けない**ため候補にすら入らない（§12 の 68）。

**`/v1/stations` の仕様**

| 項目 | 内容 |
|---|---|
| パラメータ | `bbox=west,south,east,north`（必須）、`system`（任意） |
| 上限 | 1 辺 0.5 度まで（超えたら 400）。**加えて件数の上限 1,000 件**。実測で 0.5° 四方の東京は 8,792 件・約 3 MB になり、辺の上限だけでは応答の大きさを縛れない（§10.7） |

| 応答 | ポート配列（id・名称・座標・容量・bikes・docks・貸出可・返却可・観測時刻）、`stale`、`attribution` |
| 鮮度 | `last_observed_at` が `greatest(期待周期 × 3, 取得間隔 × 3) + 取得間隔` を超えたら `stale`（監視の 0013 と同じ式）。閾値そのものも `stale_after_s` として返す。**値は返すが、観測時刻を必ず添える**（CLAUDE.md §2 の 7・8） |

| キャッシュ | `public, s-maxage=60, stale-while-revalidate=120` |
| 予測 | **返さない**。`p_bike` / `p_dock` は W4 |
| エラー | RFC 9457 Problem Details（`application/problem+json`）。`type` は相対 URI、機械が分岐する `code` を拡張メンバに置く。**誤りの応答はキャッシュさせない** |
| 上限超過 | 切り捨てずに 400。**該当件数を返す**ので「どれだけ狭めればよいか」が分かる。穴の開いた地図を黙って返さない |

**`/v1/meta`**：`v1_feeds` から `data_updated_at` を入れ、`stale` を実際に計算する。

- **`stale` の意味を変えた**：これまでのスキーマは「予測が古い、または未生成」だったが、W2 時点ではモデルが無いので常に true になり、何も伝えない値だった。**「いずれかのフィードの観測が途切れている」**に改める。予測の有無は `model_version` を見れば分かる。
- **鮮度の閾値は監視（migration 0013）と同じ式**にする：`greatest(expected × 3, poll × 3) + poll`。単純な 3 倍だとドコモが 243 秒になり、実測の最悪値 244 秒（W1-42）で false positive が出る。閾値そのものを `stale_after_s` として応答に載せ、クライアントが同じ判定をできるようにする。
- **DB に届かなくても 200 を返す**。鮮度を伝える経路が鮮度を伝えられずに 500 で落ちると、クライアントは表示条件を判断できない。取れないときは「分からない＝古い」として返す。

### 7.4 Parquet

```sql
-- 1 時間ごとの結果（行数・バイト数・所要）。job_runs から見るのがいちばん早い
select started_at, status,
       detail->>'hour_start' as 時間帯,
       detail->>'n_rows'     as 行数,
       detail->>'bytes'      as バイト,
       detail->>'duration_ms' as 所要ms,
       detail->>'n_empty'    as 空
  from public.job_runs
 where job_name = 'compact_parquet'
 order by started_at desc limit 10;

-- 1 日分の合計サイズ（見込み 5〜10 MB、合格 20 MB 以下）
select sum((metadata->>'size')::bigint) from storage.objects
 where bucket_id = 'gbfs-parquet' and name like '%date=2026-09-10%';
```

冪等性は、**同じ時間帯を明示して 2 回目を走らせ**、行の集合が一致することで見る。

```bash
# 同じ時間帯をもう一度畳む（?hour= は正時・タイムゾーン必須）

  "https://<本番>/ml/compact?hour=2026-09-10T04:00:00Z" | jq '{n_rows, bytes, systems}'
```

Parquet はメタデータに書き込み時刻が入るのでバイト単位では一致しないことがある。**行の集合で判定する。**

**合格ライン**：1 時間分が約 44 万行、1 日 20 MB 以下、2 回目の実行で行の集合が同一。

## 9. 付録：PR をまたぐ契約

### 9.1 天気アーカイブのパス規約

```
weather-raw/{YYYY}/{MM}/{DD}/jma_msm_{hour_epoch_s}_{batch:02d}.json.gz
例: weather-raw/2026/09/08/jma_msm_1788800400_00.json.gz
```

- 日付は **UTC**（`gbfs-raw` と同じ。W1 プラン §11.5）
- `hour_epoch_s` は**取得を開始した時刻を「時」に丸めた値**（§12 の 48）。応答に発行時刻が無いため、これが「いつ入手したか」の記録になる。丸めるのは**同じ時間の再実行を同じパスに写像する**ためで、取り直しが 409 として畳まれ、1 時間 1 個という数え方も崩れない
- `batch` は分割の連番（00〜05）。応答に `latitude` / `longitude` が含まれるので、どの格子かは中身で分かる
- ファイル名の `jma_msm` は**保存先の規約としての名前**で、中身のモデルが増えても変えない
- 中身は **Open-Meteo の応答そのまま**。整形も並べ替えもしない。**2 モデル分**（`jma_msm` と `best_match`）が接尾辞つきの系列で入る（§12 の 47）

**格子の丸め**：`lat` は 0.05°、`lon` は 0.0625° 刻み（jma_msm の格子。実測で確認）。

```
gy = round(lat / 0.05),  gx = round(lon / 0.0625)
セルの代表点 = (gy * 0.05, gx * 0.0625)
```

要求した座標と応答の座標は一致しないことがある（§4 の 6）。**対応づけには応答側の座標を使う。**

### 9.2 Parquet のスキーマ

```
gbfs-parquet/{system}/date=YYYY-MM-DD/hour=HH/part.parquet     ← 日時は UTC
```

| 列 | 型 | 意味 |
|---|---|---|
| `system_id` | string | `hellocycling` / `docomo-cycle` |
| `station_id` | string | 提供側の識別子。**`idx` は書かない**（W2-10） |
| `observed_at` | timestamp[ms, UTC] | フィードの `last_updated` |
| `bikes` | int16 | 貸出可能台数。**`-1` は「このスナップショットに現れなかった」** |
| `docks` | int16 | 返却可能枠。同上。**HELLO の定員超過は 0 に丸めてある**（W1-25） |
| `flags` | int16 | 1=設置 2=貸出可 4=返却可 のビット和。同上 |
| `reported_age_s` | int16 | 観測時刻とポートの報告時刻の差。**ドコモは恒常的に 0** |

- ソート：`station_id, observed_at`。圧縮：zstd
- **配列長より外側の `idx`（当時まだ台帳に無いポート）は行にしない。** 行を作ると `-1`（登録済みだが未出現）と区別できなくなる
- **観測が 1 件も無い時間帯にはファイルを置かない。** 空のファイルは「収集していない」と「畳んでいない」を混同させる。読む側は「そのパスが無い＝その時間の観測が無い」と解釈してよい
- 同じ時間帯は同じパスに写像し、内容ごと上書きする。**後から再構築で行が増えたら `?hour=` で畳み直す**（§5.6）

### 9.4 予測の水平と天気データの対応

「水平ごとに未来の天気を貯める必要があるのでは」という問いへの答えを残す。**必要ない。1 回の取得が全ての水平を覆う。**

**モデルが要るもの**：基準時刻 `t`、水平 `h ∈ {5, 10, …, 180}` 分に対し、`t` 時点で入手できた「`t+h` の予報」。

**1 回の取得が返すもの**：`forecast_days=2` の応答は、**その時刻に発行されている予報の系列そのもの**で、今日 00:00 JST から明日 23:00 JST までの 1 時間値が入る。つまり `t+5 分` から `t+180 分` までは全部この 1 本の中にある（3 時間先までなら高々 4 つの連続する時刻）。

したがって取り出し方はこうなる。

```
（t, h）に対する天気 = 「t 以前で最新のアーカイブ」を開き、「t+h を含む時刻」の値を読む
```

**水平ごとに別々のファイルを貯める必要は無い。** 貯めるのは「発行時点ごとの未来の系列」で、水平はその系列への添字にすぎない。

| 誤解しやすい形 | 実際 |
|---|---|
| 水平 10 点それぞれについて未来の予報を保存する | 1 つの系列に 10 点すべてが含まれる |
| 予測のたびに天気を取りに行く | 毎時 1 回のアーカイブを読むだけ |
| 予報を「その時刻の実況」として保存する | 保存するのは**発行時点の未来の見通し**。実況ではない |

**毎時の取得で足りる理由**：`jma_msm` は **3 時間ごとに更新**され、配信までに約 2 時間半かかる。毎時取れば、新しい発行を最大 1 時間の遅れで捕まえる。**モデルの更新周期より細かく取っても新しい情報は増えない。** 現状は 3 倍の余裕で取っている。

**基準時刻からの遅れ**：`t` で使えるのは「`t` 以前で最新の取得」なので、遅れは 0〜60 分。過去 API の近似（既定はリード 0〜24 時間、`previous_day1` は 24〜48 時間）に比べて桁違いに小さい。**ライブのアーカイブを始めた意味はここに出る。**

**15 分値を取らない理由（実測にもとづく）**：`minutely_15` は `jma_msm` でも返るが、**1 時間値から機械的に作られていて新しい情報が無い**。2026-09-07 の実測で、15 分の降水量は「次の 1 時間値 ÷ 4」を 15 分ずらして並べたものだった。

| 時刻 | 1 時間値 | 15 分値 × 4 |
|---|---|---|
| 00:00 | 10.40 | 2.6, 3.0, 3.0, 3.0 |
| 01:00 | 11.80 | 3.0, 4.3, 4.3, 4.3 |
| 02:00 | 17.00 | 4.3, 5.0, 5.0, 5.0 |
| 03:00 | 19.80 | 5.0, 1.3, 1.3, 1.3 |

`10.40 ÷ 4 = 2.6`、`11.80 ÷ 4 ≈ 3.0`、`17.00 ÷ 4 ≈ 4.3`。各時刻の先頭 1 つはその時刻の 1 時間値を、残り 3 つは**次の時刻**の 1 時間値を 4 で割った値である。気温も線形補間だった。**情報が増えないのに容量が 3 倍になり、しかも 15 分ずれる**ので取らない。天気の実効的な分解能は 1 時間であり、それはデータ源の性質であってこちらの取り方の問題ではない。

**W4 で間違えやすい点**

| 点 | 内容 |
|---|---|
| as-of の選び方 | `t` **以前**で最新のアーカイブを使う。`t` より後に取得したものを使うと漏洩する（水平が長いほど効く） |
| 降水量の意味 | Open-Meteo の 1 時間降水量は**直前 1 時間の合計**。`t+h` の値は「`t+h` を含む時刻」の行から読む。境界の扱いを実装前に 1 度検算する |
| モデルの選択 | 決定論的な値は `jma_msm`、降水確率は `best_match`（§12 の 47）。同じファイルに両方入っている |
| 経過した時刻 | 応答には今日の既に過ぎた時刻も含まれる。これは予報ではなく解析に近い値なので、**特徴量に混ぜない**（`precip_mm_now` に使うのは「`t` を含む時刻」までにとどめる） |

**取得窓を変えるか**：`past_hours` / `forecast_hours` を使えば「今から前後何時間」という一定の窓にできる（実測で動作を確認）。現行の `forecast_days=2` は日付境界に揃うため、先の覆いが時刻によって 23.7〜46.7 時間と変わる。**水平が 3 時間である限りどちらでも足り、変える理由が無い**ので現行のままとする。将来 12 時間以上先の天気を使う設計にするなら、そのときに `forecast_hours` へ移す。

### 10.7 PR E の実測（2026-09-08、本番の DB に対して）

**ポートの密度**（現在有効な属性行 20,742、`geo_suspect` 1 件、座標なし 0 件）

| 1 辺 | 最も混んでいるセル | 応答の見込み（348 B/件） |
|---|---|---|
| 0.01°（丸めの刻み） | **31 件** | 11 KB |
| 0.02°（丸めで最大になる 2×2） | **96 件** | 33 KB |
| 0.05° | 327 件 | 114 KB |
| 0.10° | 866 件 | 301 KB |
| 0.20° | 2,936 件 | 1.0 MB |
| 0.50°（1 辺の上限） | 8,612 件（東京駅中心の実測で 8,792 件） | **3.0 MB** |

1 ポートあたりの JSON は**平均 348 バイト・最大 432 バイト**（全 20,741 件で実測）。

ここから 2 つ決めた。

1. **辺の上限だけでは応答の大きさを縛れない。** 0.5° 四方の東京は 3 MB になる。
   件数の上限（1,000 件 ≒ 340 KB）を別に置き、超えたら 400 で該当件数を返す。
2. **丸めの刻み（0.01°）が実効的な最小の矩形になる。** 点のような要求でも 2×2 セルまで
   広がるので、最悪 96 件。上限 1,000 件に対して **10 倍の余裕**があり、「狭めても通らない」
   状態は起きない。

**問い合わせの所要**（本番）

```
Limit (actual time=0.082..10.533 rows=376)
  -> Seq Scan on station_attributes  (actual time=0.018..6.924 rows=376)
       Rows Removed by Filter: 20373
Execution Time: 10.633 ms
```

全件走査が 6.9 ms を占めるので部分索引を足した。ただし**最初に書いた述語では索引が使われず**、
`valid_to is null` だけに直して初めて効いた（§12 の 68）。

| 索引の述語 | 実行計画 | 所要 |

| 無し | Seq Scan | 10.6 ms |
| `valid_to is null and not geo_suspect`（0018） | Seq Scan（**使われない**） | 9.2 ms |
| `valid_to is null`（0019） | Index Only Scan | **0.27 ms** |

**いまの規模なら索引なしでも間に合うが、ポートが 10 倍になると 70 ms になる。**
