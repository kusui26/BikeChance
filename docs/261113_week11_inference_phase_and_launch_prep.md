## 1. W11 のゴールと完了条件

3. **運用の直し**：収集の見張りの閾値（所見 241）、**Supabase の一時的な不調への備え**（所見 245）。ドリフトの見張り（W10-08）は W12

## 11. 所見（W11。W10 プランの 244 の続きから番号を振る）

### 245（11/14）：Supabase の読み込みが一時的に応えないことが続いている（3 晩続けて 03 時台の前半、ほかに Supabase の障害の時間帯に 1 回）

**見つけ方**：11/14 の朝の点検で、ドコモの推論が 1 周期失敗していた（11/13 15:01:11、`SupabaseError`）。W10 の期間（11/9〜11/13 12:00）は失敗 0 だった。

- **起きたこと**（30 日。`job_runs` と `inference_log`）：10/15 05:00（参照）・10/23 06:31（ドコモのプロファイル）・10/29 19:04（HELLO の推論の失敗）の 3 回のあと、**11/12 03:28（天気の取り込み）・11/13 03:05（HELLO のプロファイル）・11/13 15:01（ドコモの推論の失敗）・11/14 03:21（ドコモのプロファイル）の 4 回が 2.5 日に集まった**。うち 3 回は 3 晩続けて 03:05〜03:28 JST
- **11/13 15:01 の失敗**：Supabase の状態の頁の「Database Connection Errors」（11/13、ap-northeast-1 を含む 18 地域、05:35〜08:40。頁に時間帯の表記が無く、UTC と読めば 14:35〜17:40 JST）の中に入る。本番の実行ログでは、Storage への GET が 6 回（206）、データベースの API への GET が 34 回（200）続いたあとで止まり、**200 以外の応答は 1 つも出ていない**——応答を受け取る前の切断か時間切れ（`httpx` の例外）の形
- **夜中の 3 回**（Storage の読み込み）：HELLO の 03:05 は 44.9 秒かかり（読み込みの時間切れ 30 秒と合う）、ドコモの 03:21 は 280 ms で切れた（945,321 バイトを読んだところ）、天気の 03:28 は 30.7 秒（時間切れ）。**同じ時間帯の収集と推論の所要は、ほかの夜と変わらない**（直近 8 晩の 02:30〜04:00 を 5 分ごとに見た。DB の側の重さではない）。DB の定時の仕事は 03:00 の保守（1 秒）と 03:30 の活動の更新だけ。原因は分からない（Supabase 側の夜の作業の見込みだが、確かめていない）
- **記録が足りない**：`SupabaseError` は段・HTTP の状態・例外の名前を持っている（`SupabaseFailure`。URL は伏せてある）が、推論の失敗の記録（`inference_log.error`）とプロファイルの読み込みの理由（`detail.profile_reason`）には**例外の名前しか残していない**。CLAUDE.md §3 の「文脈付きエラー」に届いておらず、今回も切断か時間切れかを記録から言えない

**影響**：作りどおり吸収した——プロファイルを読めない周期は全セル B3 で配り（契約 33）、推論が落ちた周期は前の周期の予測を鮮度の切り（15 分）の内で配り、天気は次の回が取り戻した。**配る確率が森から B3 に落ちたのは 2 周期（10 分）、予測が 5 分古くなったのが 1 周期**。警報は鳴らない（どれも 1 回きり）。

**直す案**（W11-11、PR S）：①失敗の記録に `SupabaseFailure` の段・状態・例外の名前を残す（URL は入らない）、②**読むだけの要求**（Storage の範囲の読み込み・データベースの API の GET）を、接続の切断・時間切れ・5xx のときに 1 度だけ取り直す（短い待ちを入れ、時間切れを短くして周期の時間の内に収める）。書く要求は取り直さない。
