## 4. W4 で確定させる設計判断

| # | 論点 | 決定 | 理由 |
|---|---|---|---|
| **W4-01** | 予測をいつ「古い」とするか | **`base_observed_at` が `FORECAST_STALE_AFTER_S`（900 秒＝15 分）より古ければ、予測を返さない**（`p_bike` / `p_dock` / `confidence` を null にする。行は返す） | **定数はもう在る。使っていないだけだった**（`packages/shared/src/constants.ts:25`。どこからも参照されていない）。判定を `generated_at` ではなく `base_observed_at` にするのは、**利用者に効くのは「どの観測に基づくか」**だから。現在値の `stale` 判定と同じ物差しになり、「台数は現在値なのに予測は古い」という食い違いが起きない。**`infer_alert_s`（900 秒）と同じ値**なので、**利用者に出せなくなった瞬間に監視も鳴る**。フィードごとの `stale_after_s`（HELLO 960 秒・ドコモ 303 秒）は使わない：ドコモの 303 秒は推論周期（300 秒）とほぼ同じで、正常運転でも切れたり戻ったりする |
| **W4-02** | 予測が無いポートをどう返すか | **行は返し、予測のフィールドだけ null にする。`forecast_absent` の理由を添えない** | 予測が無い理由は 3 つある（貸出・返却が止まっている／観測が古い／成果物に無い）。**理由を API の契約にすると、内部の都合が外に漏れる。** 利用者にとっては「いまは出せない」で十分で、原因は `inference_log` と監視が持つ。§9 の契約で `p_bike` を optional にし、iOS の `Codable` も optional で生成する（属性の無いポートと同じ扱い。開発プラン §8.3） |

## 5. 実装で踏みそうな落とし穴

**W3 で踏んだものと同じ形のものが 4 つ見えている。** 先に書いておく。

### 5.1 除外規則が 2 か所にある（**train/serve skew の芽**）

`jobs/infer.py` の `is_predictable`（1 行ずつ）と `features/exclude.py`（配列で一度に）は、**同じ規則の別実装**である。`is_predictable` の docstring は「**学習と同じ除外規則**（`features/exclude.py`）」と書いているが、コードは共有していない。

いまは両方とも「`flags` の貸出可・返却可が立ち、値が `-1` でなく、幻のポートでない」を見ていて一致している。**片方だけ直せば静かにずれる。**

**PR C で 1 つにする。** `build_now` が `exclude.py` を通るなら、`is_predictable` はその薄い包みになる。

### 5.2 `build_day` の 1 点と `build_now` は、**同じ入力でも同じにならない**ことがある

`build_day` は 25 時間の Parquet を読み、`build_now` は 3 時間の配列を読む。**同じ時刻の同じ観測から作っても、次の 3 つで違いが出うる。**

| ずれの元 | なぜ |
|---|---|
| `fetched_at` の有無 | Parquet は `fetched_at` を持つ（as-of はこれで切る）。`status_snapshots` にも在るので取れるが、**取り忘れると `observed_at` で切ることになり、W2 で潰したはずの skew が戻る**（開発プラン §6.2） |
| 配列の長さ | 台帳が増えると配列が伸びる。**時系列で単調とは限らない**（再構築を挟むと逆転する。開発プラン §6.7）。位置の割り当ては参照スナップショットの順に従う |
| 丸め | `capacity` は参照スナップショットから読むので同じ。`fill_ratio` は float32 で、**計算順が違うと最下位ビットが変わりうる** |

**ゴールデンで一致を見るときは、float の比較を許容誤差にしない。** ずれたら「なぜずれたか」を追う。許容誤差を入れた瞬間に、この検査は何も守らなくなる。

### 5.3 予測を返すと `/v1` の応答が重くなる

いまの `/v1/stations` は 1,000 件の上限で約 3 MB。予測を足すと **1 ポートあたり `p_bike` 10 個 ＋ `p_dock` 10 個 ＋ `confidence`** が増える。smallint 相当でも JSON では 1 ポート約 120 バイト増える見込みで、1,000 件で **+120 KB**。

**辺の上限（0.5 度）と件数の上限（1,000 件）は変えない。** 増えるのは応答の大きさだけで、上限の設計は W2 の PR E で決めた根拠（実測で 8,792 ポート・3 MB）がそのまま生きる。

**ただし「10 水平を全部返すか」は別の話。** 地図では 1 つの到着時刻しか使わない。§9 の契約で決める。

### 5.4 天気は「アーカイブ開始前」がある

天気アーカイブは **2026-09-08 00:17 JST**（＝ 2026-09-07 15:17 UTC）から。収集開始（9/06 15:51 JST）より **32.4 時間遅い**。

**天気列を足した版（`FEATURE_SET` を上げる）の学習期間は、実質 9/08 以降になる。** 9/06〜9/07 のサンプルは天気無し版のまま残す（**消さない**。混ぜて学習しないことだけ守る）。

W4 の v0 は配線確認なので、**9/08 以降だけで足りる**。

#### 6.2a 実装（2026-09-09）

**決めたこと**

| | 決定 | 理由 |
|---|---|---|
| 送る形 | **5 分格子に丸めた絶対時刻 `at`**（`2026-09-09T05:35:00Z`） | §12 の 114。相対だと CDN から返った応答が別の到着を指す。格子に丸めるのは、同じ時間帯の利用者が同じ URL を叩いて CDN が効くようにするため。**丸めで範囲（5〜180 分）を外れたら 1 段ずらす**（格子から降ろさない） |
| 時刻の書き方 | **`Z`（UTC）で書く** | `+09:00` だと `URLComponents` が `+` を素通しし、受け手によっては空白に化ける。サーバーはタイムゾーン必須なので省略もできない |
| 表示 | **「14:35 到着」**（「約 30 分後」と書かない） | 同上。**指している時刻は応答が持っている**（`generated_at ＋ forecast_in_min`）ので、端末の時計から数え直さない |
| 借りる／返す | **切替を置く。要求は変えない** | 応答に両方の確率が入っているので、切替では取りに行かない。**到着を選んだときだけ出す**（「いま」の地図は現在値の色で、意図によって色が変わらない。効かない操作を置かない） |
| ピンの色 | **到着を選べば帯の色、選ばなければ現在値の色。同時には出さない** | 「現在値の色と混ぜない」（§6.2）。1 枚の地図に 2 つの意味の色が並ぶと、どちらの話か分からない |
| フィードが滞っているとき | **予測を隠す**（開発プラン §9.2） | 台数が信用できないときの確率は、数字の形をしているぶんだけ余計に信用される |
| 詳細画面の並び | **確率が先、台数が後**（CLAUDE.md §2 の 7） | 出せないときも欄は残し、「下の台数は予測ではなく、いまの観測値です」と添える |

**表示の丸めで分かったこと**：開発プラン §9.3 の「5% 刻み」と「100% と言わない」は**上の端でぶつかる**。100 を 99 に落とすので、**99 だけが 5 の倍数でなくなる**。95 に落とす案は、0.96 と 0.999 が同じ表示になって上のほうの違いが全部つぶれるので採らなかった。検査（`ForecastTests`）にこの例外を書いてある。

**検査**（`swift test` で 140 件、シミュレータ不要）
- **本番の実応答 4 本**を契約テストの入力にした：`stations`（到着なし＝予測なし）、`stations_arrival`（30 分後）、`stations_arrival_late`（175 分後）、`stations_partial_forecast`（**予測の無いポートを 2 件含む**実データ）
- **到着時刻を変えると確率が変わる**：`stations_arrival` と `stations_arrival_late` を突き合わせ、**47 ポート全部で値が違う**ことを固定した。同じなら補間か起点が壊れている
- **予測の無いポート**（貸出も返却も止まっている。§12 の 109）で「いまは予測できません」が出て、**台数は出る**
- 格子と範囲：どの選択肢でも、時刻の位相を 1 秒ずつ 5 分ぶんずらして**必ず 5〜180 分に収まる**ことを確かめた
- 100% と言わない・5% 刻み・帯の境目（85/60）・「借りられます」と書かない

**シミュレータで確認したこと**（本番の値。2026-09-09 15:00 JST）
- 「いまの空き」では現在値の色（緑・青・橙）で 154 件、チップは「いまの空き」、借りる／返すの切替は**出ない**
- 「15:30 到着」に切り替えると**帯の色に変わり**、借りる／返すの切替が出る
- **借りる**では都心はほぼ緑（自転車は余っている）、**返す**では同じ範囲に赤が多数出る（空き枠が乏しい）。**同じ地図・同じ時刻で、意図によって絵が変わる**

**残り**：10 水平の曲線と履歴は W5（`/v1/stations/{system}/{id}` と同じ PR）。

### 6.2b PR B′：ドコモの「容量」を出すのをやめる（§12 の 115）

**小さく、独立している。** PR C を止めないので、いつ入れてもよい。**W5 の詳細エンドポイントより前**に入れる（あちらは同じ欄を触る）。

#### 何を選んだか

出せる案は 3 つあった。

```sql
-- 0035（案）
       case when sy.capacity_is_dynamic then null else a.capacity end as capacity,
```

- **列は増えも減りもしない。** `capacity_is_dynamic` は今までどおり返すので、クライアントは「この事業者は固定のラック数を公開していない」と書ける
- **デプロイの順序はどちらでもよい**（§12 の 112）。列を増やさないので、古いコードは NULL を「未取得」として描くだけで壊れない

#### 6.3a 実装（2026-09-10）

**格子の作り方だけを分けた。** `features/build.py` は格子の中身を知らない。

| 分けたもの | 学習 | 推論 |
|---|---|---|
| 格子 | 当日 288 点 ＋ 前後の余白（`build_grid`） | **1 点と、そこから要る 24 点だけ**（`build_point_grid`） |
| 引き方 | どちらも `Grid.shifted(minutes)` | 同じ |
| 目標時刻の除外・抽出・ラベル | 行う | **行わない**（未来が無い） |

**添字の算術を 1 か所に閉じ込めた**のが要点である。以前は `slice(day.start - steps, day.stop - steps)` が 4 か所に散らばっていて、1 点の格子では意味を成さなかった。`shifted()` にまとめたので、**疎な格子でも同じ関数が通る**。持っていないずらし量を頼まれたら `MissingShiftError` で止まる（黙って別の時刻を指すより、止まるほうがよい）。

**暦を「格子の添字 × 5 分」から時刻に直した。** 学習の格子は JST 00:00 起点なので添字がそのまま日内分になっていたが、推論の格子は 1 点で添字が常に 0 になる。**時刻から出せばどちらでも正しい。**

### 6.4 PR D：`weather_hourly` と天気の特徴量（実装済み）

**やったこと**：生アーカイブ（`weather-raw` の gzip JSON、0015）を読んで `weather_hourly` に落とし、特徴量に **4 列**を足した。`FEATURE_SET` を **v3** に上げた。

#### 決めたこと

| # | 論点 | 決定 | 理由 |
|---|---|---|---|
| **W4-12** | `weather_hourly` の形 | **1 行が「1 発行 × 1 格子」で、時間帯は配列**（`station_forecasts` と同じ形）。鍵は**格子の整数添字** `(round(lat/0.05), round(lon/0.0625))` | 開発プラン §5.3 の DDL は `cluster_id` で 1 行 1 時刻だったが、**`cluster_id` は実装に無い**（「約 50 クラスタ」の見積りは 1 桁外れ、実装は 595 格子）。長形式にすると **13 MB/日**で、**元の生アーカイブ（6.4 MB/日・72 時間ぶん）の 2 倍**になる。配列なら **5.2 MB/日**（どちらも本番の 1 発行をローカル DB に入れて実測）。派生物が一次ソースより大きいのはおかしい。座標を度のまま鍵にしないのは、応答が float32 で `26.2` を `26.199999` として返すため |
| **W4-13** | 天気の列をどれにするか | **`precip_mm_now` / `precip_mm_target` / `temp_c` / `wind_kmh` の 4 つ。** `weather_code` は**表には入れるが特徴量にしない** | EDA（59 発行 × 595 格子 × 6 時間 = 210,630 値）：降水量は σ 2.252 で**時間方向 1.519・空間方向 1.628** と両方に動く、気温 σ 3.215、風速 σ 7.076。どれも NULL 0 件。`weather_code` は **降水量と一対一に近い**（`precip = 0` ⇔ コード 0/1/2/3、`precip > 0` ⇔ 51/53/55/61/63/65）ので、独自の情報は「雨が降っていないときの雲量」だけ。**それを使う根拠がまだ無い**ので特徴量にしない。表には残すので、根拠ができたら取り込み直さずに足せる |
| **W4-14** | 取り込みをどこで回すか | **`/ml/weather`（Vercel Cron、毎時 :25 UTC）。** 取得（`/api/jobs/archive-weather`、:17）とは**別のジョブ**にする | 取得の中で解釈すると、**解釈の失敗が収集を止めうる**（CLAUDE.md §2 の 1「収集器は他の全てから隔離する」）。別にすれば、取り込みが何度落ちても生アーカイブは無傷で、あとから何度でも作り直せる。**`monitored_jobs` にも入れた**（毎時・3 時間で鳴る。§12 の 116 で決めた規則） |

#### `available_at <= t` をどう固定したか

**完了条件は「`available_at` より後の予報を 1 件も使っていない（検査で固定）」だった。** 3 段構えにした。

1. **規律は 1 か所**。どの発行を使うかを決めるのは `features/weather.py` の `Weather.issue_at` だけである（`available_at` の昇順に二分探索して `side="right" - 1`）。SQL 側の窓（`list_weather` の `[start, end)`）は**読み込み量の都合**であって規律ではない。上限は基準時刻そのものなので、窓を広げても未来は入らない
2. **見張り**。`Weather._refuse_leak` が、選んだ発行の `available_at` が基準時刻を超えていないかを毎回確かめ、超えていれば `WeatherLeakError` で止める。`Grid.shifted` の `MissingShiftError` と同じ役回りで、**静かに別の時刻の値が入るより止まるほうがよい**
3. **落ちる検査**。3 つある。
   - `test_a_later_issue_does_not_change_the_past` — **あとから入手する発行を足しても、それより前の基準時刻の値が 1 つも動かない。** これがリークの定義そのもの
   - `test_no_row_uses_a_forecast_from_the_future`（ゴールデン）— 出力の値だけから発行を復元し、`t` までに入手できていたことを確かめる
   - `test_the_weather_comes_from_the_issue_that_was_available`（ゴールデン）— 「`available_at <= t` の最新の、`t` を含む時間帯」を**素朴に選び直して**突き合わせる（`build.py` の添字の算術とは別経路）

**検査が空回りしていないことを確かめた。** `issue_at` を「`issued_hour <= t` の最新」（＝ W3-06 が禁じている引き方）に差し替えると、**4 つの検査が落ちる**（うち 1 つは推論との一致 `test_the_serving_window_is_enough`）。`available_at` を無視した実装は通らない。

#### 引く時間帯は変数で違う

**Open-Meteo の `precipitation` は「直前 1 時間の合計」で、`temperature_2m` と `wind_speed_10m` は瞬時値である**（§12 の 121）。同じ添字で引くと気温だけが最大 1 時間先の値になる。

| 列 | 引く毎正時 | 理由 |
|---|---|---|
| `precip_mm_now` | **`t` 以上で最小**の毎正時 | ラベル `H` の値が覆うのは `(H − 1 時間, H]`。`t` が入るのはこの時間帯 |
| `precip_mm_target` | **`t + h` 以上で最小**の毎正時 | 同上。**水平で変わるのはこの列だけ** |
| `temp_c` / `wind_kmh` | **`t` に最も近い**毎正時 | 瞬時値。含む時間帯を使うと最大 1 時間ぶん先の値になる |

**やったこと**：`lightgbm` を本番依存から外し（W4-19）、**木の構造そのものを成果物に持って numpy で歩く**ようにした。PR E が本番で `OSError` になった（§12 の 126）ことへの対処である。

#### 何が効いていたか（大きさではなくランタイムの中身）

W4-15 は「**334 MB < 500 MB だから入る**」で決めた。**数字は正しく、測っていたものが違った。**

|---|---|
| バンドルの大きさ（334 MB） | **ランタイムに `libgomp.so.1` があるか**（無い） |

**ここから「LightGBM は使えない」と読んだのが誤りだった。** 足りないのは 352 KB のファイル 1 個で、**同梱すれば動く**（§12 の 128 で検証済み）。

### 6.6 PR F：重点サンプリングの閾値（**9/16 以降**）

**測ってから決める。** 3 つを並べる。

1. `bikes ≤ k`（k = 0, 1, 2）と `docks ≤ k` のそれぞれで、**母集団に占める割合**
2. バケツ別の Brier が、**どのバケツで効いているか**（0 台・1 台・2 台…）
3. 閾値を変えたときの**行数と容量**

**選択肢**

| 案 | 中身 | 効き方 |
|---|---|---|
| (i) 閾値を下げる | `bikes ≤ 1 または docks ≤ 1` | 母集団の割合が下がり、層化が効き始める |
| (ii) 定義を変える | `fill_ratio` の両端、または `y` が割れる領域 | 「難しい」を素直に表す |
| (iii) 層化をやめる | 一様抽出にする | **重みが要らなくなり、話が単純になる** |

**(iii) を軽く見ない。** 層化の目的は「稀で重要な場面を濃く取る」ことである。84% が「重要」なら、**層化そのものに意味が無い**。一様抽出にすれば `weight` と `stratum` が消え、評価の重み付けも要らなくなる。

### 6.7 PR G：`/v1/trip-check`

**行程チェックは CLAUDE.md §1 が挙げる 3 つの差別化の 1 つ**（「差別化は予測・確率・**行程チェック**」）。地図の 1 ポートではなく、**出発と到着を組にして「その行程が成立するか」**を答える。

**この PR は API だけ。** iOS の Trip Check 画面は W5（§10）。

#### 契約（決めたこと。W4-21〜26）

**要求**

```
GET /v1/trip-check?system=hellocycling&from=10139&to=10145&depart_in_min=15[&ride_min=8]
GET /v1/trip-check?system=hellocycling&from=10139&to=10145&depart_at=2026-09-11T14:30:00Z
```

| 引数 | 必須 | 意味 |
|---|---|---|
| `system` | ✅ | `hellocycling` / `docomo-cycle` |
| `from` / `to` | ✅ | ポート ID（`system` の中で解決する） |
| `depart_at` または `depart_in_min` | ✅ | **出発ポートに着く時刻**。`/v1/stations` の `at` / `in_min` と同じ規則（5 分に丸める・同時指定は 400） |
| `ride_min` | | 乗車時間（分）。**省略時はサーバーが概算**する |

**応答**

```jsonc
{
  "api_version": "v1", "generated_at": "...", "stale": false,
  "system_id": "hellocycling",
  "depart_in_min": 15,        // 5 分に丸めた後
  "ride_min": 8,              // 実際に使った値
  "ride_min_estimated": true, // サーバーが概算したか
  "arrive_in_min": 23,        // depart + ride
  "from": { /* StationCurrent。forecast は depart_in_min 時点 */ },
  "to":   { /* StationCurrent。forecast は arrive_in_min 時点 */ },
  "trip": { "p_trip": 0.82, "confidence": 2, "notice": "…独立とみなして…" },
  "alternatives": { "from": [{ "distance_m": 120, "station": {…} }], "to": [ … ] },
  "feeds": [ … ], "attribution": [ … ]
}
```

#### なぜこの形か

**W4-21：ポートの指定は `system` を先頭に置く。** `station_id` は**システムをまたいで衝突する**（実測：両系 1,000 件ずつのサンプルで **313 件が重複**）。だから ID だけでは引けない。かつ **HELLO の自転車をドコモのポートには返せない**——事業者が違えば行程は成立しない（`station_neighbors.same_system` が同じ理由で在る）。`system` を 1 つだけ受け取れば、**跨いだ行程は表現できなくなる**。検査して断るのではなく、**書けなくする**。

> 誤って別系統の ID を渡したときは、**その ID が別のシステムに在ることを本文で伝える**（`system` 抜きで引いて確かめる）。書けなくすることと、診断を諦めることは別である。

**W4-22：到着は 2 つあり、両方が水平の範囲に入らなければ断る。** `depart_in_min` と `arrive_in_min = depart_in_min + ride_min` の**どちらも 5〜180 分**に収める。`interpolateForecast` は範囲外で末尾に張り付くので、**黙って「180 分の確率」を 210 分の答えとして返してしまう**。`parseArrival` が出発を見張り、到着はこちらで見張る。

**W4-23：`ride_min` は省略時に概算し、整数分に丸める。** 直線距離 ÷ 14 km/h（開発プラン §8.3）。距離は **`rebuild_geo` と同じ haversine・同じ地球半径 6,371,000 m** を使う——2 つの実装が別の距離を出す状態を作らない。**座標が無いポート**（属性の日次同期がまだ届いていない）で `ride_min` が省略されたら **400 で断る**：推測せず、呼ぶ側に渡させる。

**W4-24：`trip` は片側でも欠けたら null**（契約 10）。**`trip` が非 null であることと、`from.forecast` と `to.forecast` が両方非 null であることは同値**にする。`confidence` は**2 つの小さいほう**（鎖は弱い環の強さしかない）。**独立仮定の注記は `p_trip` と同じ欄に入れる**——別の場所に置くと、数だけ取り出して注記を落とせてしまう。

> **`p_bike` と `p_dock` を `trip` の中に複製しない。** 同じ数を 2 か所に置くと、どちらが正かが決まらない（契約 4 と同じ理由）。`trip` が非 null なら両方在ることが保証されるので、呼ぶ側は `from.forecast.p_bike` を読めばよい。

**W4-25：代替候補は同一システム・400 m 以内・確率の高い順に 5 件。** 実測（本番 1,844 ポート）で **400 m 以内の同一システムの近傍は中央 3・p90 9・最大 25**。全部返すと密集地で応答が 3 倍になるので**上限を置く**。

| 決めたこと | なぜ |
|---|---|
| **同一システムのみ** | 別事業者の自転車は借りられない。`same_system` が在るのはこのため |
| **確率の高い順**（同値なら距離→ID） | 「ここで借りられないなら、どこなら借りられるか」が問い。距離順だと **6 番目の 90% が 5 番目の 40% に隠れる**。400 m の歩き差は 14 km/h で **1.7 分**しかない |
| **上限 5 件** | 中央 3 を全部含み、密集地でも応答を抑える |
| **予測の無いポートは入れない** | 確率を答えられない候補は問いに答えていない |
| **端点と同じ時刻で評価**（出発側は `depart_in_min`、到着側は `arrive_in_min`） | 400 m の寄り道は 1.7 分で、**5 分格子より細かい** |
| **「端点より良い」で絞らない** | 出すかどうかは画面の判断。API は材料を渡す |

**W4-26：`station_neighbors` を `v1_` ビューで公開する（migration 0039）。** 公開経路が触れてよいのは `v1_` で始まるビューだけ（CLAUDE.md §5、`read-port.ts` の冒頭）。**この規律のためだけに 1 枚足す。**

## 12. 実装中に見つかった問題

番号は W3 の 111 に続けて **112 番から**採る。

### 112. デプロイの順序が W3 の 111 と**逆になる**（PR A）

W3 の 111 は「**コードが先に出る**ので、新しい関数に既定値を付けても『古い関数 × 新しいコード』は守れない」だった。今回は**同じ理由で逆の順序**が要る。

- `/v1` の新しいコードは `v1_stations_current` の `forecast_*` 列を**名指しで読む**。列が無ければ PostgREST が誤りを返し、**`/v1/stations` が全滅する**（503）。
- 逆に、**0033 を先に当てても古いコードは壊れない**。古い `STATION_COLUMNS` は新しい列を選ばないだけで、ビューの列が増えても何も起きない。

**規則にする**：**読む側が増える変更はマイグレーションを先に、書く側が増える変更はコードを先に。** どちらが「増える側」かは、**新しい名前を最初に口にするのがどちらか**で決まる。今回は API が列の名前を先に言う。

### 113. 「出さない予測」は **3% ではなく 0.04%** だった（§8.2 の想定が外れた）

§8.2 は「**出さない**」（`base_observed_at` が 15 分より古い行）が **3% 前後**で安定すると書いた。W3 の 109 で「貸出も返却も止まったポートの古い行が残る」ことが分かっており、その割合（HELLO 2.75%・ドコモ 0.38%）がそのまま出ると考えたためである。

**実測は 0.04%**（20,600 行中 9 行、2026-09-09 05:00 UTC）。**想定した壊れ方と、実際の壊れ方が違う。**

| | 実測 | 何が起きているか |
|---|---|---|
| 予測の**行が無い**ポート | **151 件（0.73%）** | 表を作り始めてから一度も予測できていない。**行が作られない** |
| 予測の行が**古いまま残る**ポート | **9 件（0.04%）** | 予測できていたポートが途中で止まった。**109 が言っていたのはこちら** |

つまり、止まったポートの多くは「古い行が残る」より前に「**行が最初から無い**」形で現れる。`station_forecasts` は 2026-09-08 20:59 JST に書き始めたばかり（17 時間）なので、**「途中で止まる」が積み上がるにはまだ時間が足りない**。

**§8.2 の合格判定を直す**：見るべきは「出さないが 3% 前後か」ではなく、**「出さない」が単調に増え続けていないか**である。予測の行が古いまま残るのは、そのポートが止まっている間だけ起きる正常な状態で、**復帰すれば次の周期で上書きされる**。増え続けるなら、上書きの経路（`upsert_forecasts`）か推論そのものが止まっている。

**どちらにせよ利用者には出ない**（PR A の鮮度切り）ので、これは監視の読み方の問題であって配信の問題ではない。

### 114. 返している確率は「**`generated_at` ＋ `in_min`**」の時刻のもので、利用者の到着時刻ではない

**`?in_min=30` に返す数は「読んだ人の 30 分後」ではない。** 起点が 2 つの意味でずれている。

```
返している時刻 = generated_at + in_min
利用者の到着  = 読んだ時刻   + in_min
ずれ          = 読んだ時刻 − generated_at
```

**`p_*_x1000[i]` の起点は `generated_at`** である。`jobs/infer.py` の `predict(artifact, system_id, rows, now, base, holidays)` は `now`（＝ `generated_at`）で標本を作っており、`minute_of_day` は `now`、`dow_type` は `now + horizon` から決まる。**`base_observed_at` からでも、読んだ時刻からでもない**（`base_observed_at` は台数の観測時刻で、鮮度の判定にだけ使う）。

**ずれは 2 つの項の和**である。

| 項 | 大きさ（実測） | 直せる場所 |
|---|---|---|
| **予測行の年齢**（`now − generated_at`） | 中央 **2.1 分**・最大 **5.3 分**（推論周期が 5 分なので当然こうなる） | **サーバー側**。`in_min + (now − generated_at)` で補間すればよい |
| **CDN のキャッシュ**（`s-maxage=60, stale-while-revalidate=120`） | **最大 3 分**。実測で `age: 82` / `x-vercel-cache: STALE` を確認 | **サーバー側では直せない**（応答を作った時刻が「いま」ではない）。クライアントが `generated_at` で補正するか、**絶対時刻の `at` を送る** |

**確率としてどれだけ違うか**（2026-09-09、鮮度内の 4,000 行 × 2 指標。行の年齢だけを補正した場合との差）

| 到着 | 中央 | 95% | 最大 | **表示の刻み（5%）を跨ぐ割合** |
|---|---|---|---|---|
| 15 分 | 0.0004 | 0.0064 | 0.0203 | 0.00% |
| **30 分** | 0.0004 | 0.0121 | **0.0776** | **2.62%** |
| 60 分 | 0.0004 | 0.0085 | 0.0405 | 0.00% |

**中央値は表示の分解能に埋もれるが、30 分では 2.6% が別の帯に落ちる。** 壊れてはいないが、**「30 分後の確率」と言い切って出すと、その 2.6% は嘘になる。**

**`at`（絶対時刻）はキャッシュでずれない。** 同じ `at` に対する答えは、いつ読んでも同じ到着時刻を指す。秒までばらばらの `at` を送るとキャッシュが効かないので、**5 分の格子に丸めた `at`** を送れば両立する。いまの §6.2 は「**`in_min` で送る**」と書いてあり、**相対の指定はキャッシュと相性が悪い**。

**直す順**

1. **PR B の前に、小さい PR で行の年齢を補正する**（`in_min + (now − generated_at)`）。ビューに `forecast_generated_at` を足す必要がある（PR A では `base_observed_at` しか出していない）。**利用者の目に入る前に直す。**
2. **PR B は `at`（5 分格子）で送る**ことを検討する。§6.2 の「`in_min` で送る」を決め直す。`in_min` のままにするなら、**応答の `generated_at` と `forecast_in_min` から実際の到着時刻を出して表示する**（「約 30 分後」ではなく「14:35 到着」と書く）。

**W3 の 109・110 と同じ形である。** 「持っている数を、少しだけ違う意味で出す」ことは、出したあとでは気づけない。

**直した（PR A′、2026-09-09）**：1 つ目の項（予測行の年齢）をサーバー側で消した。0034 で `v1_stations_current` に `forecast_generated_at` を足し、**`in_min ＋（いま − generated_at）` の位置で補間する**（`forecastHorizon`）。これで返す確率が指すのは常に **`response.generated_at ＋ forecast_in_min`** になり、応答の中の 2 つの値だけで到着の時刻が決まる。

**2 つ目の項（CDN の最大 3 分）は残る。** 応答を作った時刻が読んだ時刻ではない以上、サーバー側では消せない。**PR B の持ち物**：クライアントは `generated_at` を見て「約 30 分後」ではなく**到着の時刻**（「14:35 到着」）で表示する。表示が絶対時刻なら、キャッシュで古くなった応答も嘘にならない。

### 117. 57 列のうち 1 列だけ、**読んだ窓の長さで値が変わっていた**

PR C の一致のゴールデンを書いたところ、**`minutes_since_last_change` だけが必ず食い違う**ことが分かった。

```

推論   3 時間の観測を読む  → 「見えている範囲では動いていない」
```

他の 56 列は窓で閉じている（ラグと流量は 60 分、同時刻履歴は 1 日、静的属性と近傍は参照スナップショット）。**この 1 列だけが「どれだけ過去を読んだか」を値に持ち込んでいた。**

| 案 | 判断 |
|---|---|
| 推論も 25 時間読む | ✗ 実測で**読み込みだけで 20 秒超**。5 分毎の推論には収まらない |

### 118. 00:00〜05:00 JST は、**前日の参照スナップショットがまだ無い**

推論を「前日の版を読む」規則で書いたところ、**その版が置かれるのは 05:00 JST**（`/ml/reference`）だと気づいた。つまり、

```
02:00 JST に推論する → jst_date(t) − 1 = 昨日 の版を読みたい
                    → その版は 05:00 JST に書かれる → まだ無い
```

**1 日の 5 分の 1（60 サイクル × 2 系統）で予測が出なくなる。** 学習では起きない（その日のサンプルを作るのは日が明けてからなので、前日の版は必ず在る）。

**cron を早めることはできない。** 参照スナップショットは `rebuild_geo`（04:30）の後に走る必要があり、その `rebuild_geo` は `sync_stations`（04:00）の後である。連鎖の最後なので 05:00 が最速になる。

**1 つ古い版に下がることにした**（`read_reference_available`）。**黙って下がらない**：使った日付を `inference_log.detail.reference_date` と応答に出す。

**残る食い違い**：00:00〜05:00 のサンプルは、学習が「前日の版」・推論が「前々日の版」を使う。差が出るのは**その 1 日で変わったぶんだけ**（新しいポート約 100 件、近傍 78 ペア、`capacity_est` の増減）で、20,750 ポートの 0.5% ほどである。**新しいポートは予測が 1 日遅れて出る**ことになる（それまでは行が作られない）。

**これは記録して残す。** 直すなら「参照スナップショットの日付を、時刻から決まる関数にする」（`jst_date(t − 5 時間) − 1`）が筋だが、**学習は 1 日を 1 つの版で作る**ので、そちらも作り分けることになる。W5 で `capacity_est` を Postgres に置くとき（§6.2b）に、まとめて考える。

### 119. 予報を取った格子と、ポートから計算する格子が **2 件だけ食い違う**（PR D）

**Open-Meteo は要求した座標を自分の格子に丸め直して返す。** ふつうは要求と一致するが、**595 格子のうち 2 つだけ、1 格子ぶんずれた座標が返る**（2026-09-10 に 59 発行すべてで確認。ずれ方は毎回同じ）。

| 要求した格子 | 返ってきた格子 | そこに居るポート |
|---|---|---|
| (35.65, 138.75) | (35.65, **138.6875**) | 2 |
| (36.75, 139.5625) | (**36.70**, 139.5625) | 2 |

`weather_hourly` の鍵は**返ってきた座標**から作る（ファイルに書いてあるのはそれだけである）ので、この 2 格子に居る **4 ポート（20,754 の 0.019%）は、自分の座標から計算した鍵で引くと当たらない**。天気の 4 列が恒久的に NULL になる。

**借りない。** 隣の格子の値を代わりに入れる案（「1 格子以内でいちばん近いものを使う」）はあり、**この 2 件については実際に正しい**（Open-Meteo はその要求に対してその値を返したのだから）。それでも採らないのは、同じ仕組みが**取り込みの失敗で欠けた格子**にも働いてしまい、「補間しない」（CLAUDE.md §6）が崩れるから。**格子が無いことと、その時刻が無いことは別の話**として扱う。

**代わりに数える。** `DayStats` / `NowStats` の `stations_without_weather` に出る。増えたら気づける。

**ただしこの数は 3 つの理由の合計**で、この所見のぶんはそのうち 4 件である（本番の実測は 7 件＝ 4 ＋ 座標がまだ無い 2 件 ＋ `geo_suspect` の 1 件）。**「4 のはずが 7 ある」と読まないように**、内訳を `features/build.py` の `_without_weather` に書いた。

### 120. プランが挙げた天気の特徴量のうち **2 つは、そもそも取れない**（PR D）

開発プラン §6.3 の天気の行は `precip_mm_now`・`precip_mm_fcst_target`・**`precip_prob_fcst`**・`temp_c`・`wind_ms`・`is_raining_now` を挙げ、W4 プラン §6.4 は「気温・降水量・風速・**湿度**のうち」から選ぶと書いていた。**この 2 つは作れない。**

- **降水確率**：`precipitation_probability` を要求してはいるが、**`jma_msm` は返さない**。210,630 値すべて null で、`hourly_units` も `"undefined"` である（`best_match` は返す：0〜100、σ 30.0）。Open-Meteo の JMA API の変数一覧にも無い。**W4-05（`jma_msm` 一本）を採る以上、この列は存在しない**
- **湿度**：`OPEN_METEO_HOURLY_VARIABLES` に入れていない。**取っていないものは作れない。** 足すなら取得側を変えることになり、**変えた日以降しか埋まらない**（天気は遡れない。R16）

**列を作らない。** 常に NULL の列は、学習側に「欠損の扱い」を考えさせるだけ損をする（`features/schema.py` の冒頭）。`is_raining_now` も作らない：`precip_mm_now > 0` そのもので、木は自分で切れる。

**残るのは 4 つ**で、それが W4-13 の決定である。

### 121. `precipitation` は「直前 1 時間の合計」、`temperature_2m` は瞬時値（PR D）

Open-Meteo の hourly は、**変数ごとに「その時刻が何を指すか」が違う**（JMA API のドキュメントで確認）。

| 変数 | 値の意味 | 単位 |
|---|---|---|
| `precipitation` | **直前 1 時間の合計**（Preceding hour sum） | mm |
| `temperature_2m` | 瞬時 | °C |
| `wind_speed_10m` | 瞬時 | **km/h** |
| `weather_code` | 瞬時 | WMO コード |

つまり `time = 14:00` の降水量は **13:00〜14:00 に降った量**で、気温は **14:00 ちょうどの値**である。**同じ添字で両方を引くと、気温だけが最大 1 時間先の値になる。**

型も名前も同じなので、**間違えても何も起きない**（値が少し変なだけ）。だから規則をコードに書いた：降水量は `containing_hour_ms`（`t` を含む時間帯）、気温と風速は `nearest_hour_ms`（`t` に最も近い毎正時）。`test_the_two_rules_differ_in_the_first_half_of_an_hour` が「2 つが別物であること」を固定している。

**単位も直した。** 開発プラン §5.3・§6.3 は `wind_ms` と書いていたが、返ってくるのは **km/h** である。列名を `wind_kmh` にした（CLAUDE.md §3「変数名に単位を」）。**変換しない**：生の値をそのまま持ち、単位を名前で言う。

### 122. 格子の鍵の丸めが Postgres と Python でたまたま一致している（PR D）

予報を取る座標を決めるのは SQL（`weather_grid_cells` の `round(a.lat / 0.05)`）で、**ポートから鍵を計算するのは Python** である。2 つが違う丸め方をすると、**取ってある格子と引きにいく格子が食い違う**。

**実データにちょうど半端になるポートが 1 件ある**：`docomo-cycle/89032` は `lon / 0.0625 = 2186.5` ちょうどである。

幸い両方とも**偶数丸め**で、どちらも 2186 に落ちる。Postgres の `round(double precision)` は C の `rint()`（偶数丸め）、Python の `round()` と `np.rint()` も偶数丸めである。**`round(numeric)` だったら 2187 になっていた**（あちらは 0.5 を切り上げる）。

いまは正しいが、**正しい理由が「たまたま」に近い。** `test_the_cell_key_rounds_like_postgres` でこの 1 件を固定し、`weather.cell_key` の docstring に理由を書いた。

### 123. 関数の大きさの上限を **2 倍間違えて**書いてあった（PR E）

`apps/ml/pyproject.toml` は 2 か所で「**上限 250 MB に対して余裕がある**」と書いていた。**250 MB は Node の関数の数字**で、**Python は 500 MB** である（Vercel のドキュメント。開発プラン §4.5 は最初から「バンドル 250 MB（**Python 500 MB**）」と正しく書いていた）。

**危うく設計が変わるところだった。** LightGBM を入れると 334 MB になり、250 MB なら**入らない**。そこで「木を numpy で歩く」案を実装し、**完全に一致すること**（差 0.0、欠損・カテゴリ・未知の値まで）と、**50 倍遅いこと**（148k 行 × 120 木で 14 秒、LightGBM は 0.23 秒）まで測った。上限が 500 MB だと分かった時点で、その案は要らなくなった。

**もう 1 つ分かったこと**：同じ注記の「155 MB」は 2026-09-08 の値で、**いまは 212 MB** である。

| | 2026-09-08 | 2026-09-10 |
|---|---|---|
| pyarrow | 20.0（123 MB） | **25.0.1（152 MB）** |
| numpy | 2.2（22 MB） | **2.5.3（57 MB）** |
| 合計 | 155 MB | **212 MB** |

**依存を 1 つも足していないのに 57 MB 増えている。** 版の範囲（`pyarrow>=18,<26`）を開けてあるので、`uv lock` を打ち直すたびに動く。500 MB に対しては余裕があるが、**「余裕がある」と書いた数字は測った日の値でしかない**。

**直したこと**：注記を 500 MB に直し、いまの実測（212 / 334 / 上限 500）を表で書いた。

### 124. 0038 で書いた制約と権限が、**書いたつもりのことをしていなかった**（PR E）

2 件とも pgTAP が捕まえた。どちらも「SQL としては正しく、意図としては無効」という形をしている。

**① 空配列を弾く制約が素通りしていた。**

```sql
check (array_length(train_days, 1) >= 1)   -- 空配列で array_length は NULL
```

`array_length('{}', 1)` は **0 ではなく NULL** を返す。`NULL >= 1` は NULL で、**CHECK 制約は NULL を通す**。`coalesce(array_length(train_days, 1), 0) >= 1` に直した。

**② `grant select, insert` だけでは update / delete が残っていた。**

0006 が `service_role` に既定権限を入れてあるので、**新しい表には自動的に全権限が付く**。`grant select, insert` は足し算なので、`update` と `delete` は付いたままだった。「状態を動かす口はサービスに渡さない」という意図が効いていなかった。**`revoke all ... from service_role` を先に書く**ように直した。

同じことが関数にも起きる：`promote_model_version` は「誰にも grant しない」つもりだったが、**ローカルでは既定権限で `service_role` に EXECUTE が付いていた**（本番は「新規オブジェクトの自動公開」が OFF なので付かない。W3 プラン §12 の 90 の裏返し）。**環境によって権限が違う状態を残さない**ために、明示的に `revoke` した。

いまは PostgREST 越しに叩くと **403（`permission denied for function`）** が返ることをローカルで確認してある。

### 125. `.gitignore` の `models/` が、**新しい Python パッケージを丸ごと隠していた**（PR E）

`.gitignore` に「データ成果物」として書いてあった 1 行。


### 126. **`lightgbm` は Vercel の Python ランタイムでは読み込めない**——`libgomp.so.1` が無い（PR E → PR E′）

PR E をマージし、成果物を置き、候補を登録し、試し打ちを叩いたところ、**500 が返った**。

```
{"error":"libgomp.so.1: cannot open shared object file: No such file or directory",
 "phase":"infer","error_name":"OSError"}
```

**原因**：`lightgbm` の PyPI ホイールに入っている `lib_lightgbm.so` は、共有ライブラリとして **`libgomp.so.1`（GNU OpenMP）を必要とする**（`DT_NEEDED` に入っている）。ところが**ホイールはそれを同梱していない**（`lightgbm.libs/` が無い。numpy や scipy は `.libs/` に同梱するので、同じ流儀だと思い込んでいた）。Vercel の Python ランタイムは Amazon Linux で、**`libgomp.so.1` は入っていない**。Docker で同じ土台を作って再現した。

**W4-15 の判断は「334 MB < 500 MB」に基づいていた。** 数字は正しかった。**測っていたものが違った。**

| 測ったもの | 結果 | 効いていたか |
|---|---|---|
| バンドルの大きさ | 334 MB（上限 500 MB） | **効いていない** |
| ランタイムに `libgomp.so.1` があるか | **無い** | **これが効いていた** |

**いちばん怖いのは、どの検査も通ったこと。**

- **`pip install` は通る**（ホイールは正しい）
- **Vercel のビルドは通る**（依存を展開して固めるだけ）
- **バンドルの大きさの検査も通る**（334 MB）
- **プレビューのデプロイは「成功」と表示される**

**共有ライブラリの解決は `dlopen` の時点**、つまり **`import lightgbm` を実際に実行した瞬間**にしか起きない。そして `/ml/infer` は `kind = 'lightgbm'` の枝に入ったときだけ import していた（PR E で「ベースラインを配っているあいだは読み込まない」ようにしてあった）。**条件付き import が、失敗を最後の瞬間まで隠した。**

**本番への影響は無かった。** 配信中の `active` はベースラインで、その経路は `lightgbm` を一度も import しない。`inference_log` の lgbm 行は 0 件、`station_forecasts` は全部ベースラインのままだった。**壊れたのは試し打ちだけ**である。

**直したこと（PR E′）**：`lightgbm` を本番依存から外し（W4-19）、**木の構造そのものを成果物に持ってnumpy で歩く**ようにした（§6.5a）。PR E のときに「入らなかった場合の備え」として実装し、**測ってから捨てた**あの案を採った。

> **⚠️ ただし、これが唯一の道ではなかった**（§12 の 128）。足りないのは 352 KB の共有ライブラリ 1 個で、**同梱すれば LightGBM は動く**。**その選択肢を試さずに実装を選んでいた。**

**規則**：**「入れても動く」は、バンドルに入ることではなく、ランタイムで `import` が通ることで確かめる。** ネイティブ拡張を持つパッケージを本番依存に足すときは、**本番と同じ土台のコンテナで `python -c "import X"` を実行して**から決める。大きさだけを見て決めない。

```bash
# 本番と同じ土台で読み込めるかを見る（これを先にやる）
docker run --rm --platform linux/amd64 public.ecr.aws/lambda/python:3.12 \
  sh -c 'pip install -q lightgbm && python -c "import lightgbm"'
```

**もう 1 つの規則**：**条件付き import は「失敗を無くす」ものではなく「遅らせる」もの。** 枝の中に隠すと、その枝を最初に踏んだ人が失敗を受け取る。**枝の中で import するものほど、その枝を通す検査を先に書く。**

**3 つめ**：**捨てる側の選択肢を、採る側と同じ丁寧さで測る。** W4-15 は numpy 案を「50 倍遅い」で退けたが、それは**素直に書いた版を 1 度測っただけ**の値だった。実際に採らざるを得なくなってプロファイルを取ると、**規則を 1 つも変えずに 4.4 倍速くなり、ネイティブ・CPU 秒での実測は 1.5〜1.6 倍だった**（§12 の 128）。**退ける根拠になる数字ほど、退ける前に詰める。** 浅い測定は「採らない理由」としては通ってしまい、誰にも検算されない。

**4 つめ**：**「動かない」を「その道具は使えない」と読み替えない。** この所見を書いた私自身が、直後に同じ誤りをしている——足りないものが `libgomp.so.1` だと特定できていたのに、**足すことを試さずに**代替実装へ飛んだ（§12 の 128）。**手元に代替案があること自体が、選択肢を検討しない理由になってしまう。**

### 127. **クラウドは手元の 1.5〜2 倍ではなく 3.0 倍遅く、LightGBM を配ると費用が跳ねる**（PR E′）

PR E′ をマージし、成果物を置き換え、本番で試し打ちした。**通った**——特徴量 → 行列 → 木 → 確率まで、PR E で `OSError` になったところを越えた。**が、速さの見込みが外れていた。**

| | 見込み | 実測 |
|---|---:|---:|
| HELLO の 1 サイクル（木の探索） | 33〜44 秒 | **65.8 秒** |
| 全体（＋特徴量） | 44〜55 秒 | **77.7 秒** |

**見込みの出どころは「クラウドの vCPU は M 系の 1.5〜2 倍遅い」**（開発プラン §8.2、2026-09-04 に書いた仮定）。手元の 21.8 秒に掛けて出した数字である。**実際は 3.0 倍**だった。

**仮定を 2 段重ねた**のが誤りだった。①手元で測る → ②係数を掛けてクラウドを推す。①は丁寧にやった（4 周の最小、ブロック幅も振った）が、**②は 5 か月前に別の作業のために置いた係数を、検算せずに使った**。所見 126 で「大きさを測って、動くかを測っていなかった」と書いたのと同じ形である——**測った数字は正しく、測っていないものが効いていた。**

#### 効いてくるのは `maxDuration` ではなく費用

77.7 秒は `maxDuration`（120 秒）に収まる。**問題は Active CPU の課金のほう。**

| | **CPU 秒/周期**（両系合計） | 月の CPU | **CPU ぶんだけ**の月額（東京 $0.202/CPU 時） |
|---|---:|---:|---:|
| いま（B3） | **18 秒** | 44 CPU 時 | **$9** |
| LightGBM | **121 秒** | 291 CPU 時 | **$59** |

**$20 のクレジットを超える**（CLAUDE.md §2 の原則 9）。

> **⚠️ 2 つ注意がある。** ①**この表は推論の CPU ぶんだけ**で、メモリと他のジョブを足した使用量の総額は **$14 → $71**（§12 の 128）。②**当初ここに書いた「32 秒 / 133 秒 / $16 / $65」は実時間を CPU として計算していた**。Vercel が課金するのは **Active CPU** で、推論は実時間 31.4 秒に対し **CPU 18.3 秒**である（`cpu_ms` の実測）。**1.7 倍に見積もっていた。**

**いま壊れているものは無い。** 候補は配信していないので、この費用は発生していない（`inference_log` の lgbm 行は 0 件）。**W6 で `shadow` に上げる前の決定事項**になる。

**規則**：**「手元で測って係数を掛ける」は見積りであって実測ではない。** 費用や上限に効く数字は、**その環境で 1 回動かして測る**。動かせない段階では、見積りには必ず「見込み」と書き、**判断はそこでしない**。

**W4-11 と合流させる。** 9/12〜13 に Vercel の Usage の内訳を見て B か D を選ぶことになっていたが、**そこに「LightGBM を配ると使用量が $14 → $71 になる」という材料が加わった**（§12 の 128）。選べる手は 5 つある（開発プラン §8.2 の 4 つ ＋ 評価器をさらに詰める）。

### 128. **`libgomp` を同梱すれば LightGBM は動いた**——選択肢を試さずに実装を選んでいた（PR E′ の見直し）

PR E′ をマージした後、「numpy で木を歩くのは本当に最善だったか」を洗い直した。**最善ではなかった。少なくとも、最善だと言える根拠を持っていなかった。**

#### 試していなかったこと

所見 126 の問題は「**共有ライブラリが 1 個足りない**」だった。**足せばよい。**

```python
import ctypes
ctypes.CDLL("/vendor/libgomp.so.1", mode=ctypes.RTLD_GLOBAL)
import lightgbm          # → OK 4.7.0
```

本番と同じ土台（`public.ecr.aws/lambda/python:3.12`）で検証した。`libgomp.so.1` は **352 KB**。`LD_LIBRARY_PATH=/vendor` でも同じく動いた。**200 行の木探索コードより、はるかに小さい変更である。**

**所見 126 で「大きさを測って、動くかを測っていなかった」と書いた、その直後に同じ誤りをしている。** 問題を「LightGBM が使えない」と読み替え、**すでに手元にあった実装**（PR E のときに作って捨てた numpy 案）へ飛びついた。**「無いものを足す」を一度も試していない。** 検証に要した時間は 15 分だった。

#### 速さ——3 回とも数字が違っていた

| いつ | 主張 | 何が問題だったか |
|---|---|---|
| W4-15 | 「50 倍遅い」 | **最適化前の版を 1 度測っただけ** |
| PR E′ §6.5a | 「2.3 倍」 | **5 か月前の係数**で割り出した推定（所見 127） |
| 見直しの初回 | 「7.8 倍」 | **amd64 エミュレーション**で測った。numpy の SIMD が不利に出る歪み |
| 見直しの 2 回目 | 「1.7〜1.8 倍」 | **実時間の単発測定**。課金される単位ではない |
| **ネイティブ実測（CPU 秒・3 回の最小）** | **1.5〜1.6 倍** | 同じ機械・同じ木・同じ行。`scripts/measure-tree-evaluators.py` |

同じ木（300 本・75,544 節・深さ 25。本番の実物は 75,900 節・深さ 30）を 148,610 行に当てた実測：

| | 実時間 | **CPU 秒** |
|---|---:|---:|
| LightGBM C（1 スレッド） | 7.5〜8.1 秒 | **7.1〜7.3 秒** |
| LightGBM C（既定スレッド） | 1.6〜2.1 秒 | **8.3〜8.4 秒** |
| numpy（`models/forest.py`） | 12.0〜12.5 秒 | **11.2〜11.4 秒** |

**`scripts/measure-tree-evaluators.py` で再現できる。**（初回に「1.7〜1.8 倍・並列化の代償 49%」と書いたのは**実時間の単発測定**だった。CPU 秒を 3 回の最小で取り直した値が上である——**この節自身が 4 度目の測り直し**になっている。）

**並列化は費用を下げない。** Vercel は **Active CPU 課金**なので、実時間が 4〜5 倍速くなっても **CPU 秒は 13〜18% 増える**（スレッドの立ち上げ分）。LightGBM に戻しても **`num_threads=1` を固定しなければ差は 1.35 倍しか出ない**（11.3 対 8.4）。

#### それでも numpy を維持する（W6 まで）

**戻さない理由は「numpy のほうが良いから」ではない。**

1. **戻しても予算に届かない**（$71 → $52。クレジットは $20）。$19/月のために、**本番で一度壊れた「ビルドでは捕まらない実行時の失敗」を意図的に呼び戻す**ことになる。しかも今度は Vercel のベースイメージへの追随を自前で負う
2. **このモデルは配信しない。** v0 は採用基準を 33 バケツ中 13 でしか満たしていない（§6.5）。**評価器を決めるべきなのは、実際に配る W6 のモデルの形が分かってから**である
3. **木を半分にすれば差は実質消える。** W6 が 150 本＋スキップ規則なら numpy で足り、native 依存のリスクを一度も取らずに済む
4. numpy 版は**すでに 2,070,413 行で照合済み・本番で確認済み**である

**戻す価値が出る条件も、これで明確になった**：W6 のモデルが 300 本以上で、特徴量側（W4-11）を最適化してなお予算を超え、かつ `num_threads=1` を固定するなら、$19/月の差は実質的である。

#### 規則

**「動かない」を「その道具は使えない」と読み替えない。** 足りないものが特定できているなら、**まず足すことを試す**。手元に代替実装があるときほど、この飛躍が起きる——**代替案が既にあること自体が、選択肢を検討しない理由になってしまう。**

**比較する数字は、比較する環境で・課金される単位で・複数回の最小で測る。** この 3 つを外すたびに数字が動いた——エミュレーションで 7.8 倍、実時間の単発で 1.8 倍、**CPU 秒の 3 回最小で 1.5〜1.6 倍**。`scripts/measure-tree-evaluators.py` に測り方ごと残した。**次に決める人は、この数字を信じずに自分で回すこと。**

### 129. **`lat` / `lon` を「非 null」と宣言していた根拠が、読み方によって崩れる**（PR G）

`view-query.ts` の行の型にこう書いてあった。

```ts
/**
 * `lat` / `lon` を非 null にしているのは、**bbox で絞った結果しか読まない**からで、
 * 座標の無いポート（属性をまだ取れていない）は範囲比較で自然に外れる。
 */
lat: z.number(),
lon: z.number(),
```

**注記のとおり、正しかった。** `/v1/stations` は bbox で引くので、座標の無い行は範囲比較で落ちる。**「引き方」が前提になっている型**だった。

`/v1/trip-check` は **ID で引く**。同じビュー・同じ型・別の引き方で、**前提が黙って崩れる**。

#### 気づけたのは、検査を先に書いたから

「座標が無くても `ride_min` を渡せば通る」を確かめる検査を書いたところ、**Zod が行を弾いて 503 になった**。実装を書きながらなら「まあ起きないだろう」で済ませていた。

**実測（2026-09-11、本番）**

| | 件数 |
|---|---:|
| 座標の無いポート | **10**（全 20,700 件中） |
| **うち予測を持っていたもの** | **1** |

**「座標が無い＝属性がまだ来ていない＝予測も無い」と思い込んでいたが、違った。** 属性が失効しても `station_forecasts` の行は残る。

#### 直したこと

1. **型を実態に合わせる**（`lat: z.number().nullable()`）
2. **`hasLocation` の型ガードで明示的に外す。** `/v1/stations` は `.filter(hasLocation)` を通す——bbox が落としているので**挙動は変わらないが、「落ちているはず」が型で言える**
3. `/v1/trip-check` は座標の無いポートを**端点にも代替候補にもしない**（`station_location_missing`）

**規則**：**「この引き方なら起きない」を型の根拠にしない。** 型はデータの性質を表すもので、問い合わせの都合を表すものではない。**同じビューを別の引き方で読む日が来たとき、型は嘘になる**——そして Zod が弾くので、壊れ方は 503 になる（静かに間違うよりはよいが、200 で返せるはずのものが落ちる）。

**絞り込みは型ではなくコードで表す。** `hasLocation` のような型ガードなら、「ここで外している」が読める場所に残る。
