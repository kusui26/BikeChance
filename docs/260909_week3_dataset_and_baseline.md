## 1. Week 3 のゴールと完了条件

**ゴール：貯めたデータから「学習サンプル」を作れる状態にし、超えるべき線を測る。**

W1 で「集める」、W2 で「残す・読む」が完成した。W3 の主題は 3 つある。

1. **静かに失われる経路を塞ぐ**（監視の穴・バックアップ収集器）。W2 の点検で、ジョブが落ちても誰も気づかない状態が残っていることが分かった。天気アーカイブは落ちた時刻の予報が永久に失われる。

3. **特徴量とラベルを作る一本道を通し、ベースラインで線を引く**。LightGBM の良し悪しは、比較対象が無ければ判定できない。

## 3. W3 で確定させた設計判断

W1 の W1-01〜W1-31、W2 の W2-01〜W2-13 に続けて **W3-01 から**採番する。**実装前に決め、実装で変わったら §3 と開発プランを直してから進む**（CLAUDE.md §2 の原則 10）。

### 3.1 監視と冗長化について

| ID | 論点 | 決定 | 根拠 |
|---|---|---|---|
| **W3-01** | ジョブの異常をどう検知するか | **「失敗が在る」ではなく「直近 N 時間に成功が無い」を見る** | cron が 1 度も起動しなければ `job_runs` に行が無く、`status = 'failed'` を探しても何も見つからない。収集のウォッチドッグが `last_fetch_at` の古さを見ているのと同じ考え方（W1-29）。失敗の検知は補助として併置する |
| **W3-02** | 新しい検査をどこに置くか | **`monitor_feeds` に足さず、別関数 `monitor_jobs()` を作って pg_cron の別ジョブにする** | 現在の `monitor_feeds` は**全検査を 1 つの `begin ... exception when others` で包んでいる**（実装で確認）。1 つの検査が落ちると残りが全部飛び、`job_runs` には `failed` が 1 行残るだけになる。新しい検査は `storage.objects` を読むので、権限や重さで落ちる可能性が既存の検査より高い。**495 回連続で成功している監視を、増築で壊さない。** pg_cron のジョブは 5 本 → 6 本で、Supabase の推奨（同時 8 本以下）に収まる |
| **W3-03** | バックアップ収集器は何をするか | **生 gzip JSON を Storage に保存するだけにする。`ingest_snapshot` を呼ばない**（開発プラン §5.7 の「同じ RPC に書く」から変更） | 守るべき不変条件は「生 JSON を必ず残す」（CLAUDE.md 最重要原則 1）で、Postgres の配列は**再構築できる**（W2 の PR B で実証。照合 6/6 一致）。RPC を呼ぶには正規化（負値の丸め・重複排除・フラグ・`idx` の採番）を Deno で再現する必要があり、**本番と冗長系で正規化がずれる**という新しいリスクを作る（W2-05 と同じ型）。保存だけなら Deno 側にドメインロジックがほぼ無くなる。動いたことは `job_runs` にだけ記録する |
| **W3-04** | バックアップ収集器の ODPT 認証 | **公開エンドポイント（`api-public.odpt.org`）を使い、トークンを持たせない** | CLAUDE.md は「トークン付き URL を組み立てるのは `apps/web/lib/jobs/odpt-fetch.ts` だけ」と定めている。冗長系のために 2 つ目の組み立て箇所と 2 つ目の秘密の置き場所を作るのは、規約の例外を増やすぶん割に合わない。**実測（2026-09-08）で公開エンドポイントは無認証で 200 を返す**（HELLO 4,221,822 B / 0.91 秒 / 14,921 ポート、ドコモ 903,586 B / 0.27 秒 / 5,818 ポート）。応答は認証付きと同一（D-04 の実測）。この決定により、Edge Function に新しい秘密は 1 つも要らない（Supabase が注入するサービスロールキーだけ） |
| **W3-05** | バックアップ収集器の起動条件 | **pg_cron（1 分毎）が `feed_state.last_success_at` の 6 分超の停滞を見て `net.http_post` する。1 システムにつき 1 分に 1 回まで** | ODPT を過負荷にしない（CLAUDE.md §2 の 8）。常時二重化はしない（D-16）。6 分は、毎分ポーリング＋ウォッチドッグ（1 分毎）でも復帰しない状態、つまり Vercel 側が丸ごと死んでいる状態にだけ当たる |

### 3.2 参照データについて

| ID | 論点 | 決定 | 根拠 |

| **W3-07** | 行政区域（`pref_code` / `muni_code`） | **HELLO は `address` から `pref_code` と `muni_code` の両方を埋める（`pref_code` だけにしない）。ドコモは両方 NULL のままにし、`region_id` をカテゴリ特徴量として使う。国土数値情報 N03 のポリゴン照合は W3 では行わない** | **実測（§10.2a）で 3 つ分かった。**(1) **`pref_code` 単独はほぼ価値が無い**（ポート毎の `P(bikes=0)` を leave-one-out で当てて R² 0.024）。`muni_code` は 5 倍強い（R² 0.132）が、**住所から取れば費用は同じ**なので `pref` だけ埋める理由が無い。(2) **近傍リストのほうが `muni_code` より当たる**（k=10 / 1 km で R² 0.201、k=20 / 2 km で 0.225）。**近傍で説明したあと市区町村が足す残差は 1.49%** しかない。(3) 近傍数の帯ごとに見ると、**近傍が 1 件でもあれば必ず近傍が勝つ**。市区町村が勝つのは近傍 0 件のポートだけ。したがって N03（全国 611 MB・都道府県別 11 MB × 約 30、幾何ライブラリの追加が必要）で埋まるのは「**ドコモかつ 1 km 以内に近傍 0 件**」の **136 ポート（全 20,742 の 0.66%）**にすぎない。**費用の桁が価値に見合わない。** ポリゴン照合は §8 に置き、外部の市区町村データ（人口・乗降客数など）と結合したくなった時点で判断する |

| **W3-08** | 近傍リストの作り方 | **PostGIS を入れず、Postgres の中で緯度経度の格子バケツ＋距離式で作る** | 実測（段 5 で測り直した確定値）：全 20,741 ポート（`geo_suspect` の 1 件を除く）で半径 500 m の近傍は **106,438 ペア（片方向）**、平均 5.1・中央 4・最大 33。Postgres の中で格子バケツ＋haversine を回して **1.7 秒**で全部出る。**着手前の Python 見積り（97,822）は約 8% 低かった**（§10.2・§12 の 93）。PostGIS は利用可能（3.3.7）だが未インストールで、入れれば `spatial_ref_sys` 等で DB が増え、拡張の版管理も増える。**この規模では要らない。** `cube` + `earthdistance` も同様 |
| **W3-09** | 近傍リストの更新 | **日次で全置換する（差分更新しない）** | 10 万行の全置換は 1 秒未満。差分更新の複雑さ（消えたポート・動いたポート・SCD2 の閉じ方）に見合わない。台帳は 1 日に約 100 件増える（W1 実測）ので、日次で十分追随する |
| **W3-10** | 祝日の取り込み | **内閣府 CSV を月次で取り込む。年末年始（12/29–1/3）とお盆（8/13–16）は `jp_holidays` に「行政の祝日ではない休業日」として別種別で入れる** | 実測：CSV は Shift_JIS・21,538 B・1,068 行、**2027-11-23 まで**収録（2026 年 18 件・2027 年 17 件）、`last-modified: 2026-02-02`、`etag` あり（条件付き取得が効く）。年末年始とお盆は収録されないが、シェアサイクルの需要には効く。**同じテーブルに入れて `kind` で分ける**と、特徴量側は 1 か所を引くだけで済む |

## 5. PR の分割と各 PR の定義

### 5.1 分割の方針

W1・W2 と同じ。1 つの PR は **1 つの関心事**に閉じ、レビューが 20〜60 分で終わる量にする。各 PR はそれ自体で CI を通し、テストを含む。**本番に影響する変更を後ろに寄せる。ただし損失が日ごとに積み上がるものは最初に置く。**

W2 プラン §14.1 で決めた並べ方の原則をそのまま使う：**「遅れた分が損失になるか」で並べる。** 難しさでも面白さでもない。

| 段 | PR | 名前 | 主な成果物 | 遅れると失われるか | 本番影響 | 目安 |
|---|---|---|---|---|---|---|
| **0** | — | 天気アーカイブの 1 日判定 | W2 の暫定合格を確定させる | — | なし | 15 分 |

### 5.2 段 0：天気アーカイブの 1 日判定（PR なし）

```sql
select date_trunc('hour', created_at at time zone 'Asia/Tokyo') as 時,
```

**ゲート**：24 時間ぶんの時刻が 24 個あり、どの時刻も 6 ファイル。欠けがあれば PR A より先に原因を調べる（**そこが段 1 で塞ごうとしている穴そのもの**なので、実例が手に入る）。

### 5.3 PR A：監視の穴を塞ぐ

**目的**：静かに落ちる経路を無くす。とくに**天気アーカイブ**は、落ちた時刻の予報が永久に失われる。

```
supabase/migrations/20260908043706_0020_monitor_jobs.sql
supabase/tests/0011_monitor_jobs.sql
```

**新しい関数を作る**（`monitor_feeds` には触らない。W3-02）。pg_cron に 5 分毎のジョブとして登録する。

#### 検査を 4 つの関数に分けた（実装で決めたこと）

プランでは「`monitor_jobs()` の中に検査を並べ、`begin ... exception` で囲む」としていたが、**検査ごとに別の関数にした**。

| 理由 | |
|---|---|
| 1 関数 20 行未満・単一責務（CLAUDE.md §3） | 4 検査を 1 関数に入れると 200 行を超える |
| **単体でテストできる** | pgTAP から `check_parquet_gap()` だけを呼んで、窓の境界を 4 通り確かめられる |
| 隔離が 1 か所で書ける | 親は `execute format('select public.%I()', v_name)` で回すだけ。**コピペした exception 節が 4 つ並ばない** |

```
public.check_jobs_missing()     直近 N のあいだ status='ok' が無いジョブ
public.check_jobs_failed()      直近 3 時間に status='failed' があるジョブ（全ジョブ対象）
public.check_parquet_gap()      status_snapshots に行が在るのに Parquet が無い時間帯
public.check_reference_data()   参照データの期限（いまは祝日のみ）
public.monitor_jobs()           上を 1 つずつ例外を切り分けて呼ぶ。これだけが親の仕事
```

| 検査 | 条件 | 抑制 | 鍵 |
|---|---|---|---|
| **ジョブが動いていない** | 対象ジョブの `status = 'ok'` が直近 N のあいだ 1 件も無い | 3 時間 | `job_missing:<job>` |
| **ジョブが失敗した** | 直近 3 時間に `status = 'failed'` がある | 1 時間 | `job_failed:<job>` |
| **Parquet に欠落がある** | 直近 6 時間（末尾 1 時間は猶予）で、`status_snapshots` に行が在るのに Storage に対応するオブジェクトが無い | 6 時間 | `parquet_gap` |
| **祝日データが尽きかけている** | `jp_holidays` の最終収録日まで 90 日を切った | 7 日 | `holidays_expiring` |
| **検査そのものが落ちた** | いずれかの検査が例外を投げた | 1 時間 | `monitor_check_failed:<check>` |

#### 監視対象は `public.monitored_jobs` に持つ

プランでは 6 ジョブとしていたが、**9 ジョブにした**。毎分・5 分毎のものも入れる。

| ジョブ名 | 期待周期 | 「成功が無い」閾値 | なぜ入れるか |
|---|---|---|---|
| `watchdog_collect` | 1 分 | 15 分 | 個別に外されたら気づきたい |
| `monitor_feeds` | 5 分 | 30 分 | 同上 |
| **`monitor_jobs`** | 5 分 | 30 分 | **自分自身。復旧したときに空白があったことを検出できる** |
| `compact_parquet` | 1 時間 | **3 時間** | 2 回落ちたら鳴る |
| `archive_weather` | 1 時間 | **3 時間** | 落ちた時刻の予報は永久に失われる |
| `maintain_partitions` | 1 日 | 30 時間 | |
| `refresh_station_activity` | 1 日 | 30 時間 | |
| `daily_quality` | 1 日 | 30 時間 | **0020 で入れ忘れ、0022 で追加した**（§12 の 86） |
| `sync_stations:hellocycling` | 1 日 | 30 時間 | |
| `sync_stations:docomo-cycle` | 1 日 | 30 時間 | |

**`monitor_jobs` 自身の停止は、この仕組みでは検知できない。** pg_cron ごと止まれば監視も通知も止まる。それでも表に入れてあるのは、**復旧したときに「30 分以上動いていなかった」を残せる**ため。

#### 実装で足した 3 つの安全装置

| # | 何を | なぜ |
|---|---|---|
| 1 | **`added_at` の猶予**（`now() > added_at + missing_after` になるまで見ない） | 適用直後は「まだ 1 度も回っていない」だけかもしれない。日次ジョブは 1 巡するまで判断できない。**これが無いと migration を当てた瞬間に 9 件の誤報が出る** |
| 2 | **`missing_after > expected_every` の check 制約** | 閾値が周期より短いと必ず鳴り続ける。設定ミスを DB で止める |
| 3 | **Parquet 欠落の窓の末尾に 1 時間の猶予** | 毎時ジョブは :07 に前 1 時間を畳むので、:00〜:07 は「まだ無い」のが正常。猶予が無いと**毎時 7 分間だけ誤報**が出る |

**設計上の注意**

- `storage.objects` は**スキーマ付きで書く**（`set search_path = ''`）。`postgres` は **BYPASSRLS** を持つので `security definer` の中から全行が見える（本番・ローカルとも実測で確認）
- 欠落検査は**直近 6 時間に限る**。古い欠落の埋め戻しは別の話（データ辞書 §13 の SQL を手で回す）
- アドバイザリロックは **(8423, 6)**。1〜5 は 0009・0011・0013 が使っている（W1-30）
- Cron は **`4-59/5 * * * *`**（:04, :09, …）。`monitor_feeds`（:00, :05 …）・`compact_parquet`（:07）・`archive_weather`（:17）と重ねない
- **`job_runs` が 1 日 288 行増える**（1,780 → 約 2,070 行/日）。W7 の保持では `watchdog_collect`・`monitor_feeds` と同じく**消してよい側**に入れる（§8）

```
docs/data_dictionary.md v1.4 §7.3              # 契約
```

**列は `fetched_at` 1 つだけにする。** `raw_path` は `(system_id, observed_at)` から組み立て直せる（`rawObjectPath`）。`n_stations` と `is_anomalous` は Parquet から導ける（W2 プラン §13 の (10)(11)）。**導けるものは足さない。**

**列の位置は `observed_at` の直後**。`parquet-tools` で覗いたときに並びで意味が分かるようにする。型も `observed_at` と揃える（`timestamp[ms, tz=UTC]`）。

#### 既存を同じ変更の中で畳み直す

**列を足すだけで再圧縮しないと、読む側が静かに壊れる**（W2 §14.3 の実測）。

| 読み方 | 古いファイル（列なし）と新しいファイル（列あり）を混ぜたとき |
|---|---|
| `ds.dataset(...)`（スキーマを渡さない） | **`fetched_at` が黙って消える。** 最初に見つけたファイルからスキーマを推論するため。エラーは出ず、しかも「最初」は環境で変わる |
| `ds.dataset(..., schema=SCHEMA)` | 古いファイルの `fetched_at` が `null` になる。**気づける** |

したがって、スキーマ変更と畳み直しを**同じ変更で**行う。ただし**畳み直しは本番の `/ml/compact` を叩くので、マージして Vercel がデプロイしたあとにしか実行できない**。順序は「PR → マージ → 畳み直し → 確認」で、**列が混ざったまま放置される期間を作らない**ことが目的である。

#### 畳み直しはスクリプトにする

その場限りの `curl` ループにしない。**同じことがまた要る**からである。

| いつ | なぜ |
|---|---|
| 今回（段 2） | 47 時間（2026-09-06 06:00Z 〜 2026-09-08 04:00Z） |
| 将来スキーマを足すとき | 同じ手順になる |
| **2026-11-05 以降** | 9 月分が `status_snapshots` から落ち始める。**先に `rebuild-snapshots.ts` で生 JSON から戻し、それから畳み直す**（2 段階） |

```bash
pnpm exec tsx scripts/recompact-parquet.ts .env 2026-09-06T06:00:00Z --dry-run
pnpm exec tsx scripts/recompact-parquet.ts .env 2026-09-06T06:00:00Z
```

- 開始・終了は **UTC の正時**（Parquet のパスと同じ）。両端を含む。終了を省くと「直前の完全な 1 時間」まで
- 宛先は `app_config.project_base_url`（ウォッチドッグと同じ値。`BASE_URL` で上書きできる）
- **1 度だけ試し直す**。連続で失敗するなら原因が別にあるので止める
- 冪等（同じ時間帯は同じパスに上書き）なので、途中で落ちたら同じ範囲をもう一度流せばよい
- `CRON_SECRET` は `Authorization` ヘッダにしか出さない（CLAUDE.md §5）

#### テストで固定した契約

| 何を | なぜ |
|---|---|
| **列の順序と型**（`SCHEMA.names` の完全一致、`fetched_at` の型が `observed_at` と同じ、`nullable=False`） | 位置も契約に含める |
| **全行に値が入る**（`null_count == 0`） | スカラなのでそのスナップショットの全ポートに同じ値 |
| **`observed_at` と違う値になる** | この 2 つを取り違えると train/serve skew になる |
| **スナップショットごとに違う値になる** | 1 つの表に複数の取り込み時刻が混ざる |
| **Parquet に書いて読んで消えない** | 列を足しただけで満足しない |
| **`select` に `fetched_at` が入る** | 取り忘れると Parquet に入らず、静かに古い規約に戻る |
| **列が返ってこなければ止まる** | `null` で埋めて先に進まない（`ShapeError` → そのシステムだけ `ok=false` で `job_runs` に残る） |

あわせて、`test_eda_01.py` に 3 か所あった同じ表の組み立てを `table_of()` に集約した。**`fetched_at` を足したとき 3 か所とも直すことになった**ので、次に列が増えたときに直す場所を 1 つにする。

**完了条件**：全期間がファイル 8 列で読め、`fetched_at` に `null` が 1 件も無い。`schema=` を渡す読み方と渡さない読み方の**両方で同じ列**になる（比べ方は §7.3。hive のパーティション列が足されるので列数では比べない）。所要は 1 時間あたり約 3.3 秒（実測）で、47 時間なら 3〜4 分。

### 5.5 PR C：バックアップ収集器（Edge Function）

**目的**：Vercel 全体の障害・デプロイ事故のあいだも、生 JSON だけは失わない（R13・R18）。

```

supabase/functions/collect-gbfs-backup/index.ts       # Deno の殻（serve・env・fetch・gzip）

supabase/config.toml                                  # verify_jwt = false
```

**やることは 3 つだけ**（W3-03）。

```
1. ODPT の公開エンドポイントから station_status.json を取る（トークン無し。W3-04）
2. last_updated を読み、gzip して gbfs-raw の同じパスに upsert:false で PUT する

```

**やらないこと**：正規化、`ingest_snapshot` の呼び出し、`feed_state` の更新。復旧後は `scripts/rebuild-snapshots.ts` で DB に戻す（§9.2）。

#### 純粋な部分と Deno の殻を分けた（実装で決めたこと）

プランでは `index.ts` と `path.ts` の 2 つとしていたが、**`core.ts`（純粋）と `index.ts`（殻）**にした。

| ファイル | 中身 | 誰が見るか |
|---|---|---|
| `core.ts` | パス規約・URL の組み立て・`last_updated` の読み取り・認証・重複の判定 | **vitest と `apps/web` の `tsc`**。Deno の API を一切使わないので、拡張子なしで import できる |
| `index.ts` | `Deno.serve`・環境変数・`fetch`・`CompressionStream`・PostgREST | Deno だけ |

**型検査とテストが届く範囲を最大にする**のが目的である。`index.ts` はどの `tsconfig` にも入らないので型検査されないが、判断を含む部分は全部 `core.ts` に寄せてあるので、残るのは配線だけになる。

#### 認証は `CRON_SECRET`（W3-04a）

**`verify_jwt` を切る。** JWT で守ると、呼ぶ側（pg_cron）が**サービスロールキーを持つ必要があり、最も強い鍵を Vault に置く**ことになる。代わりに Vercel の Cron ハンドラと同じ `Authorization: Bearer <CRON_SECRET>` にする。比較は `apps/web/lib/jobs/auth.ts` と同じ規律で、**先に SHA-256 で固定長にしてから**定数時間で比べる（長さも漏らさない）。

> **W3-04 の「新しい秘密を 1 つも置かない」は言い過ぎだった。** ODPT のトークンは持たせない（そこが本題）が、**`CRON_SECRET` を Edge Function の秘密として 1 つ置く**必要がある。既に Vault と Vercel にある同じ値なので、影響範囲は増えない。

#### 起動条件は「発火したときだけ記録する」

`watchdog_collect` は毎分 `job_runs` に書くので 1 日 1,441 行になる。同じものをもう 1 本増やしたくない。そこで **`trigger_backup_collect` は停滞しているシステムが 1 つも無ければ何も書かずに戻る**（1 クエリで終わる）。

**するとその代わりに「動いているか」を見張れなくなる**ので、`monitor_jobs` に**検査 5：pg_cron のジョブが登録されていて active か**を足した。`monitored_jobs.cron_job_name` が指す `cron.job` を見るだけで、**行を 1 つも増やさずに「誰かが unschedule した」を捕まえる**。滅多に発火しないジョブや日次のジョブにも効く。

| 状態 | 記録 | 通知 |
|---|---|---|
| 停滞なし | **書かない** | なし |
| 発火した | `ok`（`fired`・`systems`） | `backup_collect_fired`（抑制 1 時間） |
| 設定漏れ（`cron_secret` / `functions_base_url`） | `failed`（`reason`） | `backup_collect_misconfigured`（抑制 6 時間） |

**設定漏れを通知するのが要点である。** 冗長系が無い状態が静かに続くのが一番まずい。

#### 設定値の置き場所

`functions_base_url`（Edge Function の宛先）は **マイグレーションに書かない**。`project_base_url`（0004）は利用者が叩く Vercel のドメインで公開されているが、Supabase のプロジェクト URL はどこにも公開していない。秘密ではないが、わざわざリポジトリに置く理由も無い。`scripts/setup-app-config.sh` が `.env` の `SUPABASE_URL` から導いて入れる。

`supabase functions serve` で**本物の ODPT を叩き、ローカルの Storage に保存し、`rebuild-snapshots.ts` で DB に戻すところまで**通した。

### 5.7 PR E：ポートの地理属性と近傍リスト

**目的**：`§6.3` の「ポート静的」と「近傍」の特徴量を作れるようにする。

**状態：完了（2026-09-08）。** 実装は下の「実装で変えたこと」のとおり、計画の TypeScript ＋ Vercel Cron から **SQL ＋ pg_cron** に変えた。

```
supabase/migrations/<ts>_0025_station_geo_and_neighbors.sql  # muni_codes（参照データ）＋ station_neighbors ＋ 3 関数 ＋ pg_cron
supabase/seed/muni_codes.csv                                 # 出典の原本（全国地方公共団体コード・総務省）
scripts/gen-muni-codes.py                                    # xlsx → CSV / マイグレーションの insert を生成
supabase/tests/0014_station_geo_and_neighbors.sql            # 44 検査
```

**実装で変えたこと（計画からの逸脱）**

計画は `apps/web/lib/jobs/{build-neighbors,parse-address}.ts` の純粋関数と日次 Cron `/api/jobs/build-geo` を置いていた。**両方の処理が「表と表の突き合わせ」そのもの**だったので、SQL に寄せた。

| | 計画 | 実装 | 理由 |
|---|---|---|---|
| 住所の解析 | TS の純粋関数 | `rebuild_station_geo()` | **一覧そのものが辞書**になる。正規表現が要らず、罠（§12 の 91）を構造的に踏まない。TS だと 20,742 件の住所と 1,917 件の一覧を関数に出し入れして 14,922 件の更新を書き戻すことになる |
| 近傍の構築 | TS の純粋関数 | `rebuild_station_neighbors()` | 20,741 点の自己結合で 106,438 行を作る。PostgREST 越しに出し入れすると往復が重く、Vercel の実行時間の上限が効いてくる |
| 起動 | Vercel Cron | pg_cron `30 19 * * *`（04:30 JST） | 入力も出力も DB の中で完結し、外部 API を叩かない。`refresh_station_activity`（0009、03:30 JST）と同じ形 |

**純粋関数としてのテスト容易性は失っていない。** 3 つの関数はどれも「表を読んで表を書く」だけで、外部 I/O を持たない。pgTAP がポートを数個だけ置いて全経路を確かめている（44 検査）。

**`public.muni_codes`（参照データ、1,917 行）**

```sql
create table public.muni_codes (
  muni_code integer primary key,     -- 上 5 桁。smallint では溢れる（与那国町 47382）
  pref_code smallint not null,
  pref_name text not null,
  muni_name text not null,
  constraint muni_codes_pref_matches_code check (pref_code = muni_code / 1000),
  constraint muni_codes_pref_range        check (pref_code between 1 and 47)
);
```

- **CSV ではなく DB の表で持つ。** CSV をジョブから読ませると Next.js の関数バンドルに同梱する設定（`outputFileTracingIncludes`）が要り、抜けると本番でだけ落ちる。参照データをマイグレーションに入れるのは 0004 と同じ形。CSV は出典の原本として `supabase/seed/` に残す（政府標準利用規約・出典明記）。
- 生成は `scripts/gen-muni-codes.py`。総務省の xlsx を**標準ライブラリだけ**で読む（zip ＋ XML。依存を増やさない）。`--out` で CSV、`--sql` でマイグレーションの `insert` を出す。
- 政令指定都市の区も 1 行として持つ（`muni_name` は「横浜市瀬谷区」の形）。

**住所 → `pref_code` / `muni_code`（`rebuild_station_geo()`）**

**正規表現を使わない。一覧への前方一致で、最も長い市区町村名を採る。**

1. 住所の先頭が一致する都道府県を選ぶ（47 通り。ここを挟まないと 20,742 × 1,917 の総当たりになる）
2. 都道府県名を除いた残りの先頭が一致する市区町村を、その都道府県の中から全部拾う
3. **`muni_name` が最も長いものを採る**（「横浜市」と「横浜市瀬谷区」の両方が当たる → 区を採る）
4. 当たらなければ **NULL のまま残す**。件数を `detail.unmatched` に出す（推測で埋めない）

**当たったポートだけを更新しない。全ポートを左外部結合で見て、当たらなければ NULL に戻す。** 当たった側だけ書くと、住所が消えたポートに**前回のコードが残る**。台帳から作り直す関数が前の値を持ち越すと、特徴量が静かに間違った地域を指す。2 回目は 1 行も書かない（冪等）ことと、住所を消すとコードも消えることを pgTAP で固定してある。

正規表現でやると必ず踏む罠が実データにある（§12 の 91）。ドコモには住所が無いので両方 NULL のまま。`region_id` を整数のカテゴリ特徴量として使う（W3-07a）。

**`station_neighbors`（106,438 行）**

```sql

  system_id text not null, station_id text not null,
  nb_system_id text not null, nb_station_id text not null,
  distance_m  smallint not null,
  same_system boolean  not null,
  primary key (system_id, station_id, nb_system_id, nb_station_id),
  constraint station_neighbors_distance_range check (distance_m between 0 and 500),
  constraint station_neighbors_not_self       check (system_id <> nb_system_id or station_id <> nb_station_id)
);
```

- 格子は **0.01 度**。緯度 0.01 度 = 1.11 km、経度 0.01 度は日本最北（北緯 43.1 度）でも 0.81 km なので、3 × 3 で 500 m は全方向を覆う。**5 × 5・7 × 7 と突き合わせて 800 m まで一致することを本番データで確認済み**（§10.2）。
- **格子は「展開してから等値結合」する**（§12 の 92）。範囲結合のままだと本番で 80 秒かかる。
- 距離は haversine。**外部キーを張らない**（毎日丸ごと作り直すので孤児が生じない）。
- 日次で全置換（W3-09）。`delete ... where true` を省かない（§12 の 88）。

**鮮度は `station_forecasts` で測る。`inference_log` では測らない。** 推論が毎回失敗していても `inference_log` には行が増えるので、そちらを見ると「新しい」に見えてしまう。見たいのは「**配信できる予測が新しいか**」であって「ジョブが動いたか」ではない。

**`generated_at` に索引は張らない。** `station_forecasts` は 5 分毎に全ポートを UPDATE し、HOT 更新率 100% で回っている。HOT が効くのは**索引の付いた列が変わらない**ときだけで、`generated_at` は毎周期変わる。**索引を足した瞬間に 100% が崩れる。** 20,464 行（10 MB）の全走査を 5 分に 1 度払うほうが安い。

**叩くのは「投げれば進むとき」だけ**（開発プラン §8.2 に足した条件）。予測が古い理由が「収集が止まっている」ことなら、`/ml/infer` を叩いても `begin_inference` が新しい `base_observed_at` を掴めず `skipped` を返すだけで、何も進まない。

|---|---|---|---|
| Vercel Cron の配信漏れ | ある | **叩く** | ここ |
| 収集の停滞 | ない | **叩かない** | `monitor_feeds` / `trigger_backup_collect` |
| 推論そのものの故障 | ある | 叩く（直らなければ 15 分で鳴る） | ここ |

**通知のほうは理由を問わない。** 「予測が 15 分古い」は利用者から見た症状で、原因が収集でも推論でも配信は等しく劣化する。1 通に材料（最終予測時刻・最終観測時刻・直近の推論の状態と `error`）を詰めて、**どちらの持ち場かが読み取れる**ようにした。

**叩いたこと自体も通知する**（抑制 6 時間）。12 分の停滞は「2 回続けて配信が漏れた」に当たり、滅多に起きない。黙って埋め合わせ続けると、**慢性的な配信漏れがウォッチドッグに隠れて気づけない**。

### 7.3 Parquet の `fetched_at`（PR B）

全期間を手元に落としてから、**2 通りの読み方で列が一致すること**を見る。

## 9. 付録：PR をまたぐ契約

ここは **PR をまたいで守る約束**を置く場所である。実装が変わったらここを直してから進む。**入力仕様の正は `docs/data_dictionary.md`（データ辞書）** で、ここに書くのは W3 で新しく決めるものだけ。

### 9.1 Parquet のスキーマ v2（PR B）

```
gbfs-parquet/{system_id}/date={YYYY-MM-DD}/hour={HH}/part.parquet   # 日時は UTC
```

| 列 | 型 | 意味 |
|---|---|---|
| `system_id` | string | `hellocycling` / `docomo-cycle` |
| `station_id` | string | 提供側の識別子。**`idx` は書かない**（W2-10） |
| `observed_at` | timestamp[ms, tz=UTC] | フィードの `last_updated` |
| **`fetched_at`** | **timestamp[ms, tz=UTC]** | **W3 で追加。**収集器が取得を終えた時刻。**as-of 結合はこの列で切る**。`observed_at` と同じ型・同じ精度 |
| `bikes` | int16 | `-1` は「観測されなかった」。0 と区別する |
| `docks` | int16 | 同上。HELLO の `-1`（定員超過）は収集時に 0 へ丸めてある（W1-25） |
| `flags` | int16 | `1 = is_installed` / `2 = is_renting` / `4 = is_returning` のビット和。`-1` は欠損 |
| `reported_age_s` | int16 | `last_updated − last_reported`。ドコモは恒常的に 0（＝情報が無い） |

**読む側の規約**

- **必ず `schema=SCHEMA` を渡す。** 渡さないと pyarrow が最初に見つけたファイルからスキーマを推論し、混在時に列を黙って落とす（§4.2 の 11）。
- **`schema=` を渡すとパーティション列（`date` / `hour`）が付かない**（§12 の 83）。要るなら `SCHEMA` に足した版を渡す。`observed_at` から導けるので、ふつうは要らない。
- **列数で比べない**（読み方で 8 にも 10 にもなる）。名前の集合で比べる。
- 1 つの JST 暦日を読むには、**UTC の `date=D-1/hour=15` から `date=D/hour=14` までの 24 個**を並べる（§4.2 の 14）。

**互換性**：v1（7 列）のファイルは PR B の再圧縮で全て v2 に置き換わる。**v1 と v2 が混在する期間を作らない。**

### 9.3 学習サンプルの契約（PR F）

**基準時刻 `t`**：JST 00:00 起点の 5 分グリッド。1 日 288 点。

**水平 `h`**：{5, 10, 15, 20, 30, 45, 60, 90, 120, 180} 分（`packages/shared` の `HORIZONS_MIN`）。

**as-of の規則**

| 用途 | 規則 |
|---|---|
| 特徴量（水準） | `fetched_at <= t` を満たす行のうち `observed_at` が最大のもの。**`t − observed_at > 600 秒` なら欠損** |
| ラベル | `observed_at <= t + h` を満たす行のうち最大のもの。同じく 600 秒の上限。**`fetched_at` では切らない**（未来の話なので「入手できたか」は問わない） |
| 流量 | フィード本来の周期のまま計算し、その結果を `t` に as-of する（W3-11） |

**ラベル**

```
y_bike(t,h) = 1[ bikes(t+h) >= 1 かつ is_renting(t+h) ]
y_dock(t,h) = 1[ docks(t+h) >= 1 かつ is_returning(t+h) ]
```

**除外規則**（開発プラン §6.1。`t` 時点で判定できるものだけ）

| 除外する | 条件 |
|---|---|
| フィードの欠損 | `t` または `t+h` の as-of 状態が無い |
| ポートが観測されていない | 値が `-1`（Parquet では行が在って `bikes = -1`） |
| 休止中のポート | `t` 時点の `flags` に該当ビットが立っていない（実質 `flags = 1`） |
| 実在しないポート | ドコモの `5753`（監視用。EDA #1） |
| **衝突** | **`as-of(t+h)` が `as-of(t)` と同じ観測を指す**（W3-12。実測 0 件） |

**`stations.is_active` で除外しない**（生存者バイアス）。**`capacity = 0` で除外しない**（ドコモの動的値）。**補間しない。**

**抽出と重み**

| 層 | 条件 | 抽出率 | 重み |
|---|---|---|---|
| 一様 | すべて | 1% | 100 |
| 難所 | `bikes(t) <= 2` または `docks(t) <= 2` | ＋3% | 100/4 = 25 |

- 抽出の乱数は `(date, system_id, station_id)` のハッシュから導く（決定的）。
- **2 回抽選しない。** 行ごとにハッシュを 1 つ作り、難所なら閾値 4%、それ以外は 1% で判定する。「一様に 1% 引いてから難所を 3% 足す」と独立抽選になり、包含確率が `1 − 0.99 × 0.97 = 3.97%` になって重みが厳密でなくなる。**1 回の判定なら重みはちょうど 25 と 100 になる。**
- **評価は重み付きで行う**（開発プラン §6.2）。重み無しの値も並べて出す。
- 難所の実測比率は 45.4%（HELLO・h=5・午前。**`bikes ≤ 2` だけ**）。定義どおり `docks ≤ 2` も or で入れると **83.9%** で、抽出後は **1 日 2,053,383 行**になった（見込みの 140 万に対し ＋47%。§12 の 99）。

**出力**

```
features/date={YYYY-MM-DD}/part.parquet    # JST の暦日
```

列：キー（`system_id`, `station_id`, `t`, `h`）、特徴量（§6.3）、ラベル（`y_bike`, `y_dock`）、`weight`、`stratum`、`feature_set`。

### 9.6 ベースラインの定義（PR G）

| ID | 定義 | 備考 |
|---|---|---|
| **B0** | `P = 1[ bikes(t) >= 1 かつ is_renting(t) ]`（dock も同様） | 0/1 の硬い予測。Brier ＝ 誤り率 |
| **B1** | `P̂(y=1 ∣ system, バケツ(t), h)` | 開発プラン §7.1 のまま。バケツは `{0, 1, 2, 3-5, 6-10, 11+}` で、**当てる対象と同じ側の台数**で切る（`y_bike` は `bikes`、`y_dock` は `docks`。§12 の 100）。**§6.1 の除外規則を適用した集合の上でだけ当てはめる**（W3-15） |
| **B2** | `P̂(y=1 ∣ station, dow_type, slot15(t+h))` | セルが下限に満たなければ B1 に落とす。下限は **2 行かつ 2 日**（**日数で数える**。行数だけだと 1 日で満たせる。§12 の 101）。**落とした割合を報告する**（W3-17） |
| **B3** | B1・B2 のロジットと `h` を入力とするロジスティック回帰 | 学習期間で当てはめ、検証期間で評価。**入力 3 つなので勾配法を自前で書く**（`scikit-learn` を足さない。W3-20） |

**評価集合の規約**：どのモデルも**同じ行**の上で測る。件数が違えば比較は無効（§4.4 の 30b）。B0 も検証期間だけで測る。

**合格基準**（開発プラン §7.1 を W3-16 で更新する）：LightGBM v1 は、**Brier ≥ 0.001 のすべての（水平, ターゲット, バケツ）**で B3 の Brier を 10% 以上改善し、ECE < 0.03。Brier < 0.001 のバケツは判定の対象外にする（相対改善が数値ノイズになるため）。満たさない（水平, バケツ）では B3 を配信する。

### 77. 予報の窓の狭さを測り直し、`forecast_days` を 3 に広げる（段 0）

> **この挙動そのものは既知である。** データ辞書 §8.2 が「取得時刻が遅いほど、前向きの予報時間は短くなる。JST 23 時に取ったファイルは 24 時間先までしか無い」と書いており、W2 プラン §9.4 も「先の覆いが時刻によって 23.7〜46.7 時間と変わる」「水平が 3 時間である限りどちらでも足り、変える理由が無い」として現状維持を選んでいる。**新しいのは、広げる費用と `jma_msm` の限界を実測したこと**である。

**Open-Meteo の `forecast_days` は「今日から数えた日数」であって「取得時刻から先の時間数」ではない。** 実測（13 時刻すべて）で、窓は取得時刻によらず **`2026-09-08T00:00` 〜 `2026-09-09T23:00`（JST・48 時間）で固定**だった。したがって**取得時刻から先の時間数は時刻とともに減る**。

| 取得（JST） | 窓 | 取得時刻から先の時間数 |
|---|---|---|
| 00:17 | 09-08 00:00 〜 09-09 23:00 | **48** |
| 06:17 | 同上 | 42 |
| 12:17 | 同上 | **36** |
| 23:17（見込み） | 同上 | **約 25** |

### 79. 予報の実更新は 1 日 4〜8 回。毎時取得は冗長だが必要（段 0）

同じ格子・同じ対象時刻の降水量が前の時刻から変わった割合を、12 の遷移すべてで測った。

| 遷移（JST） | 変わった割合 |
|---|---|
| 00→01 | 0.00% |
| 01→02 | **69.48%** |
| 02→03 | 0.00% |
| 03→04 | **53.03%** |
| 04→05, 05→06, 06→07 | 0.00% |
| 07→08 | **52.04%** |
| 08→09 | 0.00% |
| 09→10 | **51.32%** |
| 10→11, 11→12 | 0.00% |

**12 回のうち値が変わったのは 4 回**（02:00・04:00・08:00・10:00 JST）で、間隔は **2〜4 時間**。

**含意**：(1) 保存容量の 3〜6 倍は同じ内容の重複だが、`weather-raw` は 1 日 4.4 MB なので最適化する理由が無い。(2) **「3 時間毎に取れば十分」ではない**。観測された最短間隔は 2 時間なので、3 時間毎だと発行を取り逃す。**毎時のままにする。** (3) 特徴量 `precip_mm_fcst_target` は 1 日に 4〜8 回しか変わらない。これはモデルの入力の性質としてモデルカードに書く。

### 80. 天気のパスも UTC の日付。JST の 1 日は 2 つの日付プレフィックスに跨る（段 0）

`weatherObjectPath` は `gbfs-raw` と同じく **UTC の日付**でディレクトリを切る（W2 プラン §9.1）。したがって **JST の 09-08 の 13 時刻は `2026/09/07` に 9 個・`2026/09/08` に 4 個**に分かれて置かれる。

データ辞書 §7.2 は「日付・時刻は UTC」と書いており規約としては明記されている。**それでもこの検証で踏んだ**：JST の日付でパスを組み立てて **9 時刻ぶん（54 ファイル）が 400 で取れなかった**。§4.2 の 14（Parquet の `date=` / `hour=` は UTC）とまったく同じ落とし穴が**天気にも当てはまる**、と書いておかないと繰り返す。読み出しは必ず `storage.objects.name` か `weatherObjectPath` から組み立て、手で書かない。

### 81. `storage.objects` からは直接 DELETE できない（段 1）

pgTAP のテストは「自分の前提を自分で作る」ため、先に関係する表を空にしてから始める（0007 の作法）。**`storage.objects` だけはこれができない。**

```
ERROR:  Direct deletion from storage tables is not allowed. Use the Storage API instead.
HINT:   This prevents accidental data loss from orphaned objects.
CONTEXT: PL/pgSQL function storage.protect_delete() line 5 at RAISE
```

Supabase が `before delete` トリガで止めている（孤児オブジェクトを防ぐため）。**INSERT は通る**ので、テストは「消してから始める」ではなく**前提を表明してから始める**形にした。

```sql
select is(
  (select count(*)::int from storage.objects where bucket_id = 'gbfs-parquet'),
  0, '前提：ローカルの gbfs-parquet は空'
);
```

**運用への含意**：Storage のオブジェクトを消すには Storage API を通すしかない。CLAUDE.md §6 が「Storage バケットやオブジェクトの削除」を確認の要る操作に挙げているのと整合しており、**SQL でうっかり消せない**ようになっている。

### 82. 監視対象表に自分自身を入れると、適用直後に必ず誤報が出る（段 1）

`check_jobs_missing` は「直近 N のあいだ `status='ok'` が 1 件も無い」を見る。**適用直後はどのジョブも「この表に載ってから」は 1 度も成功していない**ので、9 件そろって鳴る。日次ジョブに至っては、次に回るまで最大 24 時間、正しく判断できない。

**`added_at` を持たせ、`now() > added_at + missing_after` になるまで見ない**ことで解決した。副作用として「新しく監視対象に足したジョブは、その閾値のあいだ盲点になる」が、これは**「まだ 1 巡していない」と「死んでいる」を区別できない**という事実そのものなので、正しい振る舞いである。

### 83. 明示スキーマを渡すとパーティション列が消える（段 2）

「混在で列が落ちる」を**いまの pyarrow（25.0.1）で再現**した。あわせて、`schema=` を渡す副作用が分かった。

古い 7 列のファイルと新しい 8 列のファイルを 1 つのディレクトリに置いて読む。

| 読み方 | 列数 | `fetched_at` |
|---|---|---|
| `ds.dataset(..., partitioning="hive")` | 9 | **★消える★**（エラーは出ない） |
| `ds.dataset(..., partitioning="hive", schema=SCHEMA)` | 8 | あり。ただし**古いファイルの行が `null`** |

畳み直したあと（両方 8 列）。

| 読み方 | 列数 | `fetched_at` |
|---|---|---|
| `ds.dataset(..., partitioning="hive")` | **10** | あり・`null` 0 |
| `ds.dataset(..., partitioning="hive", schema=SCHEMA)` | **8** | あり・`null` 0 |

**新しく分かったのは下の行**である。**`schema=` を渡すと `date` / `hour` のパーティション列が付かない**（10 ではなく 8）。明示スキーマがパーティション探索より優先されるためで、「必ず `schema=SCHEMA` を渡す」という規約と「Hive で読むと列が 2 つ増える」という記述は**同時には成り立たない**。

**含意**：`date` / `hour` を列として使いたいなら、`SCHEMA` にその 2 つを足した版を渡す。ただし `observed_at` から導けるので、ふつうは要らない。**「列数で比べる」検査はどちらの読み方でも書けない**（8 にも 10 にもなる）ので、名前の集合で比べる。データ辞書 §7.3 を直した。

### 84. Storage の REST API は重複を **HTTP 400** で返す（段 3）

`upsert: false` で既にあるパスに PUT したときの生の応答（実測 2026-09-08）。

```
HTTP/1.1 400 Bad Request
{"statusCode":"409","error":"Duplicate","message":"The resource already exists",
 "code":"KeyAlreadyExists"}
```

**409 は本文の中にあり、しかも文字列である。** HTTP ステータスだけを見ると「重複」が「想定外の失敗」に化け、**毎回 500 を返して `job_runs` が `failed` で埋まる**。実際にローカルで踏んだ（`{"phase":"storage","http_status":400,...}` で `failed` が 1 行残っている）。

`apps/web/lib/jobs/storage.ts` が `statusCode` を string / number の両方で読んでいるのは同じ理由（supabase-js が本文の値をそのまま載せる）。**あちらは supabase-js 越しなので気づけたが、REST を直接叩く Edge Function では自分で見に行く必要がある。**

判定は `core.ts` の `isDuplicateUpload(http_status, body)` に閉じ、5 件のテストで固定した。**本当の失敗（403・413・500）を重複と読み違えない**ことも一緒に固定してある。

### 85. `verify_jwt` を切る判断（段 3）

Edge Function を JWT で守ると、**呼ぶ側（pg_cron）がサービスロールキーを持つ必要がある**。Vault に置くことになり、**最も強い鍵の置き場所が 1 つ増える**。

代わりに Vercel の Cron ハンドラと同じ `Authorization: Bearer <CRON_SECRET>` にした。`CRON_SECRET` は既に Vault（ウォッチドッグ用）と Vercel にある同じ値で、**Edge Function の秘密として置き場所が 1 つ増えるだけ**である。鍵の強さで比べれば明らかにこちらが軽い。

**W3-04 の「新しい秘密を 1 つも置かない」は言い過ぎだった。** ODPT のトークンを持たせない（規約の例外を作らない）のが本題で、そこは達成している。

### 86. 監視対象の表への入れ忘れが、そのまま盲点になっていた（段 3 の適用後）

段 3 を本番に入れたあと、pg_cron のジョブと `monitored_jobs` を突き合わせて気づいた。

```sql
select c.jobname from cron.job c
 where not exists (select 1 from public.monitored_jobs m where m.cron_job_name = c.jobname);
-- → daily_quality
```

**`daily_quality`（毎日 07:00 JST の品質集計）が監視されていなかった。** §5.3 の表には書いてあったのに、0020 の `insert` から抜けていた。成功の有無も pg_cron への登録も見ていないので、**静かに止まっても気づけない**。

**問題は 1 行足りないことではなく、足りないことに気づけない仕組みだったこと。** 0021 の `check_cron_jobs` は「**知っているジョブがまだ登録されているか**」しか見ておらず、逆向き——「**登録されているのに知らないジョブ**」——を見ていない。だから表への入れ忘れがそのまま盲点になる。

0022 で両方向にした。

| 向き | 何を捕まえるか | 鍵 | 抑制 |
|---|---|---|---|
| ① 表 → cron | 知っているジョブが外された・無効にされた | `cron_job_missing:<name>` | 3 時間 |
| ② cron → 表 | **登録されているのに監視していない**（入れ忘れ） | `cron_job_unmonitored:<name>` | 24 時間 |

pgTAP には「**pg_cron のジョブに監視の抜けが無い**」を不変条件として足した。次に cron ジョブを増やして表に入れ忘れたら、テストと本番の両方で鳴る。

**この見つけ方自体が段 1 の理屈の実例になっている。** 「失敗を探す」検査は、そもそも対象に入っていないものを見つけられない。**在るべきものの一覧と、実際に在るものを突き合わせる**必要がある。

### 87. 年末年始とお盆を表に持たせると、優先順の決着がつかなくなる（段 4）

プラン §9.5 は `jp_holidays.kind ∈ {statutory, newyear, obon}` を持つ設計だった。**実装しようとして詰まった。**

`holiday_date` が主キーなので 1 日 1 行しか持てない。ところが **2026-01-01 は「元日（statutory）」でもあり「年末年始（newyear）」でもある**。振替休日が 1/2 や 1/3 に落ちる年もある（1/1 が日曜のとき）。どちらの `kind` を残すかを決めないと入れられない。

**そもそも年末年始（12/29〜1/3）とお盆（8/13〜16）は暦の規則で、データではない。** 表に持たせるのをやめたら、この問題ごと消えた。

|---|---|
| 内閣府 CSV の `(holiday_date, name)` | 年末年始・お盆・飛び石・月末営業日 |

### 88. `DELETE` に `WHERE` が無いと PostgREST 経由で弾かれる（段 4）

`replace_jp_holidays` の中に素直に `delete from public.jp_holidays;` と書いたら、RPC が 400 を返した。

```
21000  DELETE requires a WHERE clause
```

Supabase は PostgREST の接続ロール（`authenticator`）に **`session_preload_libraries = supautils, safeupdate`** を設定していて、`WHERE` の無い `DELETE` / `UPDATE` を止める。**`security definer` でもセッションの設定なので効く。**

`where true` を足せば通る。**pgTAP では再現できない**（`postgres` で動くので safeupdate が載っておらず、`LOAD 'safeupdate'` は許可されていない）ので、代わりに**関数の本文に `delete from public.jp_holidays where` があること**をテストで見張る。

> **気づけたのは、スクリプトがエラー本文を出していなかったのを直したから。** 最初は「HTTP 400」としか出しておらず、「行が少なすぎる」のか「関数が無い」のか分からなかった。**PostgREST のエラー本文は自分たちのエラー文なので、そのまま出してよい。**

### 89. 内閣府の CSV に条件付き取得は効かない（段 4）

プラン §5.6 は「`etag` / `last-modified` で条件付き取得（実測でどちらも返る）」としていた。**「ヘッダが返る」ことは確かめたが、「条件付き取得が効く」ことは確かめていなかった。**

| 送ったもの | 応答 |
|---|---|
| `If-None-Match: "5422-649cc6d5b61b9"` | **200**（304 ではない） |
| `If-Modified-Since: Mon, 02 Feb 2026 00:30:17 GMT` | **200** |

しかも**同じファイルなのに ETag が要求ごとに変わる**。

```
etag: "5422-649cc6d5b61b9"
etag: "5422-649cc6d5b61b9"
etag: "5422-649cc6d5b46cb"   ← 3 回目で別の値
```

サイズ（5422）は同じで後半だけが違う。負荷分散された別のサーバが別の mtime を持っているのだろう。**ETag では原理的に一致しない。**

そこで**中身の SHA-256 を自分で持って比べる**。21 KB のダウンロードは毎回払うが、それだけである。`app_config.holidays_sha256` に入れ、同じなら RPC を呼ばない。

### 90. 本番では関数の EXECUTE が `service_role` に既定で付かない（段 4 の適用後）

`db push` のあと `import-holidays.ts` を本番で流したら、**ローカルでは通っていたのに** 403 になった。

```
42501  permission denied for function replace_jp_holidays
```

0006 の冒頭が「本番プロジェクトは『新規オブジェクトの自動公開』を OFF にしてある。この設定は `anon` / `authenticated` だけでなく **`service_role` の既定権限も剥奪する**」と書いていた、まさにその罠である。**ただし 0006 は表とシーケンスにしか手当てをしていなかった。**

```
pg_default_acl（本番）
  postgres / r（表）   → {postgres=arwdDxtm/postgres, service_role=arwdDxtm/postgres}
  postgres / f（関数） → {postgres=X/postgres}          ← service_role が無い
```

だから `jp_holidays` と `v_weather_files` は読めるのに、`replace_jp_holidays` だけ呼べなかった。既存の 10 個（`ingest_snapshot`・`job_started` ほか）はすべて明示的に `grant execute` してあり、**0023 で足した 1 つだけ忘れていた**。

**ローカルでは既定権限が違うので再現しない。** `has_function_privilege` で見るテストを書いても、ローカルだけ通って本番で落ちる。そこで**「明示的な grant があること」を `proacl` の中身で見る**不変条件を 0003 に足した。

| 検査 | 何を守るか |
|---|---|
| PostgREST から呼ぶ 11 関数に `service_role=X` がある | 本番で 42501 にならない |
| **どちらにも分類されていない関数が無い** | 新しい関数を足したら、必ずどちらかに分類させる |

grant を剥がすと 1 件目が実際に落ちることを確かめてある。

**この形の抜けは 0006 の時点から仕組みとして残っていた**（「毎回書く」という約束だけで守られていた）。分類を強制する 2 つ目の検査があれば、次に関数を足す人は考えざるを得ない。

### 91. 住所の解析を正規表現でやると、実データが必ず罠を踏む（段 5）

計画（§4.3 の 19）は「都道府県は 47 件の完全一致、市区町村は総務省の表と突き合わせる」と書いていたが、**突き合わせ方**を決めていなかった。素直に書くと「市区町村名らしき部分を正規表現で切り出してから表を引く」になる。これは通らない。

| 住所 | 素朴な正規表現 | 切り出される | 正しい |
|---|---|---|---|
| 愛知県蒲郡市西浦町… | `.+?郡.+?[町村]` | 蒲郡市西浦町 | 蒲郡市 |
| 奈良県大和郡山市… | 同上 | （郡を跨いで誤爆） | 大和郡山市 |
| 東京都東村山市本町… | `.+?[市区町村]` | 東村 | 東村山市 |
| 東京都武蔵村山市… | 同上 | 武蔵村 | 武蔵村山市 |
| 東京都羽村市… | 同上 | 羽村 | 羽村市 |
| 広島県廿日市市… | 同上 | 廿日市 | 廿日市市 |
| 大阪府寝屋川市… | 同上 | 寝屋川市 | 寝屋川市（たまたま合う） |

「郡」「村」「市」が**地名の内側に出る**のが原因で、後読みや最短一致をいくら足しても例外表が育つだけになる。

**表そのものを辞書として使えば、切り出しが要らない。** 都道府県で 47 通りに絞ってから、残りの先頭が一致する市区町村を**全部**拾い、`muni_name` が最も長いものを採る。「横浜市」と「横浜市瀬谷区」の両方が当たるので、長いほう（区）が勝つ。上の 7 件はすべて正しく当たる。

**本番データ 14,922 件すべてが当たった（未一致 0 件、357 市区町村、0.87 秒）。** pgTAP に上の 7 件と「壊れた小豆島町の住所」を入れて固定してある。

**教訓は「文字列を切ってから照合する」の順序が逆だということ。** 照合先の一覧を持っているなら、切らずに前方一致させれば、一覧が正解の定義そのものになる。

### 92. 格子の範囲結合はハッシュ結合にできず、本番で 47 倍遅くなる（段 5）

`rebuild_station_neighbors()` の最初の版は、3 × 3 の格子を素直に範囲で書いていた。

```sql
join pts r on r.gy between l.gy - 1 and l.gy + 1
          and r.gx between l.gx - 1 and l.gx + 1
```

ローカル（ポート数個）では一瞬で終わる。**本番の 20,741 ポートで 80.45 秒かかった。** 不等号の結合条件はハッシュ結合にもマージ結合にもできず、20,741 × 20,741 の入れ子ループになる。

左側を 9 行に展開して、格子キーを**等値**にすると解ける。

```sql
probes as (
  select p.*, p.gy + dy as key_gy, p.gx + dx as key_gx
    from pts p, generate_series(-1, 1) dy, generate_series(-1, 1) dx
)
...
join pts r on r.gy = l.key_gy and r.gx = l.key_gx
```

**80.45 秒 → 1.70 秒（47 倍）。** 結果は 1 行も変わらない（106,438 ペア、候補 978,756）。触るペアの数は同じで、突き合わせ方だけが変わる。左の行数が 9 倍になるのは、ハッシュ結合が使えるようになる対価としては安い。

**この契約はローカルでは検知できない。** ポートが数個しか無いので、範囲結合に戻しても pgTAP は同じ速度で通ってしまう。そこで**速度ではなく関数の定義そのものを固定した**（`prosrc` に `r.gy = l.key_gy` があり `between l.gy` が無いこと）。§12 の 88 で `delete ... where true` を同じ形で固定したのと同じ理由である。

**副作用として、関数本文のコメントにも同じ検査がかかる。** 最初はコメントに旧式の `r.gy between l.gy - 1 …` を引用していて、自分の検査に引っかかった（`prosrc` はコメントを含む）。コメントは式を引用せず日本語で説明する形に直した。

### 93. 一度きりの計測スクリプトを残さないと、実装と食い違ったときに追えない（段 5）

§10.2 の近傍の分布は、着手前に Python で測って **97,822 ペア（500 m）** と記録していた。段 5 で SQL に実装したら **106,438 ペア**になった。300 m（39,488 → 42,950）も 800 m（229,222 → 250,606）も、**全半径で約 8% 低い**。

どちらが正しいかは決着した。SQL 側は

- 格子を 3 × 3 / 5 × 5 / 7 × 7 と変えても値が動かない（800 m まで完全一致）
- 距離は pgTAP が手計算値（91 / 489 / 511 / 22 m）で固定している

ので、**低かったのは Python の見積りのほう**である。しかし**なぜ低かったのかは分からない**。あの計測は「その場で書いて捨てた」スクリプトで、リポジトリに残していなかった。

残っている手がかりから、点を `station_id` だけで持ったのではないかと疑っている。`station_id` の異なり数は **18,133** で、ポート数 20,741 より **2,608 少ない**（HELLO とドコモで ID が衝突している）。辞書のキーにすれば静かに潰れる。ただし潰れ方が地理的に偏るので、8% という数字までは再現できていない。

**計測スクリプトは、その数字が設計判断（W3-08）の根拠になる以上、コードと同じ資産である。** 今回は結論（PostGIS を入れない）が変わらなかったので実害は無かったが、**「桁が違う」側に外れていたら設計を間違えたまま進んでいた**。段 5 以降の計測は `scripts/` に残す。

**このプランに書いた実測値は、実装後に必ず測り直す。** 着手前の値は見積りであって、実装が出す値ではない。

段 5 では次の 2 つを残した。

### 94. `job_runs` の所要時間が、pg_cron のジョブでは必ず 0 秒になる（段 5 の適用後）

`rebuild_geo()` は本番で 4.38 秒かかった（`\timing` で計測）。ところが `job_runs` の記録は

```
started_at = finished_at   →   所要 0.00 秒
```

になっている。`job_started` / `job_finished`（0009）が **`now()`** を使っているためで、Postgres の `now()` は**トランザクション開始時刻で固定**される。pg_cron のジョブは 1 トランザクションで走るので、開始と終了が同じ値になる。

| ジョブ | 起動 | 直近 2 日の平均所要 |
|---|---|---|
| `archive_weather` | Vercel Cron | 4.07 秒 |
| `compact_parquet` | Vercel Cron | 3.52 秒 |
| `sync_stations:hellocycling` | Vercel Cron | 3.46 秒 |
| `watchdog_collect`（2,767 回） | pg_cron | **0.00 秒** |
| `monitor_feeds`（556 回） | pg_cron | **0.00 秒** |
| `rebuild_geo` | pg_cron | **0.00 秒** |

Vercel 側は `job_started` と `job_finished` が**別のリクエスト＝別のトランザクション**なので実測値が入る。差が出ているのはそのためで、pg_cron 側だけが 0 になる。

**`job_finished` の `now()` を `clock_timestamp()` に変えれば直る**（`started_at` はトランザクション開始のままで正しい）。13 系統が使う共有関数なので**別 PR にした**（0028。段 9 のあと）。

本番で測り直すと、13 系統は**壊れている 7 と、元から正しい 6** にきれいに割れていた。

| 呼び出し経路 | ジョブ | 行数 | 所要 |
|---|---|---|---|
| **pg_cron の中**（関数の呼び出し全体が 1 トランザクション） | `watchdog_collect` / `monitor_feeds` / `monitor_jobs` / `maintain_partitions` / `refresh_station_activity` / `daily_quality` / `rebuild_geo` | 2,697 | **全行きっかり 0 ms** |

機構は本番サーバーで直接確かめた。`now()` はトランザクション開始時刻で、何秒はたらいても動かない（時刻はサーバーの UTC）。

**これでも測れないもの**

### 96. Storage は「オブジェクトが無い」も HTTP 400 で返す。404 の判定は一度も効いていなかった（段 6）

### 97. 明示スキーマは「無い列を null で作る」。パスで引くキャッシュが古い形を返す（段 6）

データ辞書 §7.3 に「読む側は必ず明示スキーマを渡す」と書いた（§12 の 83）。段 6 で、その規則の裏側を踏んだ。

```python
pq.read_table(body, schema=SCHEMA)   # fetched_at が無いファイル → fetched_at が全行 null
```

明示スキーマは**余分な列を落とす**ためのもので、**無い列を作る**ためのものではない。ところが pyarrow は足りない列を黙って null で埋める。`fetched_at` が全行 null になると、as-of が全滅しているのに例外も警告も出ない（気づいたのは numpy の `invalid value encountered in cast` という間接的な警告だった）。

**なぜ古い形のファイルを読んだのか。** `analysis/eda_01.py` と同じ `.cache/parquet` を使い回していて、そこには **EDA #1 のときに落とした 7 列のファイル**が残っていた。段 2 の畳み直しは**同じパスの中身を差し替える**ので、パスで引くだけのキャッシュは前の形を返し続ける。

| | 中身 | 作られた時刻 |
|---|---|---|
| `.cache/parquet/…/hour=00/part.parquet` | **7 列** | 2026-09-08 10:17（畳み直しの前） |
| Storage の同じパス | 8 列・`fetched_at` の null 0 | 2026-09-08 12:xx（畳み直しの後） |

直したのは 2 つ。

1. `read_table(body, where)` が**ファイル自身の列**を先に見て、契約と違えば `SchemaMismatchError` で止める
2. キャッシュは**読む前に形を確かめ、違えば捨てて取り直す**

**「同じパスの中身が変わる」設計にした以上、パスはキャッシュのキーとして不十分だった。** 畳み直しは費用の面では正しい判断（§5.4）だが、その副作用がここに出た。

### 98. HELLO の as-of は**常に約 205 秒古い**（段 6）

2026-09-07 の 1 日ぶんを本番データで作り、`feed_delay_s`（`t − observed_at`）を見た。

### 99. 難所を「`bikes ≤ 2` または `docks ≤ 2`」にすると 84% になり、層化がほとんど効かない（段 6）

W3-14 と開発プラン §6.2 は、難所を **`bikes(t) <= 2` または `docks(t) <= 2`** と定義している。実装して 1 日ぶんを作ったところ、

### 100. B1 の条件は、当てる対象と同じ側の台数で切る（段 7）

§9.6 は B1 を

    P(y=1 | system, bikes_bucket(t), h) の推定値

と書いている。これは**貸出側の式**で、返却側（`y_dock`）にそのまま当てると「**返せるか**を**借りられるか**で説明する」ことになる。台数と返却枠は `capacity` を挟んで逆向きに動くので、`bikes` のバケツは `y_dock` の条件としてはほとんど働かない。

**当てる対象と同じ側で切る**：`y_bike` は `bikes`、`y_dock` は `docks`。§10.1 の実測（HELLO・y_dock・h=180 で +15.4%、y_bike の +14.0% とほぼ同じ大きさ）も、この読み方でないと説明がつかない。`bikes` で切っていれば `y_dock` の改善はもっと小さかったはずである。

pgTAP ならぬ pytest でこれを固定した：`bikes` が同じで `docks` が違う 2 行を置き、`docks` で条件づけていれば両方当たり、`bikes` で条件づけていれば 0.5 になる、という形にしてある。

**式を 1 つ書いて 2 つの対象に使い回すときは、対称性を明示する。** §9.6 の表記を「当てる対象と同じ側の台数」に直した。

### 101. 気候値のセルの下限は「行数」ではなく「日数」で数える（段 7）

W3-17 は「セルのサンプル数が下限未満なら B1 に落とす」と決め、下限を **2 サンプル**にした。理由は「1 サンプルの平均は 0 か 1 になり、気候値ではなく**その日の観測そのもの**になる」から。

**行数で数えると、この意図が守れない。** 1 つの基準時刻に 10 の水平があるので、`t + h` が同じ 15 分枠に落ちる行が**同じ 1 日から複数入る**。実測（学習 1 日・693,525 行）：

```
下限 2 行を満たすセル              176,331
そのうち寄与した日が 1 日のセル    176,331   ← 全部
セルあたりの行数の分布             2 行 121,525 / 3 行 41,583 / 4 行 10,587 / 5 行 2,252 …
```

**「2 サンプル」はすべて同じ日の、ほぼ同じ観測を別の `(t, h)` から見たものだった。** 気候値は「別の日にも同じことが起きるか」なので、日をまたいでいないセルは使ってはいけない。

**この誤差は静かに効く。** B2 が使う 0.4% のセルは「9/06 のその時刻にどうだったか」をそのまま返し、B3 がそれを混ぜて短い水平で B1 に負けていた（下の 102）。

**下限を `(行数 >= 2) かつ (日数 >= 2)` に変えた。** 学習が 1 日のいまは B2 が 100% 落ち、B2 ＝ B1 になる。**これは正しい姿である**：日数が足りないときに気候値を名乗らせない。

### 102. B3 が短水平で B1 に負けた原因を切り分ける（段 7）

最初の実測で、**B3 が 40 の（system, ターゲット, 水平）のうち 23 で B1 に負けた**。しかも負けたのは短い水平ばかりで、長い水平では勝っていた。3 つの仮説を順に潰した。

| 仮説 | 確かめ方 | 結果 |
|---|---|---|
| (a) 学習期間の B1・B2 が「自分の答えを見た」推定なので、B3 が両者を信じすぎる | 入力を leave-one-out で作り直す | 23 → 22 件。**ほぼ効かない**（B1 のセルは 1 セルあたり数千行あり、1 行抜いても動かない） |
| (b) B3 の係数が水平をまたいで共有されるので、短い水平に合わない | 水平ごとに当てはめて比べる | **むしろ悪化**（h=5 で 0.00877 → 0.00910）。学習の行数が 10 分の 1 になるほうが効く |
| (c) **B2 を混ぜること自体が害** | 入力を `logit(B1)` だけにして比べる | **これだった。** h=5 で 0.00877 → 0.00819 と、B1（0.00823）を下回った |

原因は 101 で、B2 の「使えるセル」が 1 日ぶんの観測そのものだったこと。**日数で下限を切ったら 23 → 6 件になり、残る 6 件もドコモの `dock` の 0.1〜0.5 ポイントの差**に収まった。

**切り分けの手順そのものを残しておく価値がある。** (a) は書いた本人がいちばん疑わしいと思った仮説で、実際 `blend.py` の docstring に「まずこれを疑え」と書いていた。**書いた人の直感は当てにならない。3 つとも測った。**

leave-one-out は効かなかったが**外していない**：日数が増えれば B1 のセルは細かくなり、そのとき効いてくる。**測って効かなかったものを消す**のは、効く条件が分かっているときは早すぎる。

### 103. PostgREST 越しにアドバイザリロックは効かない。掴むのは一意制約（段 8）

開発プラン §8.2 は推論の同時実行について

> `inference_log` に unique (system_id, base_observed_at)。同じスナップショットに対する二重推論はスキップ。`pg_try_advisory_lock('infer:' || system)` で同時実行を抑止

と書いている。**後半は PostgREST 経由では成り立たない。**

| ロックの種類 | PostgREST 越しに何が起きるか |
|---|---|
| `pg_try_advisory_xact_lock` | RPC が返った時点でトランザクションが終わり、**解放される** |
| `pg_try_advisory_lock`（セッション） | 接続はプールに返る。**次に誰がその接続を掴むか決まらない**ので、解放も持続も当てにできない |

`jobs/compact.py` は W2 で同じ結論に達していて、「構造で冪等にする」（同じ時間帯は同じパスに上書き）を選んでいた。推論も同じで、**掴むのは「`inference_log` に行を 1 つ入れられたか」**にする。

```sql
insert into public.inference_log (system_id, base_observed_at, model_version)
values (...) on conflict (system_id, base_observed_at) do nothing returning id;
```

入れられたら掴めた、入れられなければ誰かがやっている。**接続をまたいで正しく効き、Vercel Cron の二重起動が無害になる。** 開発プラン §8.2 の記述を直した（v1.19）。

**ロックが要るように見えたのは、「同じことを 2 回やらない」を「同時に走らせない」と読み替えていたから。** 欲しいのは前者で、それは一意制約そのものである。

### 104. 成果物の丸めが、標準化の分母を 0 にした（段 8）

B3 は入力を標準化してから勾配法で降りる（`blend.py`）。係数と一緒に**平均と標準偏差**を持ち回り、配信でも同じ変換を使う。

成果物を書き出すとき、確率を 6 桁で丸めていた。B2 のセルが数百万になり得るので、桁を落とさないと JSON が膨らむ。**同じ関数で標準偏差も丸めていた。**

学習期間で `logit(B2)` がほとんど動かないと、標準偏差は `1e-9` の桁になる。`round(1e-9, 6)` は **0.0**。読み直したモデルは `(x - center) / 0.0` を計算し、`RuntimeWarning: divide by zero` を出しながら `inf` を返した。

**確率が pytest の警告に出るまで気づかなかった。** 予測は `nan` にはならず（`sigmoid(inf) = 1`）、テストの assert も通っていた。

直したのは 2 か所。

1. `blend.fit` が標準偏差に**下限**（`1e-6`）を置く。それより散らばりが小さい列は「動いていない」とみなして 1 で割る（中心を引けば 0 になるので害が無い）
2. 成果物は**係数を丸めない**。4 つずつしか無い。丸めるのは数が多い B1・B2 の確率だけ

**「数が多いから丸める」を、数が少ないものにも当てはめてしまった。** 丸める理由は大きさで、係数には当てはまらない。

### 105. 「全水平で気候値が効いた」を confidence 3 にすると、ほぼ出ない（段 8）

`station_forecasts.confidence` は 0〜3 で、UI が「どれだけ信じてよいか」を示すのに使う（W4）。最初は

> 3: **すべての水平**で気候値のセルが引けた

と定義した。気候値のセルは**水平ごとに違う 15 分枠**を引く（`slot15(t + h)`）ので、10 個そろうには 10 枠すべてに 2 日以上の実績が要る。

本番データで測ると、**14,663 ポート中 40 しか 3 にならなかった**（0.27%）。3 日ぶんの蓄積では、セルの充足率が 10.6%（629,025 / 593 万）で、その 10 乗はほぼ 0 になる。

**「過半の水平で効いた」に変えたら 31% になった。**

| 基準時刻 | confidence 3 の割合（全水平） | （過半） |
|---|---|---|
| 02:04 JST | 0.3% | **33.9%** |
| 10:04 JST | 0.3% | 31.5% |
| 19:04 JST | 0% | 0%（9/08 の収集範囲外） |

蓄積が伸びればどちらの定義でも 3 に近づくが、**いま信号として使えるのは過半のほう**である。0% と 31% では、UI が出す「参考」と「高」の意味が変わる。

**閾値は「いつか正しくなる」ではなく「いまの蓄積で信号になるか」で決める。** 蓄積が伸びたら測り直して、必要なら厳しくする。

### 106. モデルの置き場所を作っていなかった（段 8 の適用後）

`db push` の次に成果物を上げようとしたら、Storage が 415 で弾いた。

### 107. 地図が自分から再取得しない。5 分で灰色になったまま戻らない（段 9）

段 9 の確認のためシミュレータを立ち上げたまま数分放置したら、**全部のピンが灰色になった**。

```
起動直後   154 件・1 分前の観測      … 緑・橙・青・赤
7 分後     154 件・7 分前の観測      … ほぼ全部が灰色
```

灰色は「鮮度が切れていて現在値として出せない」を表す色で、**判定そのものは正しい**。ドコモの閾値は 303 秒なので、5 分を超えれば灰色になる。

問題は**戻らない**ことである。`MapScreen` は 30 秒ごとに `now` を進めるだけで、**再取得しない**。

```swift
// MapScreen.task
while !Task.isCancelled {
    try? await Task.sleep(for: .seconds(Self.tickSeconds))
    now = Date()          // ← 時刻だけ進む
}
```

再取得が起きるのは `.onMapCameraChange(frequency: .onEnd)`、つまり**地図を動かしたときだけ**。**画面を開いたまま待っている利用者には、データが古くなっていく様子だけが見える。**

`StationsModel.reloadCurrent()`（「明示的な再取得（引っぱって更新など）」）は W2 で作ってあり、テストもある。**どこからも呼ばれていない。**

**段 9 の範囲外だったので、別 PR で直した**（§5.11 で「地図の再設計はしない」と決めていた）。

`StationsModel.refreshIfDue(interval:)` を足し、`MapScreen` の刻みから呼ぶ。**間隔は 60 秒**：`/v1` の CDN キャッシュが `s-maxage=60` なので、それより短く投げても同じ本文しか返らない。いちばん厳しい鮮度の閾値はドコモの 303 秒なので、60 秒あれば灰色になる前に取り直せる。

**取り直しは「静かに」行う。** `loading` にせず、失敗しても前の値を消さない。取れなければ表示はそのまま古くなり、**鮮度の表示がそれを伝える**。一瞬の失敗で「通信に失敗しました」を出したり消したりするより、「N 分前の観測」が伸びていくほうが正しく伝わる。明示的な再取得（`reloadCurrent`）はいままでどおり失敗を出す。

| | 直す前 | 直したあと |
|---|---|---|
| 起動直後 | 154 件・1 分前の観測 | 154 件・1 分前の観測 |
| **6〜9 分後** | **9 分前の観測・ほぼ全部が灰色** | **2 分前の観測・全部が色付き** |

**「作ったが呼んでいない」は、テストが通っているぶん見つけにくい。** `reloadCurrent()` には単体テストがあり、緑のままだった。**画面を放置するという使い方をしなかった**だけである。

### 108. `.task` に閉じ込めた `@Environment` は、開始時の値のまま固まる（所見 107 の修正中）

107 を直すとき、背面では取りに行かないよう `scenePhase` で囲った。

```swift
.task {
    while !Task.isCancelled {
        try? await Task.sleep(for: .seconds(30))
        now = Date()
        if scenePhase == .active { model.refreshIfDue() }   // ← 一度も真にならなかった
    }
}
```

**シミュレータで 8 分放置しても、一度も取り直さなかった。** `now` は進んでいた（「9 分前の観測」まで伸びた）ので、ループ自体は生きている。つまり `scenePhase == .active` が偽のままだった。

**`.task` の中身は、開始した時点の View の値を捕まえている。** SwiftUI の View は値型で、`body` が評価されるたびに作り直される。`@Environment` はその評価のときに解決されて構造体に入るので、**走り続けているクロージャが見ているのは「タスクを始めたときの View」に入っていた値**である。あとから場面が変わっても、そこは動かない。

`simctl launch` はシミュレータのウィンドウが前面でないときにも起動できる。そのとき最初の `scenePhase` は `.active` ではなく、**それが固定された。**

直し方は `id:` を付けること。**場面が変わるたびにタスクを作り直す**ので、中で見る値は常にいまのものになる。

```swift
.task { model.viewportChanged(to: Bbox(region: MapScreen.initialRegion)) }   // 最初の 1 回
.task(id: scenePhase) {
    guard scenePhase == .active else { return }
    while !Task.isCancelled {
        now = Date()
        model.refreshIfDue()       // 前面に戻った直後にも 1 度試すよう、眠る前に呼ぶ
        try? await Task.sleep(for: .seconds(30))
    }
}
```

最初の読み込み（`viewportChanged`）は別の `.task` に分けた。`id:` の付いたほうに入れると、場面が変わるたびに**初期表示の矩形**を取りに行き、利用者が動かした地図と喧嘩する。

**この種の間違いは、テストでは捕まらなかった。** 判断（`refreshIfDue`）は `BikeChanceCore` にあって 11 件の検査が通っており、壊れていたのは**それを呼ぶ側の配線**である。**画面を 8 分放置するという使い方をして初めて出た。**

### 109. 貸出も返却も止まったポートの予測が、消えずに残り続ける（段 8 の運転で判明）

11 時間の運転を点検していて、**`station_forecasts` の全行が最新周期で更新されていない**ことに気づいた。

```
直近 1 周期    14,436 件    09-09 07:29
6 時間以内          1 件    09-09 01:59
6 時間より前      198 件    09-08 20:29 〜 09-09 00:59   ← 最古は 11 時間前
```

最初は「フィードから消えたポートだろう」と思った。**違った。199 件はすべて `station_status_latest` に居り、台帳でも `is_active` だった。**

原因は `flags` である。

| `flags` | 意味 | HELLO | 推論 |
|---|---|---:|---|
| `7` | 設置 ＋ **貸出可** ＋ **返却可** | 14,436（96.7%） | 出す |
| `1` | 設置のみ（**貸出も返却も止まっている**） | 492（3.3%） | **出さない** |

`is_predictable`（`jobs/infer.py`）が `FLAG_RENTING | FLAG_RETURNING` の両方を要求している。**除外規則は正しく働いている**（「**出さない**のであって、0 や 0.5 で埋めない」）。最新周期の更新行数 14,436 は `flags = 7` の数とぴたり一致する。

**問題は、出さなくなったあとの行が残ることである。** `upsert_forecasts` はその周期に来たポートしか触らないので、止まったポートの行は**最後に出した確率を抱えたまま古くなっていく**。492 のうち 199 が「この 11 時間のどこかでは動いていた」ポートである。

**W4 への申し送り。** `/v1` が `station_forecasts` を素直に返すと、**11 時間前の確率を「現在の予測」として配る**ことになる。CLAUDE.md §2 の 7・8（予測値には予測時刻を必ず添える／ttl 超過の値を「現在値」として出さない）に真正面から触れる。手は 2 つある。

| 手 | 中身 | 難点 |
|---|---|---|
| **読む側で切る**（推奨） | `/v1` が `generated_at` の鮮度で落とす | 行は残るので、テーブルは緩やかに増える |
| 書く側で消す | 推論のたびに、出さなかったポートの行を消す | 復帰のたびに消して入れ直すことになり、**HOT 率 100% が崩れる** |

**読む側で切るほうがよい。** 199 件は 14,635 行の 1.4% で容量は問題にならず、100% の HOT 率は段 8 でいちばん確かめたかった性質である。**行が残っていること自体は害ではない。害は「古い行を新しい顔で出す」ことのほうにある。**

**この取り残しは、完了条件の書き方では捕まらなかった。** 段 8 の完了条件は「`station_forecasts` が 5 分毎に**全件**更新され」だが、実測は 14,436 / 14,635 ＝ **98.6%** である。**分母を数えていなければ「全件更新されている」と読めてしまう。** §7.8 に取り残しを数えるクエリを足した。**「全件」と書いたら、その全件を数えるクエリも一緒に置く。**

### 110. 成果物に無いポートが、別のポートの気候値を読む（ドコモを足したあとの点検で判明）

109 の「取り残し」の**分母を数えていて**気づいた。**いま予測対象の 20,289 ポートのうち 5 件が、配信中の成果物 `baseline-b3-v0-20260908` に載っていない。**

```
docomo-cycle/6103, hellocycling/27483, 27484, 27485, 27486
```

成果物を作った 9/06〜9/08 より**後に現れた**ポートである。`to_samples`（`jobs/infer.py`）は知らないポートに **`port = -1`** を振る。`climatology._key` はそれを

```
key = (-1 × 3 + dow_type) × 96 + slot   →   -288 〜 -1
```

にし、`table.usable[key]` / `table.rate[key]` が **numpy の負インデックスで表の末尾に回り込む**。行き先は**成果物の最後のポート**（`hellocycling/9972`）のセルで、そこにある 288 セルのうち **35 セルが `usable`** だった。

**本番の `station_forecasts` で実際に起きていた。**

| `system_id` | `station_id` | 信頼度 | 借りられる確率 ×1000（h=5,10,15,20） |
|---|---|---:|---|
| `docomo-cycle` | 6103 | **3** | 295, 379, 440, 467 |
| `hellocycling` | 27483 | **3** | 995, 991, 989, 987 |
| `hellocycling` | 27485 | **3** | 176, 253, 306, 348 |

**5 件とも `confidence = 3`**（＝過半の水平で気候値が効いた）。読んでいたのは**別のポートの履歴**である。**数字が違うだけでなく、いちばん高い信頼度のラベルが付く。**

**規模と伸び方**：いまは 20,289 中 5 件（0.02%）で、時間帯も 288 枠中 35 枠にすぎない。ただし**新規ポートは 1 日約 100 件**現れ、W6 以降は週次再学習なので、**再学習の間隔ぶんだけ溜まる**。

**直し方**：`climatology._lookup` を足し、範囲外の番号を「使えないセル」として扱う。`predict` の docstring が最初から書いていた「使えないセルは `fallback`（B1 の予測）に落とす」の動作になる。**予測を出さなくする必要はない**：新しいポートでも B1（システム × バケツ × 水平）は正しく出るので、外すのは気候値の層だけでよい。学習側の `predict_leave_one_out` も同じ表を引くので一緒に直した。

**検査はあった。何も見ていなかった。**

```python
def test_unknown_port_still_gets_a_baseline() -> None:
    ...
    assert result[0].confidence == 2      # ← 直す前も通っていた
```

`confidence` は「過半の水平で気候値が効いたか」しか見ておらず、**引いた先が別のポートでも 2 のまま**になる。実際、未知ポートは末尾ポートと**同じ確率をバイト単位で**返していたのに、検査は緑だった。**確率そのものを比べる検査に置き換えた**：0 台の未知ポートは 0 台の既知ポートと同じ値を返さなければならない（直す前は 2 に対し **417**）。B2 の単体でも、`port = -1` が末尾のセルに重なる最小の表を組んで固定した。3 件とも、直す前に確かに落ちることを確かめてある。

**教訓は「境界の外を指す番号を、配列にそのまま渡さない」。** numpy の負インデックスは**例外を投げない**。`_key` は番号を作るだけで、範囲を知らない。**表の引き方は、番号を作る側ではなく引く側で守る。**

**残っている穴**：直したあとも、**成果物が台帳から離れていくこと自体は見えない**。未知ポートは静かに B1 に落ちるだけである。§7.8 に突き合わせの手順を足した。

| Parquet | 欠落 0（進行中の 1 時間を除く）。`fetched_at` の null 0 件 |

**`daily_quality` を品質フィルタに素直に使ってはいけない。** 収集開始より前の日付の行があり、`n_snapshots = 0 / n_expected = 1080`（2026-09-05）になっている。「その日は全滅」と読めてしまう。**M0 以降で切ること**を、使う側の規則として書いておく。

### 13.2 参照データに as-of が無い（**W4 で決める。最大の未解決点その 1**）

§6.2 の漏洩防止の規則は**スナップショット（`fetched_at`）と天気（`available_at`）しか覆っていない**。参照データは全部「いまの値」で過去のサンプルを作っている。

| 参照データ | 読み方 | 履歴 |
|---|---|---|
| `station_attributes`（緯度経度・容量・充電） | **現行行だけ**（`valid_to is null`。`features/reference.py`） | **SCD2 で在るのに使っていない** |
| `station_neighbors`（近傍 9 列） | 現在の表 | **無い**（日次全置換。W3-09） |
| `stations.pref_code` / `muni_code` | 現在の値 | 無い（上書き） |

帰結は 2 つある。

1. **再現性**。同じ日のサンプルを翌日作り直すと、近傍・静的特徴量が変わりうる。§1 の「2 回作ってバイト列が同一」は**同じ参照データの上での話**であって、時間をまたぐ再現性ではない。
2. **軽い先読み**。`t` より後に変わった属性が `t` のサンプルに入る。ラベルを含まないので目的変数の漏洩ではないが、**`t` の時点で入手できた情報ではない**。

**W3 の 3 日では実害はほぼ無い**（近傍は 1 日 +78 ペア、属性の変更は 4 日で 10 行）。**効いてくるのは W6 の週次再学習**で、数週間ぶんを一度に作るときに「その週のどこの地理か」が曖昧になる。手は 3 つ。**採ったのは (a)**（設計は §14.3、実装は §14.6。**閉じた**）。

| 手 | 中身 | 費用 |
|---|---|---|
| **(a) 参照データを成果物と一緒に固定する** | ビルド時の参照を版として保存し、再構築はその版で行う | 保存が増える。**再現性は完全に戻る** |
| (b) `station_neighbors` に `valid_from` を持たせる | 日次全置換をやめて履歴を積む | W3-09 の判断（差分更新の複雑さ）を覆すことになる |
| (c) 現状のまま「参照は最新」と割り切る | 何もしない。文書に明記する | 0。**再現性を諦める** |

### 13.3 `capacity` の定義が、計画と実装で違う

開発プラン §3 は「学習・推論では **`capacity_est = 過去 7 日の max(bikes + docks)`** を使う」と書いている。実装（`features/static.py` の `running_capacity`）は **ビルド窓の累積最大**で、窓は `LOOKBACK_HOURS = 25` ＋ 対象日 ＝ **約 49 時間**である。

ドコモの `capacity` はこの値で、そこに乗っている列が 3 つある（`fill_ratio` / `gap` / `is_over_capacity`）。7 日版より**小さめに出る**（`gap` が小さく、`fill_ratio` が大きい）。

**`LOOKBACK_HOURS` を触ると特徴量の値が変わる。** `FEATURE_SET` を上げずに窓を変えてはいけない。→ **7 日に寄せて閉じた**（2026-09-09、`FEATURE_SET = v1`。§14.6）。`capacity_est` は参照スナップショットが持つので、ビルド窓から独立した。

### 13.4 推論側は `features/` を通っていない（**W4 で決める。最大の未解決点その 2**）

CLAUDE.md §2 の 4 と開発プラン §8.2 の手順 3〜4 は、**学習と同一コードで特徴量行列を作る**と決めている。**段 8 の実装はそうなっていない。**

```
学習   Parquet（1 時間 1 ファイル、25 時間の遡り）→ features/build.py       → 65 列
推論   station_status_latest（1 ポート 1 行の現在値）→ jobs/infer.py の to_samples → 履歴を持たない Samples
```

**B0〜B3 はこれで足りている。** 必要なのは `(system, port, bucket, dow_type, slot15)` だけで、履歴が要らない設計になっているからである。**足りなくなるのは LightGBM v1（W6）で**、57 個の特徴量にはラグ（5〜60 分）・流量（60 分）・近傍集約・同時刻 1 日前が要る。**いまの推論経路には履歴が 1 行も無い。**

`features/build.py` の入口は `pa.Table`（Parquet の形）なので、推論側は **DB の配列から同じ表を組み立てる**必要がある。**これは W4 の最初の設計課題**で、後回しにすると「TS 移植」や「推論だけ別実装」に流れて、まさに開発プラン §4 が避けようとしたズレを作る。

## 14. 残りの実装：W3 で片づけるものと、W4 に送るもの

**W4 は W4 で別に計画する。** ここで決めるのは**切り分け**だけ ——「W4 のプランを待たずに、いま片づけてよいものはどれか」。

### 14.1 切り分けの軸は「W4 の設計に依存するか」

W3 の実装は終わっていて、**9/16 までは段 7 の測り直し待ちで実質「待ち」**である。その 1 週間に何を入れるか。判断の軸は 2 つだけ。

| 軸 | 意味 |
|---|---|
| **W4 の設計に依存するか** | 依存するなら送る。`/v1` の契約や推論の経路は、W4 の API 設計と一体で決める |
| **待つとコストが上がるか** | 上がるなら前倒す。**サンプルの定義**は、モデルを 1 つでも学習したあとに変えると再学習になる |

**この 2 軸で、9 件は 3 つに割れる。**

### 14.2 W3 の残り期間にやる（W4 のプランを待たない）

| # | やること | 規模 | 根拠 |
|---|---|---|---|
| **1** | ~~**日次の参照スナップショット**（§14.3）~~ **済（2026-09-09）** | 中（新ジョブ 1 本＋読み手） | §13.2・§13.3 |
| **2** | ~~`build_features` をスナップショット読みに切り替え、`FEATURE_SET` を上げる~~ **済（2026-09-09、§14.6）** | 小 | 1 の適用 |

**1 と 2 は「いま直せばタダ」の側**である。`capacity` に乗る 4 列（`capacity` / `fill_ratio` / `gap` / `is_over_capacity`）を使っているモデルはまだ 1 つも無い（B0〜B3 は `bikes` / `docks` しか読まない）。W4 で v0 を学習したあとに定義を変えると、再学習と全期間の再生成が要る。

**3〜5 は「ついで」に見えるが、いま入れる理由がある。** 3 は成果物のドリフトが**静かに育つ**性質のもの（§12 の 110 で B1 に落ちるようにしたが、落ちていること自体は見えない）。4 は 576 行/日で、W7 まで放置すると約 5 万行になる。どちらも W4 の設計に何も依存しない。

### 14.3 日次の参照スナップショット（設計）

**3 つの所見が 1 つの仕組みで片づく。**

```
いま      参照データ ＝ DB の「いまの値」を、学習も推論もその場で読む
          → 過去を作り直すと値が変わる                （§13.2）
          → capacity がビルド窓の長さに依存する        （§13.3）
          → 推論側は同じ入口を持てない                 （§13.4 の半分）

これから  日次で参照スナップショットを 1 組書き、学習も推論もそれを読む
```

**置き場所**は既存の `gbfs-parquet` バケット。MIME も既存の許可リスト（`application/vnd.apache.parquet`）に収まるので、バケットを増やさない（§12 の 106 の轍を踏まない）。

```
reference/date=YYYY-MM-DD/stations.parquet    約 20,750 行
reference/date=YYYY-MM-DD/neighbors.parquet   約 106,516 行
```

| ファイル | 列（実装 `features/reference_snapshot.py`） |
|---|---|
| `stations` | `system_id`・`station_id`・`first_seen_at`・`pref_code`・`muni_code`・**`has_attributes`**・`lat`・`lon`・`capacity`・`is_charging_station`・`region_id`・**`capacity_daily_max`**・**`capacity_est`**・**`capacity_days`** |
| `neighbors` | `system_id`・`station_id`・`nb_system_id`・`nb_station_id`・`distance_m`・`same_system` |

**`SystemReference` が持たないものは持たせない。** `is_active` は入れない（`list_station_geo` が読まないのと同じ理由で、活性なポートだけ残すと生存者バイアスになる）。`idx`（台帳の位置）も入れない。**`has_attributes` だけは足す**：台帳にあって属性が無いポートがあり、全 null の属性行をでっち上げると「`lat` が無いポート」と区別が付かなくなる。

**除外規則はここで適用しない。** ドコモの `5753`（【監視】メンテナンスポート）は `capacity_est = 9999` のまま入る。除外は特徴量を作る側の仕事で、**参照は「事業者が出しているもの」をそのまま持つ**（データ辞書 §7）。

**`capacity_est` は「過去 7 日の `max(bikes + docks)`」を日次で作る**（開発プラン §3 の定義に戻す）。7 日ぶんの Parquet を毎回読むのではなく、**その日の最大（`capacity_daily_max`）を各スナップショットに残し、直近 7 版の最大を取る**。読むのは当日の Parquet（48 ファイル・約 4 MB）と、前 6 版の `stations.parquet` だけで済む。7 日揃うまでは揃った日数を `capacity_days` に出す（**足りないことを黙って隠さない**）。

**読む規則は 1 つに揃える。**

> **学習も推論も、基準時刻の「前日」の版を読む。**

- 学習：`build_features --date X` は `reference/date=X-1` を読む。**同じ日を何度作り直しても同じ値になる**（§13.2 が閉じる）。
- 推論：`/ml/infer` は「昨日の版」を読む。成果物と同じくモジュール変数にキャッシュする（1 回 1.5 MB を 5 分毎に取り直さない）。
- **規則を同じにするのが要点。** 「学習は前日、推論は最新」にすると、そこが新しい train/serve skew になる。当日現れたポート（1 日約 100 件・全体の 0.5%）は翌日まで参照を持たないが、**属性が最大 1 日遅れるのは今も同じ**である（開発プラン §8.3）。

**いつ動かすか**：`rebuild_geo`（pg_cron 04:30 JST）の後。**05:00 JST の Vercel Cron で `/ml/reference`**。前日ぶんを書くので、パスの日付は前日になる。

**容量と所要（2026-09-09 に本番で実測）**：`stations` 510 KB ＋ `neighbors` 509 KB ＝ **1 日 1.0 MB、年 370 MB**（Storage は 100 GB 込み）。所要は**手元から 43 秒**で、ほぼ全部が 48 ファイルの逐次取得である（CPU は 10%）。`maxDuration` は 120 秒。本番は Supabase と同じ東京なので、ここより速い見込み。

**持ち回りが効くことを確かめた**（9/06〜9/08 を順に書いた）。

| 版 | `capacity_days_max` | `capacity_est` を持つポート | `missing_hours` |
|---|---:|---:|---:|
| 2026-09-06 | 1 | 20,647 | **30**（収集開始が 15:51 JST。15 時間 × 2 系統） |
| 2026-09-07 | 2 | 20,742 | 0 |
| 2026-09-08 | 3 | **20,749** | 0 |

**日を重ねるほど推定を持つポートが増える。** 7 日揃うまでは `capacity_days` にその日数が出る。

**版**：`REFERENCE_SET` を持ち、Parquet の**スキーマメタデータ**に `reference_set` と `built_at` を入れる（列にしない。20 万行に同じ値を並べない）。`build_features` は使った `reference_date` を出力サンプルのスキーマメタデータに記録する。

**これで閉じるもの／閉じないもの**

| 所見 | どうなるか |
|---|---|
| §13.2 参照データの as-of | **閉じる。** 近傍・属性・行政区画がすべて日付で固定される |
| §13.3 `capacity` の定義 | **閉じる。** 7 日の定義に戻り、`LOOKBACK_HOURS` から独立する |
| §13.4 推論側の特徴量経路 | **半分だけ閉じる。** 参照側の入口は揃うが、**観測履歴（ラグ・流量・同時刻 1 日前）は別**。25 時間ぶんの観測を推論時にどう手当てするかは W4 の設計 |

### 14.4 W4 のプランに送る

| # | 何を | なぜ W4 か | 根拠 |

### 14.5 並行できるか

**できる。14.2 の 5 件は W4 の設計に何も依存しない。**

| | 並行 | 理由 |
|---|---|---|
| 14.2 の 1〜2（参照スナップショット） | **できる。むしろ先にあるほうがよい** | W4 の B（推論の観測履歴）を設計するとき、**参照側が既に片づいている**ほうが問題が小さくなる。「参照 ＋ 履歴」の 2 つを同時に考えると決まらない |
| 14.2 の 3〜5 | **できる** | 独立した小さい変更。DB の保持と記録だけ |
| 14.4 の A | **すべきでない** | `/v1` の契約と一体 |
| 14.4 の B | **すべきでない** | 14.2 の 1〜2 の結果を前提にする |
| 14.4 の C | できるが**待つ** | 学習窓が 9/08 以降に縮むので、データが貯まってからのほうが判断できる |
| 14.4 の D | **待つ**（9/16） | 測り直しの結果が判断材料 |

**やらないほうがよいこと**：この 1 週間に W4 の B（推論の観測履歴）へ手を付けること。**参照スナップショットが入る前に設計すると、参照と履歴を一度に考えることになって決まらない。** 順番を守れば、W4 は「履歴だけ」を考えればよくなる。

**減るほうが多いのは正しい。** 旧 `running_capacity` は**対象日の観測を含む**累積最大だったので、その日に新記録が出れば取り込んでいた。`capacity_est` は**前日までの 7 日**なので取り込まない。**推論時に作れない値を学習だけが使っていた**、という状態が解消されたということである。

**予想していなかった収穫：`is_over_capacity` が意味のある特徴量になった。**

```
false → true 14,714 件   true → false 0 件
true の合計   389 → 15,103（ドコモの 559,777 行のうち 2.7%）
```

v0 の `capacity` は当日の観測を含む累積最大だったので、**定義上ほとんど超えられない**。true は 0.07% しかなく、**分散のほとんど無い列**だった（データ辞書が `parking_type` について書いたのと同じ状態）。v1 では「**直近 7 日の最大を超えた**」を意味し、ドコモの 2.7% で true になる。

**`gap` は 1 行も動いていない。** HELLO 専用の列で、HELLO の容量は宣言値のままだからである（設計どおり）。

**システムの並び順に注意が要った。** `to_reference` は `system_id` の昇順で返す（ドコモが先）が、`SYSTEM_IDS` は HELLO が先である。台帳の位置＝出力の行順がこれで決まるので、`build_features` で **`SYSTEM_IDS` の順に並べ直している**。最初これを入れ忘れて、行順だけが黙って入れ替わった。

**`stations_unreferenced` を `DayStats` に足した。** `to_observations` は参照に無いポートの行を黙って捨てる（台帳が正）。参照が前日の版になったので、**当日現れたポートがここに出る**。2026-09-08 の実測は **0** だが、これは**遡って作った版が「いまの台帳」を持っている**ためでもある（`build_reference` は `stations` を DB から読む）。日次の cron が回り始めれば、実際の値が出る。

**参照スナップショットが無ければ止める。** DB の「いまの値」で代用しない（代用すると §13.2 の状態に戻る）。`MissingReferenceError` に、先に走らせるコマンドを入れてある。
