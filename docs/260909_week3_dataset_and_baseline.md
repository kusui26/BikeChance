## 1. Week 3 のゴールと完了条件

**ゴール：貯めたデータから「学習サンプル」を作れる状態にし、超えるべき線を測る。**

W1 で「集める」、W2 で「残す・読む」が完成した。W3 の主題は 3 つある。

1. **静かに失われる経路を塞ぐ**（監視の穴・バックアップ収集器）。W2 の点検で、ジョブが落ちても誰も気づかない状態が残っていることが分かった。天気アーカイブは落ちた時刻の予報が永久に失われる。
2. **学習に要る参照データを揃える**（暦・地理・近傍・天気の入手時刻）。どれも「あとから作れる」ものだが、無いと特徴量が書けない。
3. **特徴量とラベルを作る一本道を通し、ベースラインで線を引く**。LightGBM の良し悪しは、比較対象が無ければ判定できない。

## 3. W3 で確定させた設計判断

W1 の W1-01〜W1-31、W2 の W2-01〜W2-13 に続けて **W3-01 から**採番する。**実装前に決め、実装で変わったら §3 と開発プランを直してから進む**（CLAUDE.md §2 の原則 10）。

### 3.1 監視と冗長化について

| ID | 論点 | 決定 | 根拠 |
|---|---|---|---|
| **W3-01** | ジョブの異常をどう検知するか | **「失敗が在る」ではなく「直近 N 時間に成功が無い」を見る** | cron が 1 度も起動しなければ `job_runs` に行が無く、`status = 'failed'` を探しても何も見つからない。収集のウォッチドッグが `last_fetch_at` の古さを見ているのと同じ考え方（W1-29）。失敗の検知は補助として併置する |
| **W3-02** | 新しい検査をどこに置くか | **`monitor_feeds` に足さず、別関数 `monitor_jobs()` を作って pg_cron の別ジョブにする** | 現在の `monitor_feeds` は**全検査を 1 つの `begin ... exception when others` で包んでいる**（実装で確認）。1 つの検査が落ちると残りが全部飛び、`job_runs` には `failed` が 1 行残るだけになる。新しい検査は `storage.objects` を読むので、権限や重さで落ちる可能性が既存の検査より高い。**495 回連続で成功している監視を、増築で壊さない。** pg_cron のジョブは 5 本 → 6 本で、Supabase の推奨（同時 8 本以下）に収まる |
| **W3-03** | バックアップ収集器は何をするか | **生 gzip JSON を Storage に保存するだけにする。`ingest_snapshot` を呼ばない**（開発プラン §5.7 の「同じ RPC に書く」から変更） | 守るべき不変条件は「生 JSON を必ず残す」（CLAUDE.md 最重要原則 1）で、Postgres の配列は**再構築できる**（W2 の PR B で実証。照合 6/6 一致）。RPC を呼ぶには正規化（負値の丸め・重複排除・フラグ・`idx` の採番）を Deno で再現する必要があり、**本番と冗長系で正規化がずれる**という新しいリスクを作る（W2-05 と同じ型）。保存だけなら Deno 側にドメインロジックがほぼ無くなる。動いたことは `job_runs` にだけ記録する |
| **W3-04** | バックアップ収集器の ODPT 認証 | **公開エンドポイント（`api-public.odpt.org`）を使い、トークンを持たせない** | CLAUDE.md は「トークン付き URL を組み立てるのは `apps/web/lib/jobs/odpt-fetch.ts` だけ」と定めている。冗長系のために 2 つ目の組み立て箇所と 2 つ目の秘密の置き場所を作るのは、規約の例外を増やすぶん割に合わない。**実測（2026-09-08）で公開エンドポイントは無認証で 200 を返す**（HELLO 4,221,822 B / 0.91 秒 / 14,921 ポート、ドコモ 903,586 B / 0.27 秒 / 5,818 ポート）。応答は認証付きと同一（D-04 の実測）。この決定により、Edge Function に新しい秘密は 1 つも要らない（Supabase が注入するサービスロールキーだけ） |
| **W3-05** | バックアップ収集器の起動条件 | **pg_cron（1 分毎）が `feed_state.last_success_at` の 6 分超の停滞を見て `net.http_post` する。1 システムにつき 1 分に 1 回まで** | ODPT を過負荷にしない（CLAUDE.md §2 の 8）。常時二重化はしない（D-16）。6 分は、毎分ポーリング＋ウォッチドッグ（1 分毎）でも復帰しない状態、つまり Vercel 側が丸ごと死んでいる状態にだけ当たる |

### 3.2 参照データについて

| ID | 論点 | 決定 | 根拠 |
|---|---|---|---|
| **W3-06** | 天気ファイルの「入手できた時刻」 | **記録から引く。`job_runs` の `detail.hour_epoch_s` → `finished_at` を公開ビュー `v_weather_files` にする。保守的な既定（`hour_epoch + 1 時間`）は、記録が無い時間帯のフォールバックとしてだけ残す** | W2 プラン §14.4 は「W3 は保守的な既定、W4 で厳密版」としていたが、**実測で材料が全部揃っていることが確認できた**（12/12 の行に `finished_at` と `duration_ms` がある。遅延は 17.637〜17.658 分でばらつき 0.02 分）。厳密版のほうが実装が短い（ビュー 1 本）ので、**先に保守的な既定を作り込む理由が無い**。既定を使うと 18〜60 分のあいだ 1 時間古い予報を使うことになり、5 分グリッド点の 30%（開発プラン §6.2）が無駄に劣化する |
| **W3-07** | 行政区域（`pref_code` / `muni_code`） | **HELLO は `address` から `pref_code` と `muni_code` の両方を埋める（`pref_code` だけにしない）。ドコモは両方 NULL のままにし、`region_id` をカテゴリ特徴量として使う。国土数値情報 N03 のポリゴン照合は W3 では行わない** | **実測（§10.2a）で 3 つ分かった。**(1) **`pref_code` 単独はほぼ価値が無い**（ポート毎の `P(bikes=0)` を leave-one-out で当てて R² 0.024）。`muni_code` は 5 倍強い（R² 0.132）が、**住所から取れば費用は同じ**なので `pref` だけ埋める理由が無い。(2) **近傍リストのほうが `muni_code` より当たる**（k=10 / 1 km で R² 0.201、k=20 / 2 km で 0.225）。**近傍で説明したあと市区町村が足す残差は 1.49%** しかない。(3) 近傍数の帯ごとに見ると、**近傍が 1 件でもあれば必ず近傍が勝つ**。市区町村が勝つのは近傍 0 件のポートだけ。したがって N03（全国 611 MB・都道府県別 11 MB × 約 30、幾何ライブラリの追加が必要）で埋まるのは「**ドコモかつ 1 km 以内に近傍 0 件**」の **136 ポート（全 20,742 の 0.66%）**にすぎない。**費用の桁が価値に見合わない。** ポリゴン照合は §8 に置き、外部の市区町村データ（人口・乗降客数など）と結合したくなった時点で判断する |
| **W3-07a** | ドコモの地域名 | **`region_id` は整数のまま使う。名前は引かない** | GBFS の `system_regions.json` は **ODPT が配信していない**（実測：両システムとも 404。`gbfs.json` に載っているのは `system_information` / `station_information` / `station_status`（＋HELLO の `vehicle_types`）だけ）。`system_information` にも地域の手がかりは無い。**名前を得る手段が無いので、カテゴリ ID として使う**（GBM には十分） |
| **W3-08** | 近傍リストの作り方 | **PostGIS を入れず、Postgres の中で緯度経度の格子バケツ＋距離式で作る** | 実測：全 20,742 ポートで半径 500 m の近傍は **97,822 ペア（片方向）**、平均 4.7・中央 4・最大 30。純 Python の格子バケツ法で **2.0 秒**で全部出る。PostGIS は利用可能（3.3.7）だが未インストールで、入れれば `spatial_ref_sys` 等で DB が増え、拡張の版管理も増える。**この規模では要らない。** `cube` + `earthdistance` も同様 |
| **W3-09** | 近傍リストの更新 | **日次で全置換する（差分更新しない）** | 10 万行の全置換は 1 秒未満。差分更新の複雑さ（消えたポート・動いたポート・SCD2 の閉じ方）に見合わない。台帳は 1 日に約 100 件増える（W1 実測）ので、日次で十分追随する |
| **W3-10** | 祝日の取り込み | **内閣府 CSV を月次で取り込む。年末年始（12/29–1/3）とお盆（8/13–16）は `jp_holidays` に「行政の祝日ではない休業日」として別種別で入れる** | 実測：CSV は Shift_JIS・21,538 B・1,068 行、**2027-11-23 まで**収録（2026 年 18 件・2027 年 17 件）、`last-modified: 2026-02-02`、`etag` あり（条件付き取得が効く）。年末年始とお盆は収録されないが、シェアサイクルの需要には効く。**同じテーブルに入れて `kind` で分ける**と、特徴量側は 1 か所を引くだけで済む |

### 3.3 特徴量とラベルについて

| ID | 論点 | 決定 | 根拠 |
|---|---|---|---|
| **W3-11** | 水準と流量の計算 | **水準（`bikes`・`docks`・`flags`）とラベルは 5 分グリッドの as-of、流量（`rentals_60`・`returns_60`・`n_changes_60`・`minutes_since_last_change`）はフィード本来の周期で計算してからグリッドに集約する。実装も 2 つの関数に分ける** | 開発プラン §6.7 の実測：ドコモを 5 分グリッドに畳むと **流量の 13% が消える**（22,704 → 19,741 台）。毎分収集がデータ量を増やしているのはドコモだけで、その増分はここでしか効かない。**同じ関数で両方をやると必ずどちらかを間違える** |
| **W3-12** | ラベルの as-of と衝突ガード | **ラベルは `t+h` 以前の最新観測。`as-of(t+h)` が `as-of(t)` と同じ観測を指すサンプルは落とす** | ユーザーが到着時に見るのは「その時点で公開されている最新の値」なので、`t+h` 以前の最新が正しい。衝突ガードは、HELLO の公開周期（300 秒）とグリッド（5 分）が同じことから来る危険への保険。**実測（2026-09-07 の 1 日・5,731 万ペア）で衝突は 0 件**。費用ゼロで、位相が月単位でずれたときにだけ効く |

## 5. PR の分割と各 PR の定義

### 5.1 分割の方針

W1・W2 と同じ。1 つの PR は **1 つの関心事**に閉じ、レビューが 20〜60 分で終わる量にする。各 PR はそれ自体で CI を通し、テストを含む。**本番に影響する変更を後ろに寄せる。ただし損失が日ごとに積み上がるものは最初に置く。**

W2 プラン §14.1 で決めた並べ方の原則をそのまま使う：**「遅れた分が損失になるか」で並べる。** 難しさでも面白さでもない。

| 段 | PR | 名前 | 主な成果物 | 遅れると失われるか | 本番影響 | 目安 |
|---|---|---|---|---|---|---|
| **0** | — | 天気アーカイブの 1 日判定 | W2 の暫定合格を確定させる | — | なし | 15 分 |
| **1** | **A** | 監視の穴を塞ぐ | `0020_monitor_jobs.sql`、pgTAP、pg_cron ジョブ 1 本 | **はい**（気づけない時間がそのまま損失） | 小 | 半日 |
| **2** | **B** | Parquet に `fetched_at` ＋既存の再圧縮 | `snapshot_table.py`・`supabase.py`・再圧縮の実行 | **費用が増える**（2026-11-05 に段差） | 中 | 半日 |
| **3** | **C** | バックアップ収集器 | `supabase/functions/collect-gbfs-backup`、`0021`、起動条件 | **はい**（Vercel 障害中の GBFS は永久に失われる） | **大** | 1 日 |
| **4** | **D** | 暦と天気アーカイブの索引 | `0022`、`jp_holidays` 取り込み、`v_weather_files` | いいえ | 小 | 半日 |
| **5** | **E** | ポートの地理属性と近傍リスト | `0023`、`stations.pref_code`、`station_neighbors`、日次ジョブ | いいえ | 小 | 半日 |
| **6** | **F** | 特徴量パイプライン v0 | `apps/ml/bikechance_ml/features/`、ゴールデンテスト | いいえ | なし | 1 日 |
| **7** | **G** | ベースライン B0–B3 と評価ハーネス | `apps/ml/bikechance_ml/baselines/`・`eval/`、EDA #2 | いいえ | なし | 1 日 |
| **8** | **H** | `/ml/infer` の配線 | `0024`、`station_forecasts`、5 分 Cron、ウォッチドッグ | いいえ | 中 | 1 日（任意） |
| **9** | — | iOS のポート詳細 | 詳細シートを画面に昇格 | いいえ | なし | 半日（任意） |

**この順にする理由**

- **段 1 と段 3 は「静かに失われている」を止める。** 段 1 のほうが先なのは、**費用が段違いに安く**（マイグレーション 1 本）、しかも**段 3 を直している最中に別のジョブが落ちても気づけるようにしておくため**である（W2 プラン §14.7）。
- **段 2 は締切が動く。** 再圧縮の費用は 1 時間ごとに増え、2026-11-05 に「生 JSON からの再構築が先に要る」段差がある。安いうちに終わらせる。
- **段 4・5 は段 6 の入力**。祝日・地理・近傍が無いと特徴量が書けない。
- **段 6 は段 2 の後**（`fetched_at` で as-of を切るため。W3-13）。
- **段 7 は日数が効く**（§6）。段 8 は遅れても失われない（W3-18）。

### 5.2 段 0：天気アーカイブの 1 日判定（PR なし）

### 5.3 PR A：監視の穴を塞ぐ

**目的**：静かに落ちる経路を無くす。とくに**天気アーカイブ**は、落ちた時刻の予報が永久に失われる。

```
supabase/migrations/<ts>_0020_monitor_jobs.sql
supabase/tests/0011_monitor_jobs.sql
```

**新しい関数 `monitor_jobs()` を作る**（`monitor_feeds` には触らない。W3-02）。pg_cron に 5 分毎のジョブとして登録する。

| 検査 | 条件 | 抑制 | 鍵 |
|---|---|---|---|
| **ジョブが動いていない** | 対象ジョブの `status = 'ok'` が直近 N 時間に 1 件も無い | 3 時間 | `job_missing:<job>` |
| **ジョブが失敗した** | 直近 3 時間に `status = 'failed'` がある | 1 時間 | `job_failed:<job>` |
| **Parquet に欠落がある** | 直近 6 時間で、`status_snapshots` に行が在るのに Storage に対応するオブジェクトが無い時間帯がある | 6 時間 | `parquet_gap` |
| **祝日データが尽きかけている** | `jp_holidays` の最終収録日まで 90 日を切った | 7 日 | `holidays_expiring` |

対象ジョブと閾値は**テーブルで持つ**（`app_config` ではなく専用の小さな表）。ジョブが増えるたびに関数を書き換えたくない。

祝日の検査は PR D が `jp_holidays` を作るまで対象が無い。**`to_regclass('public.jp_holidays') is null` なら黙って飛ばす**（例外に頼らない）。

| ジョブ名 | 期待周期 | 「成功が無い」閾値 |
|---|---|---|
| `archive_weather` | 1 時間 | **3 時間**（2 回落ちたら鳴る） |
| `compact_parquet` | 1 時間 | 3 時間 |
| `sync_stations:hellocycling` | 1 日 | 30 時間 |
| `sync_stations:docomo-cycle` | 1 日 | 30 時間 |
| `maintain_partitions` | 1 日 | 30 時間 |
| `daily_quality` | 1 日 | 30 時間 |

**設計上の注意**

- 検査ごとに `begin ... exception when others` で囲み、**1 つの失敗が他を巻き込まない**ようにする。関数全体としては `job_runs` に `ok` を記録し、`detail` に検査ごとの結果（`checked` / `alerts` / `errors`）を残す。
- `storage.objects` は**スキーマ付きで書く**（`set search_path = ''`）。
- 欠落検査は**直近 6 時間に限る**。`status_snapshots` の `observed_at` を UTC の時に丸め、`storage.objects` の `name` から `date=` / `hour=` を組み立てて突き合わせる。

**テスト**（pgTAP）

- 関数が在り、`security definer` かつ `search_path = ''` であること
- `postgres` が `storage.objects` を読めること（**これが読めないと設計が成り立たない**）
- ジョブ表に上表の 6 行が在ること
- 「成功が無い」検査：`job_runs` を空にして呼ぶと `alert_state` に `job_missing:archive_weather` が入ること
- 「失敗」検査：`failed` を 1 行入れると `job_failed:*` が入ること
- 1 つの検査を壊しても（存在しないテーブルを見る等）他の検査が走り、`job_runs` が `ok` で終わること
- 抑制：連続 2 回呼んでも 2 通目は送られないこと

**完了条件**：ローカルで `archive_weather` の `job_runs` を空にした状態から `monitor_jobs()` を呼び、通知が組み立てられることを確認する。本番適用後、**実際に 1 度鳴らして Discord に届くことを見る**（段 0 で Webhook を確かめたときと同じ）。
※ 本番の cron を止めるのは CLAUDE.md §6 の確認が要る操作なので、**ローカルで再現する**。

### 5.4 PR B：Parquet に `fetched_at` ＋既存の再圧縮

**目的**：学習の as-of 結合を `fetched_at` で切れるようにする（開発プラン §6.2、W2 プラン §13 の (2)）。

```
apps/ml/bikechance_ml/jobs/snapshot_table.py   # SCHEMA と Snapshot に fetched_at
apps/ml/bikechance_ml/io/supabase.py           # select に fetched_at
apps/ml/tests/{test_snapshot_table,test_compact}.py
docs/data_dictionary.md §7.3                   # 契約の更新
```

**列は `fetched_at` 1 つだけにする。** `raw_path` は `(system_id, observed_at)` から組み立て直せる（`rawObjectPath`）。`n_stations` と `is_anomalous` は Parquet から導ける（W2 プラン §13 の (10)(11)）。**導けるものは足さない。**

#### 既存を同じ PR の中で再圧縮する

**列を足すだけで再圧縮しないと、読む側が静かに壊れる**（W2 §14.3 の実測）。

| 読み方 | 古いファイル（列なし）と新しいファイル（列あり）を混ぜたとき |
|---|---|
| `ds.dataset(...)`（スキーマを渡さない） | **`fetched_at` が黙って消える。** 最初に見つけたファイルからスキーマを推論するため。エラーは出ず、しかも「最初」は環境で変わる |
| `ds.dataset(..., schema=SCHEMA)` | 古いファイルの `fetched_at` が `null` になる。**気づける** |

したがってこの PR で 2 つを同時にやる。

1. スキーマに列を足す（7 列 → 8 列）
2. **アーカイブ開始（2026-09-06 06:00 UTC）から現在までを `?hour=` で再圧縮する**

あわせて、**読む側は必ず明示スキーマを渡す**という規約をデータ辞書に書く。

**完了条件**：全期間がファイル 8 列で読め、`fetched_at` に `null` が 1 件も無い。`schema=` を渡す読み方と渡さない読み方の**両方で同じ列**になる（比べ方は §7.3。hive のパーティション列が足されるので列数では比べない）。所要は 1 時間あたり約 3.3 秒（実測）で、着手時点（9/9 朝）の約 65 時間なら 4 分前後。

### 5.5 PR C：バックアップ収集器（Edge Function）

**目的**：Vercel 全体の障害・デプロイ事故のあいだも、生 JSON だけは失わない（R13・R18）。

```
supabase/functions/collect-gbfs-backup/index.ts
supabase/functions/collect-gbfs-backup/path.ts        # rawObjectPath の Deno 版（拡張子つきの相対 import）
apps/web/backup-collector-path.test.ts                # shared と同じ文字列を返すことを固定
supabase/migrations/<ts>_0021_backup_collector.sql    # 起動条件と pg_cron ジョブ
supabase/tests/0012_backup_collector.sql
```

**やることは 3 つだけ**（W3-03）。

```
1. ODPT の公開エンドポイントから station_status.json を取る（トークン無し。W3-04）
2. last_updated を読み、gzip して gbfs-raw の同じパスに upsert:false で PUT する
3. job_runs に記録する（job_started / job_finished）
```

**やらないこと**：JSON のパース（`last_updated` を読むための最小限を除く）、正規化、`ingest_snapshot` の呼び出し、`feed_state` の更新。復旧後は `rebuild-snapshots.ts`（W2 の PR B）で DB に戻す。

**起動条件**（`0021`）

```sql
-- 1 分毎。feed_state.last_success_at が 6 分超のときだけ Edge Function を叩く
select cron.schedule('backup_collect', '* * * * *', $$select public.trigger_backup_collect()$$);
```

`trigger_backup_collect()` は `security definer` で、Vault から `cron_secret` を読み、`net.http_post` で Edge Function を起動する。**応答は待たない**（結果は `job_runs` で見る）。

**踏むと分かっている点**

- **CPU 2 秒の上限**：パースしないので gzip だけ。`CompressionStream("gzip")` を使い、`Response.body` をそのまま流す。
- **同じパスへの衝突**：`upsert: false` で PUT し、**409 を正常系**として `job_runs` の `detail` に `duplicate: true` で残す。
- **パス規約の重複**：Deno は拡張子なしの相対 import を解決しないので `packages/shared` をそのまま import できない。`path.ts` に同じ式を置き、**vitest から両方を import して同じ文字列を返すことをフィクスチャで固定する**（§9.2）。
  - 契約テストは **`apps/web` に置く**。`supabase/functions/` は vitest の対象外で、`apps/web` は既に `vercel-crons.test.ts` でリポジトリのルート（`vercel.json`）を読んでいる前例がある。
  - `path.ts` を拡張子つきで import するので、typecheck の tsconfig に **`allowImportingTsExtensions`**（`noEmit` 前提）が要る。**入れる前に `pnpm typecheck` が通ることを確かめる。**
- **秘密**：Edge Function には `SUPABASE_URL` と `SUPABASE_SERVICE_ROLE_KEY`（Supabase が自動注入）以外は要らない。**新しい秘密を 1 つも置かない**（W3-04）。

**検証**：本番の cron を止められないので、**手動で 1 回叩いて確かめる**。

1. `supabase functions deploy collect-gbfs-backup --use-api`（Docker 不要）
2. `curl` で 1 回起動 → `gbfs-raw` にオブジェクトが 1 個増える（または 409 で `duplicate`）
3. `job_runs` に `backup_collect:<system>` が `ok` で入る
4. `rebuild-snapshots.ts --from <その時刻>` で DB に戻せる
5. 起動条件が**普段は発火しない**ことを、24 時間の `job_runs` で確認する（発火 0 回）

**完了条件**：上の 1〜5。ODPT への呼び出しが増えていないこと（`feed_fetch_log` の件数が変わらないこと）も見る。

### 5.6 PR D：暦と天気アーカイブの索引

**`v_weather_files`**（W3-06）

```sql
create view public.v_weather_files as
select (r.detail->>'hour_epoch_s')::bigint            as hour_epoch_s,
       r.finished_at                                   as available_at,
       (r.detail->>'n_saved')::int                     as n_saved,
       (r.detail->>'n_failed')::int                    as n_failed,
```

### 7.3 Parquet の `fetched_at`（PR B）

全期間を手元に落としてから、**2 通りの読み方で列が一致すること**を見る。

**列数で比べない。** `partitioning="hive"` はパスの `date=` / `hour=` を列として足すので、ファイルが 8 列でもデータセットは 10 列になる。**名前の集合で比べる。**

## 9. 付録：PR をまたぐ契約

ここは **PR をまたいで守る約束**を置く場所である。実装が変わったらここを直してから進む。**入力仕様の正は `docs/data_dictionary.md`（データ辞書）** で、ここに書くのは W3 で新しく決めるものだけ。

### 9.1 Parquet のスキーマ v2（PR B）

```
gbfs-parquet/{system_id}/date={YYYY-MM-DD}/hour={HH}/part.parquet   # 日時は UTC
```

| 列 | 型 | 意味 |
|---|---|---|
| `system_id` | string | `hellocycling` / `docomo-cycle` |
| `station_id` | string | 提供側の識別子。**`idx` は書かない**（W2-10） |
| `observed_at` | timestamp[us, tz=UTC] | フィードの `last_updated` |
| **`fetched_at`** | **timestamp[us, tz=UTC]** | **W3 で追加。**収集器が取得を終えた時刻。**as-of 結合はこの列で切る** |
| `bikes` | int16 | `-1` は「観測されなかった」。0 と区別する |
| `docks` | int16 | 同上。HELLO の `-1`（定員超過）は収集時に 0 へ丸めてある（W1-25） |
| `flags` | int16 | `1 = is_installed` / `2 = is_renting` / `4 = is_returning` のビット和。`-1` は欠損 |
| `reported_age_s` | int16 | `last_updated − last_reported`。ドコモは恒常的に 0（＝情報が無い） |

**読む側の規約**

- **必ず `schema=SCHEMA` を渡す。** 渡さないと pyarrow が最初に見つけたファイルからスキーマを推論し、混在時に列を黙って落とす（§4.2 の 11）。
- 1 つの JST 暦日を読むには、**UTC の `date=D-1/hour=15` から `date=D/hour=14` までの 24 個**を並べる（§4.2 の 14）。

**互換性**：v1（7 列）のファイルは PR B の再圧縮で全て v2 に置き換わる。**v1 と v2 が混在する期間を作らない。**

### 9.2 バックアップ収集器の契約（PR C）

| 項目 | 内容 |
|---|---|
| 取得元 | `https://api-public.odpt.org/api/v4/gbfs/{system}/station_status.json`（**トークン無し**。W3-04） |
| 保存先 | `gbfs-raw/{system_id}/{YYYY}/{MM}/{DD}/station_status_{last_updated}.json.gz`（UTC。`rawObjectPath` と同一） |
| 保存方法 | `upsert: false`。**409 は正常系**（`job_runs.detail.duplicate = true`） |
| パース | `last_updated` を読むためだけ。**正規化も検証もしない** |

### 9.3 学習サンプルの契約（PR F）

**基準時刻 `t`**：JST 00:00 起点の 5 分グリッド。1 日 288 点。

**水平 `h`**：{5, 10, 15, 20, 30, 45, 60, 90, 120, 180} 分（`packages/shared` の `HORIZONS_MIN`）。

**as-of の規則**

| 用途 | 規則 |
|---|---|
| 特徴量（水準） | `fetched_at <= t` を満たす行のうち `observed_at` が最大のもの。**`t − observed_at > 600 秒` なら欠損** |
| ラベル | `observed_at <= t + h` を満たす行のうち最大のもの。同じく 600 秒の上限。**`fetched_at` では切らない**（未来の話なので「入手できたか」は問わない） |
| 流量 | フィード本来の周期のまま計算し、その結果を `t` に as-of する（W3-11） |

**ラベル**

```
y_bike(t,h) = 1[ bikes(t+h) >= 1 かつ is_renting(t+h) ]
y_dock(t,h) = 1[ docks(t+h) >= 1 かつ is_returning(t+h) ]
```

**除外規則**（開発プラン §6.1。`t` 時点で判定できるものだけ）

| 除外する | 条件 |
|---|---|
| フィードの欠損 | `t` または `t+h` の as-of 状態が無い |
| ポートが観測されていない | 値が `-1`（Parquet では行が在って `bikes = -1`） |
| 休止中のポート | `t` 時点の `flags` に該当ビットが立っていない（実質 `flags = 1`） |
| 実在しないポート | ドコモの `5753`（監視用。EDA #1） |
| **衝突** | **`as-of(t+h)` が `as-of(t)` と同じ観測を指す**（W3-12。実測 0 件） |

**`stations.is_active` で除外しない**（生存者バイアス）。**`capacity = 0` で除外しない**（ドコモの動的値）。**補間しない。**

**抽出と重み**

| 層 | 条件 | 抽出率 | 重み |
|---|---|---|---|
| 一様 | すべて | 1% | 100 |
| 難所 | `bikes(t) <= 2` または `docks(t) <= 2` | ＋3% | 100/4 = 25 |

- 抽出の乱数は `(date, system_id, station_id)` のハッシュから導く（決定的）。
- **2 回抽選しない。** 行ごとにハッシュを 1 つ作り、難所なら閾値 4%、それ以外は 1% で判定する。「一様に 1% 引いてから難所を 3% 足す」と独立抽選になり、包含確率が `1 − 0.99 × 0.97 = 3.97%` になって重みが厳密でなくなる。**1 回の判定なら重みはちょうど 25 と 100 になる。**
- **評価は重み付きで行う**（開発プラン §6.2）。重み無しの値も並べて出す。
- 難所の実測比率は 45.4%（HELLO・h=5・午前）。抽出後の行数の見込みは **1 日 約 140 万行**（開発プラン §6.2 と一致）。

**出力**

```
features/date={YYYY-MM-DD}/part.parquet    # JST の暦日
```

列：キー（`system_id`, `station_id`, `t`, `h`）、特徴量（§6.3）、ラベル（`y_bike`, `y_dock`）、`weight`、`stratum`、`feature_set`。

### 9.4 天気アーカイブの入手時刻（PR D）

```sql
-- t 時点で入手できていた最新の予報ファイルの hour_epoch_s
select hour_epoch_s
  from public.v_weather_files
 where status = 'ok' and available_at <= $1     -- $1 = t
 order by available_at desc limit 1;
```

| 規則 | 内容 |
|---|---|
| 正 | `job_runs`（`archive_weather`）の `finished_at`。`v_weather_files.available_at` |
| フォールバック | 記録が無い時間帯は `hour_epoch_s + 3600`（保守的）。**使った件数を必ず出す** |
| してはいけないこと | `hour_epoch_s <= t` で引くこと。実際の保存は `hour_epoch + 約 18 分`なので、`t` が毎正時から 18 分の間にあると**まだ発行されていない予報**を使う（5 分グリッド点の 30%） |
| 定数化してよいか | **だめ。** 実測の遅延 17.64 分は cron の分（`17 * * * *`）に由来し、設定を変えれば変わる。過去のファイルは過去の時刻を持ち続ける |

### 9.6 ベースラインの定義（PR G）

| ID | 定義 | 備考 |
|---|---|---|
| **B0** | `P = 1[ bikes(t) >= 1 かつ is_renting(t) ]`（dock も同様） | 0/1 の硬い予測。Brier ＝ 誤り率 |
| **B1** | `P̂(y=1 ∣ system, bikes_bucket(t), h)` | 開発プラン §7.1 のまま。バケツは `{0, 1, 2, 3-5, 6-10, 11+}`。**§6.1 の除外規則を適用した集合の上でだけ当てはめる**（W3-15） |
| **B2** | `P̂(y=1 ∣ station, dow_type, slot15(t+h))` | セルのサンプル数が下限未満なら B1 に落とす。**落とした割合を報告する**（W3-17） |

**評価**：Brier・BSS（B0 基準）・log loss・ECE・信頼度図を、**水平 × ターゲット × バケツ**で出す。重み付きを主、重み無しを従として並べる。

**評価集合の規約**：どのモデルも**同じ行**の上で測る。件数が違えば比較は無効（§4.4 の 30b）。B0 も検証期間だけで測る。

**合格基準**（開発プラン §7.1 を W3-16 で更新する）：LightGBM v1 は、**Brier ≥ 0.001 のすべての（水平, ターゲット, バケツ）**で B3 の Brier を 10% 以上改善し、ECE < 0.03。Brier < 0.001 のバケツは判定の対象外にする（相対改善が数値ノイズになるため）。満たさない（水平, バケツ）では B3 を配信する。

## 12. 実装中に見つかった問題

### 77. 予報の窓は毎時スライドしない。夕方以降は先が足りない（段 0）

**Open-Meteo の `forecast_days` は「今日から数えた日数」であって「取得時刻から先の時間数」ではない。** 実測（13 時刻すべて）で、窓は取得時刻によらず **`2026-09-08T00:00` 〜 `2026-09-09T23:00`（JST・48 時間）で固定**だった。したがって**取得時刻から先の時間数は時刻とともに減る**。

| 取得（JST） | 窓 | 取得時刻から先の時間数 |
|---|---|---|
| 00:17 | 09-08 00:00 〜 09-09 23:00 | **48** |
| 06:17 | 同上 | 42 |
| 12:17 | 同上 | **36** |
| 23:17（見込み） | 同上 | **約 25** |

**含意**：`OPEN_METEO_FORECAST_DAYS = 2` は「48 時間先まで取れている」という意味ではない。夜に取ったファイルは翌日の昼までしか持たない。短期モデル（水平 3 時間）には影響しないが、**「今日これから降るか」の表示と、長期側で天気を使う道（開発プラン §8.1）には効く**。そして**天気は唯一あとから遡って取れない入力**なので、広げるなら早いほうがよい。

**広げる費用を実測した**（100 格子・本番と同じ変数とモデル）。

| `forecast_days` | 時間数 | 生バイト | gzip | 所要 | `jma_msm` の欠損 |
|---|---|---|---|---|---|
| **2（現行）** | 48 | 386,777 | 30,001 | 2.30 秒 | **0** |
| **3** | 72 | 535,986 | 43,423 | 2.44 秒 | **0** |
| 4 | 96 | 689,085 | 55,355 | 2.50 秒 | 2,000（20.8%） |
| 5 | 120 | 841,864 | 63,701 | 2.53 秒 | 4,400（36.7%） |
| 7 | 168 | 1,146,268 | 78,789 | 2.82 秒 | 9,200（54.8%） |

**`jma_msm` が値を返すのは当日 00:00 から数えて 76 時間ちょうど**で、そこから先は全格子いっせいに null になる（`forecast_days=4` で最初の欠損 index が全 25 格子とも 76）。`best_match` は 96 時間でも欠損 0。

**したがって `forecast_days = 3` が「`jma_msm` が欠けない最大」である。** 費用は容量 +45%（4.4 MB/日 → 約 6.4 MB/日、年 2.3 GB。Storage は 100 GB 込み）、所要 +6%、呼び出し回数は変わらない（144 回/日、無料枠 10,000 回/日 の 1.4%）。

**これは本番 Cron の挙動と容量を変えるので、実施には確認が要る**（CLAUDE.md §6）。実施する場合は開発プラン §4.5 の見積りも更新する。

| **35–40°** | **0.00%** | 151,632 |

**本州・四国・九州（緯度 30–40°）では 259,272 値がすべて一致する。** 元のコメントは東京で測ったもので、そこでは正しい。**全域では誤り**なので直す。該当するポートは沖縄 307 件・北海道の緯度 40° 以北で、**あわせて全 20,742 の 2% 前後**。

**W4 の「どちらのモデルを使うか決める」への入力**：本州域では選択が結果を変えない。変わるのは沖縄と北海道北部だけで、そこでは `jma_msm` の値が MSM の領域外の外挿である可能性が高い。**`precipitation_probability` は `best_match` にしか無い**（77 の表のとおり `jma_msm` は 100% 欠損）ので、いずれにせよ両方を保存し続ける判断（W2-03）は正しい。

### 79. 予報の実更新は 1 日 4〜8 回。毎時取得は冗長だが必要（段 0）

同じ格子・同じ対象時刻の降水量が前の時刻から変わった割合を、12 の遷移すべてで測った。

| 遷移（JST） | 変わった割合 |
|---|---|
| 00→01 | 0.00% |
| 01→02 | **69.48%** |
| 02→03 | 0.00% |
| 03→04 | **53.03%** |
| 04→05, 05→06, 06→07 | 0.00% |
| 07→08 | **52.04%** |
| 08→09 | 0.00% |
| 09→10 | **51.32%** |
| 10→11, 11→12 | 0.00% |

**12 回のうち値が変わったのは 4 回**（02:00・04:00・08:00・10:00 JST）で、間隔は **2〜4 時間**。

**含意**：(1) 保存容量の 3〜6 倍は同じ内容の重複だが、`weather-raw` は 1 日 4.4 MB なので最適化する理由が無い。(2) **「3 時間毎に取れば十分」ではない**。観測された最短間隔は 2 時間なので、3 時間毎だと発行を取り逃す。**毎時のままにする。** (3) 特徴量 `precip_mm_fcst_target` は 1 日に 4〜8 回しか変わらない。これはモデルの入力の性質としてモデルカードに書く。

### 80. 天気のパスも UTC の日付。JST の 1 日は 2 つの日付プレフィックスに跨る（段 0）

`weatherObjectPath` は `gbfs-raw` と同じく **UTC の日付**でディレクトリを切る（W2 プラン §9.1）。したがって **JST の 09-08 の 13 時刻は `2026/09/07` に 9 個・`2026/09/08` に 4 個**に分かれて置かれる。

この検証でも、JST の日付でパスを組み立てて **9 時刻ぶん（54 ファイル）が 400 で取れない**という形で一度踏んだ。§4.2 の 14（Parquet の `date=` / `hour=` は UTC）とまったく同じ落とし穴で、**天気にも当てはまる**。読み出しは必ず `storage.objects.name` か `weatherObjectPath` から組み立て、手で書かない。
